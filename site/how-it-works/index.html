An engineer's guide · from issue to pull request

How thirdshift works

You describe the work. thirdshift runs an unattended coding agent in its own Git checkout, asks it to implement and review the change, then checks the pull request against the repository's latest state. By default, you review before merging. A Ticket run Self-merges when asked.

Start with one issue below, then follow the same process into larger Specs and scheduled work. This guide describes the source on main; an installed release may differ.

01 / The human handoff

Start with work you can describe

The Day shift is you: settle what should change, what success looks like, and what is out of scope. Put that in a GitHub issue. One session's worth of work can stand alone; a larger Spec is an issue with Tickets as GitHub sub-issues. We'll follow a standalone issue first.

For issues labelled bug, a fresh Ticket run or Continuation uses /thirdshift-diagnosing-bugs before changing code. It captures a failing regression test, then fixes it. If the bug cannot be reproduced, it comments with triage notes, replaces ready-for-agent with needs-info and ends successfully with the comment link, without opening or merging a pull request. Security fixes and Base fixes keep their own flow.

From a clone of the issue's repository, normally checked out on your intended Base branch, start a Ticket run. In this example, main is the Base branch and the pull request will target it:

cd ~/repos/widgets
thirdshift --no-merge https://github.com/acme/widgets/issues/7

In that clone, thirdshift 7 also starts the issue's Ticket run: a bare issue number is resolved from origin. Add --no-merge to leave it for review regardless of your defaults. Command forms.

--no-merge explicitly leaves the pull request for review, even if your User config normally requests merging. Before starting, install and authenticate GitHub CLI (gh) and your chosen Harness (the agent CLI, such as Claude Code or Codex), configure Git's commit identity and push access, and install the repository's test toolchain. thirdshift setup chooses machine defaults and offers to save a Claude setup token, made with claude setup-token, with hidden input. That token is reserved for Trials; ordinary Runs use the Harness's existing login.

02 / Where the work happens

Give the Ticket run its own checkout

thirdshift checks that the Issue URL matches the clone's origin, that the issue is open, and that the Base branch, Harness and Git identity are usable. It selects an Issue branch, marks the issue in-progress (its Claim), then acquires a sibling Git Worktree. A fresh Issue branch starts from the fetched Base branch on origin.

The work happens in the Worktree rather than switching your Launch directory to the Issue branch. If an existing Issue branch has no pull request or an open one, thirdshift continues it instead of starting over. An open pull request supplies its Base branch. Once a branch's pull request is closed or merged, later work uses a new numbered Issue branch.

A checkout is not a sandbox. Except Trials and Graders, which run in bwrap sandboxes with their own networks, sessions run unattended as your user. The Harness has access to that account's files, credentials and tools; the separate Worktree keeps edits apart, but does not confine the process. Read the permissions and cleanup details.

03 / What the agent does

Let the agent implement and review

thirdshift starts a headless session in the selected Harness, in the Worktree. The Session prompt supplies the issue, Base branch, Issue branch and review instructions. Factory skills are linked where that Harness discovers them. The opening session carries the change from implementation through review to a committed branch and pull request.

The Standards axis checks repository coding standards and code smells. The Spec axis checks the change against the issue. For findings that say behavior is wrong, the implementing agent must run the reviewer's reproducer before deciding: a demonstrated failure gets fixed with its test kept; a declined finding needs evidence that exercises it. Skipped findings go in the pull request's Unaddressed findings section, and decisions for the Day shift get a linked triage issue.

These are agent reviews, followed by deterministic Git and CI checks in Delivery. They do not guarantee correctness or replace your judgment. You can inspect the exact prompts and Factory skills, including the review procedure.

04 / From a published change to a checked result

Deliver against the latest Base branch

A pull request existing is not the finish line. Delivery runs the opening session, then keeps the captured pull request mergeable and checks CI. This orchestration is thirdshift's code; a Repair is another agent session started when the branch needs work.

Repair and upstream-move budgets keep the loop bounded. If a CI-fix Repair leaves the same failing head, that head gets one Check re-run; if its own checks stay red, the Ticket run fails rather than spending more Repairs on unchanged code.

An Inherited failure is a check that also failed under the same name on the Base branch commit last merged in. thirdshift does not ask a Repair to fix that on this Issue branch. It fails the Ticket run, or, when allowed, starts a separate Base fix and waits before trying again.

An optional Security review runs after the opening session, including each Ticket, and after the Spec review for a Spec PR. It uses the User config's security.harness when set, and the Command's Harness otherwise. Preflight checks its Harness; an unavailable review Harness falls back to the default Harness. A Harness error before the first turn can also trigger that fallback once. The review fixes reproduced vulnerabilities introduced by this change; an introduced finding left unfixed holds Self-merge. Security review details.

05 / The result and your next move

Know what comes back

Ready for review

The usual successful result: an open pull request into the Base branch, ready, mergeable and passing CI (or with no checks). You review the diff, tests and Unaddressed findings before merging.

Merged, when requested

A thirdshift merge <Issue URL> command requests a Ticket run that Self-merges. thirdshift itself merges the exact head whose CI it watched. Foreign commits on the Issue branch are reconciled and their resulting changes reviewed first. Required human reviews can still block it, leaving the pull request ready for review.

Failed ticket run, with work preserved

Unfinished work is committed and pushed; an open pull request normally becomes a draft. If pushing fails, the Worktree and local Issue branch are kept. Rerun the same Issue URL to continue. A stopped or failed run may need Day shift attention before scheduled Pickup takes it again.

Ordinary cleanup removes the factory-owned Worktree and local Issue branch after work reaches origin; the remote work remains available for review or continuation. Cleanup retains resources when ownership or preservation is uncertain. A successful Self-merge also deletes the remote Issue branch and closes the issue. A merge refused by repository policy can fail the Ticket run while leaving the pull request ready.

If a Harness reports exhausted usage, the saved or emailed Run notification highlights it near the failure cause. For a Spec run it names the affected Tickets, while keeping each Ticket's error and any provider-reported reset time in the details. Retry the Recovery command when usage is available.

You can watch progress without interrupting the agent:

thirdshift status
thirdshift show https://github.com/acme/widgets/issues/7
thirdshift logs https://github.com/acme/widgets/issues/7 --follow

When a Ticket run ends, its Command record keeps its Run metrics: outcome, Repairs, CI rounds, Unaddressed findings by Standards, Spec and Security from Delivery's final PR body, minutes in each stage and in total, and each stage's time against its Usual range. The Unaddressed findings counts include the Security review. Each Session stage also keeps the review's Standards and Spec finding counts from its summary, including findings later fixed or declined; missing counts stay missing. Ticket runs and Base fixes keep their own. Read them with thirdshift show <Issue URL> --json. thirdshift metrics <command> [--json] shows one Ticket run with its children, and thirdshift metrics [--json] shows weekly trends by repository, Harness, Model, Effort and kind of session. Narrow trends with --from and --through Monday week-start dates and repeatable --repo owner/repository. Past records are computed when read, with missing signals left missing. Every signal stays separate.

Session traces add tokens by observed Model (input, output, cache read and cache write), cost only where the Harness reports it, and counts of tool errors, permission denials, killed work and repeated calls to the same tool with the same input in one session. Run metrics sum them by session kind. Weekly Session trends also split by the Harness version recorded in each trace. Past Ticket runs gain these signals when metrics read their converted traces; absent traces stay missing.

When metrics are read, confirmed Bug origins count against the Ticket run that introduced each bug, even if confirmed after it ended. The local Scoring data covers both hosts; metrics match only this machine's Ticket runs and add the counts to their start weeks in weekly Ticket run trends. Rejected and unsettled origins count for nothing, and corrections use the settled pull request.

Every Ticket run checks its sessions' shell commands against a code-owned list of destructive-command patterns: force pushes, shared-branch history rewrites and recursive deletes outside the Worktree. Matches stay with their original command in Run metrics. These flags are advisory and never block or fail a Ticket run; weekly Session trends count them.

Run metrics and Experiments share Session usage rules. Partial totals replace only reported fields, preserving known input, cache counts and cost. Input includes cache reads and writes. A reported Session cost wins; otherwise each Model's reported cost replaces its call costs. Missing measurements stay missing, and saved completion metrics stay fixed.

CLI log following and the Console keep reading through the captured writer's exit, including final output written after a Command's outcome is recorded. An exact Session trace finishes when its writer exits or its owning record moves to a later Session.

The Console shows this machine's Commands, opening on its Inbox. Beside the CLI, you can watch their stages and logs there. Open Command details for a Ticket run's metrics, including available historical signals and late Bug-origin confirmations; unavailable signals say Missing. Stages keeps each Spec run with its Ticket runs, newest-started groups first, filling the window's width beside any open Command details: scroll right for older runs, or switch from All runs to By repository for one grid per repository. When a later Command takes up an issue, the earlier row stays in Resolved for inbox.days from that Command's start, saying why it left.

The Console reads ready rows' pull requests and Needs you rows' issues and pull requests from GitHub in the background once a minute, even with no pages open. A changed answer wakes open Inbox pages; an unchanged answer leaves them idle. thirdshift status uses the same kept answer and reads GitHub itself only when it is missing or five minutes old. An ended Needs you row leaves once its issue closes or its pull request merges; a Triage row also leaves when needs-triage is removed. Architect and Security runs use the issue and pull request of the Spec run or Ticket run they dispatched. A pull request closed unmerged leaves a failure waiting while its issue is open. Live Silent and Slow rows wait until their Commands end. A merged or closed pull request takes its row out of Ready for review. Each exit says why, with Resolved counted from when GitHub shows it settled. Rows GitHub can speak for keep waiting however old they are. Reopening brings back a row still in Done or Resolved; History keeps the last facts and is not read again. Dismissals hold through GitHub changes; Undo uses GitHub's latest kept facts. Rows with no issue or pull request, no Command record, no read yet or nothing GitHub can find still age out, straight to History.

When GitHub cannot answer, each row keeps the group its last facts give it; a row never read still goes by age. After five minutes without a good read, the Console and status warn with the last-answer time and latest failure. A successful read clears that warning. With fewer than 500 GraphQL points or 500 REST requests left, both skip reads until that quota resets and say why, leaving the rest to the factory. status --json gives the last-answer time and latest failure. These limits are fixed, with no User config settings.

status --json also gives each row's kept GitHub facts and when they were read. History keeps those observation times with its facts. A dismissed row stays in Resolved for inbox.days from its dismissal; a later GitHub settlement does not extend it.

Each Needs you row has a Copy button to share its problem with an agent. It copies the machine, Command, state, cause, issue title and run details, with issue, pull request and Console log links and the thirdshift show '<command>' --json command. If the browser cannot use the clipboard, a dialog selects the text for copying by keyboard and keeps it through live updates.

For this machine on localhost, start the Console with:

thirdshift console --no-sign-in

Above its groups, the Inbox counts the active runs, such as 2 active runs: each Command with live work counts once, wherever its row sits, so a Spec run's Tickets and the run a Pass dispatched are part of that one. thirdshift status shows the same count.

The Inbox and thirdshift status show when each repository's Pickup, Architect and Security Pass last fired, including repeated skips with the same reason. When no Commands are running, the Inbox points to work waiting for you and offers the last recorded skipped Pass reasons under Last recorded skipped Passes, folded closed on each page load. Open it to read the reasons; live updates keep it open while you read. Cron jobs and thirdshift cronjobs show the same last-fired times beside this account's schedules to help diagnose launch failures.

Ended rows show the recorded finish date and time in UTC and an explicit age, such as Ended Oct 23, 2026 at 23:03:17 UTC · 52 min ago. The age means time since finish, not run duration. Nested Ticket runs and History show each Command's own finish; an unavailable finish says End time unknown.

For a server, thirdshift console install prints an installation script to read and run with sudo, putting its Console behind a sign-in. The script checks that the Console is active and answering on its localhost port before setting up the proxy; failed startup prints recent journal lines and exits nonzero. On an SELinux-enforcing host it also warns that SELinux can block the Console. Console installation and machine status.

The Console's Resources page and thirdshift resources show available memory and one-minute CPU load. Optional [resources] limits in the User config make each new session wait while the host is busy; sessions already running continue.

A signed-in Console account can Stop a live Command or Requeue it for Pickup. The CLI does the same:

thirdshift stop <command>
thirdshift stop <command> --requeue

Stop waits for cleanup and leaves the issue for the Day shift, labelled needs-triage. With --requeue, it releases the Claim and puts ready-for-agent back so Pickup can continue the work. Stopping a Command.

A row in Needs you or Ready for review that asks nothing more can be Dismissed instead, live ones included. Any signed-in Console account can click Dismiss directly on the Inbox row or in Command details, beside Stop when available, with no confirmation page. A dismissed row offers Undo there. Both buttons immediately show pending feedback and stay disabled while saving, including through live updates; a failed request shows its error and lets you retry. The CLI forms appear beside the buttons in Command details: thirdshift dismiss <command> and thirdshift dismiss <command> --undo. Every open page updates, and the Activity log names the account's email and the Console. Nothing else changes: the Command keeps running and nothing is written to GitHub. Dismissing a row.

Slow becoming Silent, Silent becoming Slow, or a live Command dying, failing or ending ready brings a dismissed row back. A dismissed Security failure returns as a Finding only while GitHub still shows its findings waiting. One paginated REST list per repository with such a Security run reads the private records, respecting the quota reserve. A Finding leaves saying “findings triaged” once all its records are triaged: draft advisories without severity and open security-finding issues labelled needs-triage still wait; records closed by a merged fix do not. The kept answer holds waiting flags, never titles, severities or write-ups. Dismissing again adds the new kind; another Ticket going Silent in the same Spec run does not repeat a kind already dismissed.

The Command log records the whole command; a Session trace records each agent session, and the Activity log records starts and outcomes per repository. Export a Command's whole Trace for another tool with thirdshift logs <command> --export <dir>. Optional email notifications report how the Ticket run ended. Inspecting logs and exporting Traces.

06 / The same primitive, composed

Scale one Ticket run into a Spec run

When the Issue URL has Tickets as GitHub sub-issues, thirdshift starts a Spec run. GitHub's “blocked by” links determine when a Ticket can start. Independent Tickets can run in parallel, each in its own Worktree; a blocked Ticket waits for its prerequisites to land.

Each Ticket gets a Ticket run that Self-merges into the Spec branch, not directly into main. The Spec PR gathers the result into the Base branch. A Ticket closing means its work landed on the Spec branch; the whole Spec has not shipped yet.

A failed Ticket stops only its dependents; other reachable Tickets can still run. Tickets marked for human work or triage also hold their dependents. An incomplete Spec leaves a draft Spec PR with a Tickets checklist. An Unready Ticket's checklist and Command log line name its open blockers, marking those outside the Spec and those labelled ready-for-agent; outside blockers are reported but never run. Rerunning continues existing branches. Spec run controls and limits.

07 / Where the next issue comes from

Choose how the next work starts

A direct Issue URL starts work you have already chosen. Other commands find work, then dispatch the same Ticket run or Spec run you just followed. Each invocation makes one pass; your operating system's scheduler starts the next one.

To run one skill directly, use thirdshift skill <skill> [issue <issue>]. It starts one headless session on your default Harness, Model and Effort in a temporary worktree at your checkout's committed HEAD, and prints the final message. Worktrees with local work are kept. Standalone skills.

thirdshift process is experimental, beside thirdshift skill. It runs the Steps in ~/.thirdshift/processes/<name>.toml, a skill session or a command. Consecutive Steps can run together, each in a throwaway worktree the file names, and the last finished Step's result is printed. An optional Step can fail without stopping the process. thirdshift process <name> issue <issue> gives the process an issue, so each session Step works from that issue. With no issue it is a Pass and skips while another Pass on the repository is running, without an Architect run's Ready-issue or Architect-idea gates. With an issue, it is not a Pass. Custom processes.

Pickup respects issue readiness, open blockers and the Claim limit. Before choosing work, it files one ordinary bug Ticket if the Base branch's latest push CI failed more than 30 minutes ago and no CI-red Ticket is open. CI read failures warn and let Pickup continue; red Base CI does not hold Self-merges. Architect and Security runs yield to ready human-shaped work. Gates can skip a pass without failure, and unresolved plans, ideas or findings can leave the next decision with the Day shift. This is scheduled CLI work on your machine, using your authenticated tools.

When a Security run fails before its audit starts, its requested Run notification names a fixed Cause for Base branch preparation failures, such as Base branch not found, and points to stderr on the host at the command's start time for diagnostics. Security run notifications.

Before dispatch, Pickup reserves its selected issue on origin and checks that it is still Ready. Competing Pickup runs on two machines cannot take the same issue: only the reservation's owner can dispatch it. The reservation's commit message records its host, launch path, process and start time. After a crash, the reservation waits for the Day shift to confirm its owner has stopped and release it. Pickup's reservation and readiness checks.

Scoring runs sample merged factory pull requests across the GitHub owners in [scoring]. Start one with thirdshift score; thirdshift scores --json lists samples by week. Each sample gets a blind packet: historical issue text, merged diff, pull request, CI names and conclusions, and repository files at the merge. Attribution lines are removed from the text and repository files; Git metadata is removed. Its Command appears in the Inbox and can be Stopped. A Grader on a different Model scores Correct, Scoped, Tested, Honest and Standards in the Experiment sandbox, with the repository read-only. Each Score has a reason. A plan-limit warning stops grading; the next Scoring run finishes pending packets without repeating completed Scores. Every closed bug except a Security fix also gets a Bug-origin proposal, whoever fixed it. A sandboxed session reads the fix and earlier history, naming a commit only with evidence; GitHub maps it to pull requests and their Runs. The first proposal run backfills all closed bugs. Read them with thirdshift bug-origins [issue] --json, then settle one with --confirm, --correct <pull request> or --none. A confirmed origin counts against its retained Ticket run in show --json and proposes a code-review Eval task holding the historical PR diff and a draft catch criterion. Rejected and unsettled origins count for nothing; proposed Eval tasks need explicit approval before Experiments can use them. A plan-limit warning during Bug-origin analysis stops Scoring without advancing its window.

Scoring samples, Bug-origin proposals and settlements, and Run metrics share retained pull-request attribution. Matching ignores ASCII letter case and trailing slashes. Latest means chronological RFC 3339 time, including UTC offsets, then greatest lexical record path and Command name for ties; invalid times sort before valid ones. Saved local record-path/name pairs select that exact Command under the matching pull request. Missing or mismatched local identities count for nothing; only absent or cross-host attribution selects the latest local Command, so Continuations never multiply a count.

The first run also draws 20 historical pull requests for your Scores, spread across Harnesses and Models. Later runs mark two per week. Enter yours with thirdshift scores <pull request> --mine: all five pass/fail answers and reasons are saved before the model's Scores appear, including in ordinary CLI views. Add --json to return the saved result as JSON. Text and JSON views show each revealed criterion as calibrated when at least 18 of the last 20 paired Scores agree; an uncalibrated criterion leaves the others alone.

You can also enter your five Scores on the Console's Scores page, beside the weekly sample and criterion calibration. The model's Scores stay hidden until yours are saved. The Bug origins page offers the CLI's Confirm, Correct and Reject actions for proposed and settled origins. Both pages work on a phone; reload to see changes made elsewhere.

For offline Eval data, thirdshift evals list lists private suites and proposed Eval tasks, evals touched selects suites by their declared dependencies, and evals prepare prepares approved Eval tasks for inspection at a detached base with the reviewed patch staged. Spec-review repositories get a local bare origin. Before launching an Arm, complete Trial preparation creates the requested branches and synthetic reviewed commit, publishes Spec-review refs to that origin and excludes the issue input, all under isolated Git settings before publishing the repository. evals prepare-arms caches each Arm's build by commit and records its Harness's real path and version before Trials, keeping symlink updates from switching the Harness between Arms. On the host holding #429's private material, evals import-replays imports its manifests and grading files into the code-review and Spec-review suites, including their Trial inputs. Rerunning adds missing Eval tasks and completes missing Trial inputs, preserving local edits. These commands start no agent sessions. Eval task commands and format.

Experiments, including release Experiments, name approved Eval tasks missing Trial inputs before building either Arm. Before each Trial's session, the host prepares its repository's pinned Rust toolchain and listed components. Trials with the same pin share preparation; an installation failure makes the Trial void with session_unavailable. Spec review Trials keep the production prompt, with no PR service: gh calls fail in the sandbox and only their reports are graded.

thirdshift experiment runs Code review and Spec review Trials. A Code review uses the production review skill on the historical diff, retaining both reports without fixing or publishing anything. The code-review suite runs three Trials per Arm per Eval task and reports pass^3, the share where all three passed; the Spec-review suite runs one. Experiments.

thirdshift experiment <candidate> builds the Baseline and Candidate Arms and runs their Trials with two workers, keeping the Bar fixed. Code Graders score mechanical checks, then fresh model Graders score written criteria from one blind packet per Eval task. Scores retain reasons, wrong findings and borderline marks; the paired Verdict shows each suite's interval with each Arm's minutes, tokens by Model, reported cost and Void causes. Trial and model Grader Session traces and code Grader spans join the Command's Trace. Void Trials retry fresh up to twice; an exhausted task drops out of both Arms, and more than a tenth dropped makes the Verdict inconclusive. Repeated Trial-only memory-cap stops appear as an Arm finding. A plan-limit warning pauses new Trials and makes any Trial cut short void; the same command resumes paused or interrupted work. Ordinary Runs keep running at warnings. thirdshift experiments [id] --json lists or shows saved results. A pass goes in Done; a fail or inconclusive Verdict goes in Needs you. Experiments accept Stop. Trials and model Graders run in bwrap sandboxes with provider-only networks. Model Graders see only their blind packets; Code Graders run offline with report packets and the prepared repository. Graders cannot read raw Trial logs, Arm mappings or the Experiment’s other files. Experiment commands.

Provider capacity and overload errors void a Trial with rate_limit and pause the Experiment. Start the same Experiment again to retry under its saved Bar.

Review commits, local-origin pushes and repository reports do not void a Trial. Changing its issue text, declared inputs or commits under review does. Mechanical checks grade a private copy of the prepared repository captured before the session.

The Console's Experiments list groups Running, Needs you and Done, newest first. Open one to watch Trials fill in, then see the Verdict by suite. The page compares Arms, folds the Bar and opens a Trial or Eval task in the Peek with Grader reasons and links to Session logs or Session traces. Rechecks stay in the CLI, with copyable commands and a filter for their Eval tasks.

Proposed Eval tasks appear on the Experiments list and, for its suites, on each Experiment page. Approve one there or with thirdshift evals approve <suite> <task> --json to change its state in its suite, preserving its inputs. Approval starts no work and affects future Experiments; existing Experiments keep their fixed Eval tasks on resume. Unapproved proposals never run.

Each Trial and each Grader runs in its own memory-capped scope and raises its OOM score to give way before the factory. The User config defaults to 1 GiB for throttling, 2 GiB for killing and 1 GiB of swap per scope. Enable lingering once with loginctl enable-linger <user>; an Experiment stops before dispatch if it cannot reach the systemd user manager.

A Verdict stays waiting on rechecks until you have checked every borderline Score and every decisive Score, whose flip would change the Verdict. The pending list gives Trial IDs for thirdshift recheck <id> <trial> pass|fail --reason '…'. Your latest decision feeds the calculation; the Grader's Score and your timestamped history remain. Each recheck updates the pending list and the latest invocation's Command outcome and Inbox group. A confirmed pass moves from Needs you to Done.

thirdshift experiment --release <commit> compares touched suites with the last release tag. The release script waits for rechecks before pushing and asks whether to release on a fail or inconclusive Verdict. Reruns reuse the Experiment, including before opening a pushed branch’s PR. If main gains different content, the script refuses to publish it under the old Candidate's Experiment; choose a fresh release version. No touched suite or a last release with no Trial flag carries on with a note. Release checks.

Architect runs every few minutes and Security runs on a schedule, with fixing allowed, started by your operating system.
