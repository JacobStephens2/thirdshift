An engineer's guide · from issue to pull request

How thirdshift works

You describe the work. thirdshift runs an unattended coding agent in its own Git checkout, asks it to implement and review the change, then checks the pull request against the repository's latest state. By default, you review before merging. A Ticket run Self-merges when asked.

Start with one issue below, then follow the same process into larger Specs and scheduled work. This guide describes the source on main; an installed release may differ.

01 / The human handoff

Start with work you can describe

The Day shift is you: settle what should change, what success looks like, and what is out of scope. Put that in a GitHub issue. One session's worth of work can stand alone; a larger Spec is an issue with Tickets as GitHub sub-issues. We'll follow a standalone issue first.

For issues labelled bug, a fresh Ticket run or Continuation uses /thirdshift-diagnosing-bugs before changing code. A fresh run, or a Continuation with nothing on the Issue branch beyond the Base branch, reproduces on that checkout. A Continuation whose Issue branch is ahead of the Base branch reproduces at their merge base, then checks the fix on the branch: a bug there, with the fix already on the branch, goes on to review and the pull request. Otherwise it captures a failing regression test, then fixes it. If the bug cannot be reproduced at that checkout, it comments with triage notes, replaces ready-for-agent with needs-info and ends successfully with the comment link, without opening or merging a pull request. Flaky-test Tickets use the recorded CI failure as evidence and go straight to implementation. Security fixes and Base fixes keep their own flow.

From a clone of the issue's repository, normally checked out on your intended Base branch, start a Ticket run. In this example, main is the Base branch and the pull request will target it:

cd ~/repos/widgets
thirdshift --no-merge https://github.com/acme/widgets/issues/7

In that clone, thirdshift 7 also starts the issue's Ticket run: a bare issue number is resolved from origin. Add --no-merge to leave it for review regardless of your defaults. Command forms.

--no-merge explicitly leaves the pull request for review, even if your User config normally requests merging. Before starting, install and authenticate GitHub CLI (gh) and your chosen Harness (the agent CLI, such as Claude Code or Codex), configure Git's commit identity and push access, and install the repository's test toolchain. thirdshift setup chooses machine defaults and offers to save a Claude setup token, made with claude setup-token, with hidden input. That token is reserved for Trials; ordinary Runs use the Harness's existing login.

02 / Where the work happens

Give the Ticket run its own checkout

thirdshift checks that the Issue URL matches the clone's origin, that the issue is open, and that the Base branch, Harness and Git identity are usable. It selects an Issue branch, marks the issue in-progress (its Claim), then acquires a sibling Git Worktree. A fresh Issue branch starts from the fetched Base branch on origin.

The work happens in the Worktree rather than switching your Launch directory to the Issue branch. If an existing Issue branch has no pull request or an open one, thirdshift continues it instead of starting over. An open pull request supplies its Base branch. Once a branch's pull request is closed or merged, later work uses a new numbered Issue branch.

A checkout is not a sandbox. Except Trials and Graders, which run in bwrap sandboxes with their own networks, sessions run unattended as your user. The Harness has access to that account's files, credentials and tools; the separate Worktree keeps edits apart, but does not confine the process. Read the permissions and cleanup details.

03 / What the agent does

Let the agent implement and review

thirdshift starts a headless session in the selected Harness, in the Worktree. The Session prompt supplies the issue, Base branch, Issue branch and review instructions. Factory skills are linked where that Harness discovers them. The opening session carries the change from implementation through review to a committed branch and pull request.

On Claude and Grok, a Session's completion line survives later background-task notifications. A later reply carrying a completion line takes precedence.

Command records and Session traces retain each run's Process name, whether it is Built-in or Custom, and its file's SHA-256 hash. Each child Ticket run records its selected Process separately from its parent, defaulting to ticket-run. A run awaiting a Built-in file keeps its run-type name without a hash. Status, the Console, the Activity log and Run notifications keep their existing names.

A session Step in a Custom process gets the same single Resume as a Ticket run when background work was killed as its turn ended. If the Resume ends the same way, a progress line names the work and the following Steps decide the outcome. A later Process failure names the killed work ahead of the failing Step. Resumes do not count against the Repair cap.

The Standards axis checks repository coding standards and code smells. The Spec axis checks the change against the issue. For findings that say behavior is wrong, the implementing agent must run the reviewer's reproducer before deciding: a demonstrated failure gets fixed with its test kept; a declined finding needs evidence that exercises it. Skipped findings go in the pull request's Unaddressed findings section, and decisions for the Day shift get a linked triage issue.

These are agent reviews, followed by deterministic Git and CI checks in Delivery. They do not guarantee correctness or replace your judgment. You can inspect the exact prompts and Factory skills, including the review procedure.

04 / From a published change to a checked result

Deliver against the latest Base branch

A pull request existing is not the finish line. Delivery runs the opening session, then keeps the captured pull request mergeable and checks CI. This orchestration is thirdshift's code; a Repair is another agent session started when the branch needs work.

Repair and upstream-move budgets keep the loop bounded. If a CI-fix Repair leaves the same failing head, that head gets one Check re-run; if its own checks stay red, the Ticket run fails rather than spending more Repairs on unchanged code.

An Inherited failure is a check that also failed under the same name on the Base branch commit last merged in. thirdshift does not ask a Repair to fix that on this Issue branch. It fails the Ticket run, or, when allowed, starts a separate Base fix and waits before trying again.

An optional Security review runs after the opening session, including each Ticket, and after the Spec review for a Spec PR. It uses the User config's security.harness when set, and the Command's Harness otherwise. Preflight checks its Harness; an unavailable review Harness falls back to the default Harness. A Harness error before the first turn can also trigger that fallback once. The review fixes reproduced vulnerabilities introduced by this change; an introduced finding left unfixed holds Self-merge. Security review details.

05 / The result and your next move

Know what comes back

Ready for review

The usual successful result: an open pull request into the Base branch, ready, mergeable and passing CI (or with no checks). You review the diff, tests and Unaddressed findings before merging.

Merged, when requested

A thirdshift merge <Issue URL> command requests a Ticket run that Self-merges. thirdshift itself merges the exact head whose CI it watched. Foreign commits on the Issue branch are reconciled and their resulting changes reviewed first. Required human reviews can still block it, leaving the pull request ready for review.

Failed ticket run, with work preserved

Unfinished work is committed and pushed; an open pull request normally becomes a draft. If pushing fails, the Worktree and local Issue branch are kept. Rerun the same Issue URL to continue. A stopped or failed run may need Day shift attention before scheduled Pickup takes it again.

Ordinary cleanup removes the factory-owned Worktree and local Issue branch after work reaches origin; the remote work remains available for review or continuation. Cleanup retains resources when ownership or preservation is uncertain. A successful Self-merge also deletes the remote Issue branch and closes the issue. A merge refused by repository policy can fail the Ticket run while leaving the pull request ready.

If a Harness reports exhausted usage, the saved or emailed Run notification highlights it near the failure cause. For a Spec run it names the affected Tickets, while keeping each Ticket's error and any provider-reported reset time in the details. Retry the Recovery command when usage is available.

The local Scoring data covers both hosts; metrics match only this machine's Ticket runs and add the counts to their start weeks in weekly Ticket run trends. Rejected and unsettled origins count for nothing, and corrections use the settled pull request.

Every Ticket run checks its sessions' shell commands against a code-owned list of destructive-command patterns: force pushes, shared-branch history rewrites and recursive deletes outside the Worktree. Matches stay with their original command in Run metrics. These flags are advisory and never block or fail a Ticket run; weekly Session trends count them.

Run metrics and Experiments share Session usage rules. Partial totals replace only reported fields, preserving known input, cache counts and cost. Input includes cache reads and writes. A reported Session cost wins; otherwise each Model's reported cost replaces its call costs. Missing measurements stay missing, and saved completion metrics stay fixed.

06 / The same primitive, composed

Scale one Ticket run into a Spec run

When the Issue URL has Tickets as GitHub sub-issues, thirdshift starts a Spec run. GitHub's “blocked by” links determine when a Ticket can start. Independent Tickets can run in parallel, each in its own Worktree; a blocked Ticket waits for its prerequisites to land.

Each Ticket gets a Ticket run that Self-merges into the Spec branch, not directly into main. The Spec PR gathers the result into the Base branch. A Ticket closing means its work landed on the Spec branch; the whole Spec has not shipped yet.

A failed Ticket stops only its dependents; other reachable Tickets can still run. Tickets marked for human work or triage also hold their dependents. An incomplete Spec leaves a draft Spec PR with a Tickets checklist. A Spec PR closed, merged or retargeted mid-run starts no further Ticket, holds the Self-merge of a running Ticket started after it opened, and ends the Spec run without a Recovery command. An Unready Ticket's checklist and Command log line name its open blockers, marking those outside the Spec and those labelled ready-for-agent; outside blockers are reported but never run. Rerunning continues existing branches. Spec run controls and limits.

07 / Where the next issue comes from

Choose how the next work starts

A Custom process can use fix-findings → close-findings to fix reproduced Security findings and close only merged fixes whose proof-of-concept passes against the merged Base branch. The Steps keep private records and the Security run’s fixing and closing permissions. fix-findings can select a child Ticket Process with process; it defaults to ticket-run. Failed fixes and failed rechecks stay with the Day shift. Their sessions and the Ticket runs they start stay off any configured OTLP endpoint, as a Security run's do. The Built-in Security run still fixes at most one finding per invocation.

A direct Issue URL starts work you have already chosen. Other commands find work, then dispatch the same Ticket run or Spec run you just followed. Each invocation makes one pass; your operating system's scheduler starts the next one.

To run one skill directly, use thirdshift skill <skill> [issue <issue>]. It starts one headless session on your default Harness, Model and Effort in a temporary worktree at your checkout's committed HEAD, and prints the final message. Worktrees with local work are kept. Standalone skills.

thirdshift process is experimental, beside thirdshift skill. It runs the Steps in ~/.thirdshift/processes/<name>.toml, a skill session, a command, or a catalogue Step. delivery publishes the Issue branch. run-published-issue starts a Ticket run or a Spec run on the issue the session Step before it published. Its optional process = "<name>" setting selects the child Ticket Process, defaulting to ticket-run; it must exist and declare an Issue-branch worktree. An issue with Tickets still starts a Spec run. Consecutive Steps can run together, each in a throwaway worktree the file names, and the last finished Step's result is printed. An optional Step can fail without stopping the process. thirdshift process <name> issue <issue> gives the process an issue, so each session Step works from that issue. One Issue-branch worktree plus delivery publishes a ready-for-review pull request from that Issue branch and then removes the Claim. A self-merge Step directly after it merges when merge or the User config asks, and a file can only tighten limits. With no issue, and neither an Issue-branch nor a Spec-branch worktree, it is a Pass and skips while another Pass on the repository is running, without an Architect run's Ready-issue or Architect-idea gates. With an issue, it is not a Pass. Status, the Console and the Activity log list it as Process <name>, and a failed one is in Needs you. It sends a Run notification under the same email rules as a Ticket run, except a skipped Process sends none. Custom processes.

A Step may name its own Harness, Model and Effort. Each omitted setting inherits the Command's resolved value, including --harness and User config choices. process check prints each choice, its origin and whether the Harness starts. thirdshift process list lists Processes and marks Built-in processes; process show <name> prints a Process file exactly, ready to save under a new Custom process name. The compiled-in ticket-run file runs implement → security-review → delivery → self-merge. Ticket runs execute it by default, including those started by Spec, Architect and Security runs, inheriting the Command's Harness, Model and Effort, Child asks and Limits. The Security review and Self-merge still run only when asked. Inspect it with thirdshift process show ticket-run, or check it with thirdshift process check ticket-run issue <issue>.

Spec runs execute the compiled-in spec-run file: land-tickets → spec-review → security-review → delivery → self-merge, on a spec-branch worktree. Every starter uses it: an Issue URL, Pickup, Architect and Security runs, and run-published-issue. Dispatch, the Claim, Child asks and Limits stay in front of the file. The run keeps its sessions, progress lines and Spec run name, and records the compiled file's hash. Inspect it with thirdshift process show spec-run or validate it with thirdshift process check spec-run issue <spec>; its name is reserved against Custom processes.

Security runs execute the compiled-in security-run file: security-audit → reproduce-findings → fix-findings → close-findings. The Pass lock and Ready-issue, failed-fix and unchanged-Base skip gates stay before the file. An earlier reproduced finding awaiting an allowed fix makes the first two Steps skip. The run fixes at most one finding and closes only that finding after its fix merges and its proof passes. Sessions, progress, logs, Run notifications and the Security run name stay the same, with the compiled file's hash recorded. Inspect it with thirdshift process show security-run or validate it with thirdshift process check security-run; its name is reserved against Custom processes. A copy under a new name takes only the shared Pass lock and can fix several findings.

Pickup has no Built-in process file. It selects and reserves a Ready issue, then dispatches ticket-run or spec-run.

Architect runs execute the compiled-in architect-run file: architecture-review → run-published-issue, after their Pass lock and open-plan, waiting-idea and Ready-or-settling-issue gates. The review Step owns its session, conclusion and labels, ending successfully on an idea or with --plan-only; otherwise the next Step runs the plan. Read it with thirdshift process show architect-run, or validate it with thirdshift process check architect-run. A copy under a new Custom process name takes only the shared Pass lock. The Architect run's name, progress, logs and Run notification stay the same, with the compiled file's hash retained in its records and Session traces.

A Custom process can use a spec-branch worktree and land-tickets to run a Spec's Tickets in dependency order, up to spec.parallel at once, with the same refusal checks and failure accounting as a Spec run. The first landing opens a draft Spec PR with its Tickets checklist; the Step's process setting chooses every child Ticket's Process. An Issue-branch file refuses Specs, a Spec-branch file requires one, and a file cannot declare both. Both require an issue and make the Claim before the worktree; a draft Spec PR keeps its Claim.

After land-tickets, spec-review reviews the whole Spec branch against the Base branch with the Spec run's prompt and report contract. Follow it with security-review, delivery and self-merge on the same worktree. Delivery restores the Tickets checklist and leaves the Spec PR ready, removing its Claim; Self-merge merges only when asked. Security review runs only when the command or User config asks, and a refused or incomplete review holds the merge. Each Step takes its own Harness, Model and Effort.

Add catalogue = "implement" on the Issue-branch worktree before delivery to use the Ticket run's fresh or Continuation implementation session. It diagnoses ordinary bug issues first; Flaky-test Tickets use recorded evidence directly. When a bug is not reproduced, the Process ends successfully with triage notes and needs-info, skips later Steps and cleans up the Claim and worktree.

A Custom process can run security-audit → reproduce-findings: audit the Base branch in a throwaway worktree, record findings privately, then reproduce and score each at its audited commit. Both required Steps run outside parallel groups with their own Harness, Model and Effort. Repeated findings keep completed reproductions and the Day shift's grades. With security-fix or the User config allowing fixes, each Step skips when a recorded finding awaits a fix. The Steps publish no findings, and their traces stay local even with OTLP configured. Security runs execute security-run after their existing skip gates.

Use architecture-review → run-published-issue to review the Base branch and build a Strong Architect plan. The review owns a fresh throwaway worktree, the plan checks and the plan-or-idea labels. An Architect idea or the command's --plan-only ends successfully, skips later Steps and records why. Each Step can choose its own Harness, Model and Effort. The Architect run's skip gates stay outside the Step.

Add security-review after editing the Issue branch and before delivery for the Ticket run's Security review. It runs when security-review or the User config asks, and no-security-review skips it. Its configured Harness can fall back to the default; a Harness the Step names explicitly must start before any session. A refused or incomplete review leaves the PR ready and holds a following Self-merge.

Pickup respects issue readiness, open blockers and the Claim limit. Before choosing work, it re-runs failed jobs of the Base branch's latest push CI once, immediately. Green on re-run files a Flaky-test Ticket using the recorded failure as evidence, without requiring reproduction on demand. Red again files an ordinary bug Ticket after 30 minutes from the re-run's completion. An open CI-red Ticket in needs-info does not block a new report; another open CI-red Ticket receives new failing commits as comments. CI read failures warn and let Pickup continue; red Base CI does not hold Self-merges. Architect and Security runs yield to ready human-shaped work. Gates can skip a pass without failure, and unresolved plans, ideas or findings can leave the next decision with the Day shift. This is scheduled CLI work on your machine, using your authenticated tools.

When a Security run fails before its audit starts, its requested Run notification names a fixed Cause for Base branch preparation failures, such as Base branch not found, and points to stderr on the host at the command's start time for diagnostics. Security run notifications.

Before dispatch, Pickup reserves its selected issue on origin and checks that it is still Ready. Competing Pickup runs on two machines cannot take the same issue: only the reservation's owner can dispatch it. The reservation's commit message records its host, launch path, process and start time. After a crash, the reservation waits for the Day shift to confirm its owner has stopped and release it. Pickup's reservation and readiness checks.

Scoring runs sample merged factory pull requests across the GitHub owners in [scoring]. Start one with thirdshift score; thirdshift scores --json lists samples by week. Each sample gets a blind packet: historical issue text, merged diff, pull request, CI names and conclusions, and repository files at the merge. Attribution lines are removed from the text and repository files; Git metadata is removed. Its Command appears in the Inbox and can be Stopped. A Grader on a different Model scores Correct, Scoped, Tested, Honest and Standards in the Experiment sandbox, with the repository read-only. Each Score has a reason. A Claude or Codex quota window at 85%, or a Claude rejection, stops grading. A Claude warning with no readable utilization also stops grading. The next Scoring run finishes pending packets without repeating completed Scores. Every closed bug except a Security fix also gets a Bug-origin proposal, whoever fixed it. A sandboxed session reads the fix and earlier history, naming a commit only with evidence; GitHub maps it to pull requests and their Runs. The first proposal run backfills all closed bugs. Read them with thirdshift bug-origins [issue] --json, then settle one with --confirm, --correct <pull request> or --none. A confirmed origin counts against its retained Ticket run in show --json and proposes a code-review Eval task holding the historical PR diff and a draft catch criterion. Rejected and unsettled origins count for nothing; proposed Eval tasks need explicit approval before Experiments can use them. The same quota stop during Bug-origin analysis stops Scoring without advancing its window.

Scoring samples, Bug-origin proposals and settlements, and Run metrics share retained pull-request attribution. Matching ignores ASCII letter case and trailing slashes. Latest means chronological RFC 3339 time, including UTC offsets, then greatest lexical record path and Command name for ties; invalid times sort before valid ones. Saved local record-path/name pairs select that exact Command under the matching pull request. Missing or mismatched local identities count for nothing; only absent or cross-host attribution selects the latest local Command, so Continuations never multiply a count.

The first run also draws 20 historical pull requests for your Scores, spread across Harnesses and Models. Later runs mark two per week. Provider capacity and overload errors void a Trial with rate_limit and pause the Experiment. Start the same Experiment again to retry under its saved Bar.

A suite with fewer than 20 discriminating Eval tasks is an Advisory suite: it keeps its Verdict and intervals, but cannot pass or block a release. The Bar saves this minimum before the first Trial; --min-discriminating-tasks sets it for one Experiment, and changing it refuses resume. Only suites that are not advisory decide the overall Verdict, Void dropout guard and required rechecks. When every suite is advisory, the Verdict is inconclusive. CLI text, JSON and the Console mark Advisory suites; the Console also shows judged and measurement counts. The release summary lists each Advisory suite and its Verdict, and asks whether to release when the overall Verdict is fail or inconclusive, including when all suites are advisory. Saved Experiments without the minimum keep their original Bar and Verdict.

Experiment JSON identifies its documented result contract with format: 4. The Experiment results format covers retained Trial files, Scores, recheck history, suite Verdicts and the Bar.

Review commits, local-origin pushes and repository reports do not void a Trial. Changing its issue text, declared inputs or commits under review does. Mechanical checks grade a private copy of the prepared repository captured before the session.

The Console's Experiments list groups Running, Needs you and Done, newest first. Open one to watch Trials fill in, then see the Verdict by suite. The page compares Arms, folds the Bar and opens a Trial or Eval task in the Peek with Grader reasons and links to Session logs or Session traces. Details stays beside the Trials grid as you scroll on desktop and opens at the bottom on phones. Rechecks stay in the CLI, with copyable commands and a filter for their Eval tasks.

The Bar has a pass level and a fail level, 70% and 95% by default. Set them with --pass-level and --fail-level before the first Trial. Each metric fails if its interval at the fail level is wholly below zero; otherwise it passes if its interval at the pass level sits above the margin, and is otherwise inconclusive. A pass whose pass-level interval lies wholly below zero is marked worse, within the margin, without changing the decision. The Verdict shows both intervals, and the forecast uses the same decision. Saved Experiments retain their original Bar and Verdict, including the older rule that a pass also reach zero. At the 70% default, a simulated A/A Experiment passes about 67% of the time on today's 10 code-review Eval tasks and 56% on 30 Spec-review tasks; reaching 80% needs about 20 and about 80 tasks.

Proposed Eval tasks appear on the Experiments list and, for its suites, on each Experiment page. Approve one there or with thirdshift evals approve <suite> <task> --json to change its state in its suite, preserving its inputs. Approval starts no work and affects future Experiments; existing Experiments keep their fixed Eval tasks on resume. Unapproved proposals never run.

Each Trial and each Grader runs in its own memory-capped scope and raises its OOM score to give way before the factory. The User config defaults to 1 GiB for throttling, 2 GiB for killing and 1 GiB of swap per scope. Enable lingering once with loginctl enable-linger <user>; an Experiment stops before dispatch if it cannot reach the systemd user manager.

A Verdict stays waiting on rechecks until you have checked every borderline Score and every decisive Score, whose flip would change the Verdict. The pending list gives Trial IDs for thirdshift recheck <id> <trial> pass|fail --reason '…'. The JSON view names each decisive flip and the provisional Verdict it gives. thirdshift recheck <id> --pending lists all pending Scores and a fingerprint; thirdshift recheck <id> --batch <fingerprint> pass|fail --reason '…' records one decision and reason for that reviewed list in one locked save, refusing a changed list. Your latest decision feeds the calculation; the Grader's Score and your timestamped history remain. Each recheck updates the pending list and the latest invocation's Command outcome and Inbox group. A confirmed pass moves from Needs you to Done.
