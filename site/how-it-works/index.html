An engineer's guide · from issue to pull request

How thirdshift works

You describe the work. thirdshift runs an unattended coding agent in its own Git checkout, asks it to implement and review the change, then checks the pull request against the repository's latest state. By default, you review before merging. A Ticket run Self-merges when asked.

Start with one issue below, then follow the same process into larger Specs and scheduled work. This guide describes the source on main; an installed release may differ.

01 / The human handoff

Start with work you can describe

The Day shift is you: settle what should change, what success looks like, and what is out of scope. Put that in a GitHub issue. One session's worth of work can stand alone; a larger Spec is an issue with Tickets as GitHub sub-issues. We'll follow a standalone issue first.

For issues labelled bug, a fresh Ticket run or Continuation uses /thirdshift-diagnosing-bugs before changing code. A fresh run, or a Continuation with nothing on the Issue branch beyond the Base branch, reproduces on that checkout. A Continuation whose Issue branch is ahead of the Base branch reproduces at their merge base, then checks the fix on the branch: a bug there, with the fix already on the branch, goes on to review and the pull request. Otherwise it captures a failing regression test, then fixes it. If the bug cannot be reproduced at that checkout, it comments with triage notes, replaces ready-for-agent with needs-info and ends successfully with the comment link, without opening or merging a pull request. Flaky-test Tickets use the recorded CI failure as evidence and go straight to implementation. Security fixes and Base fixes keep their own flow.

From a clone of the issue's repository, normally checked out on your intended Base branch, start a Ticket run. In this example, main is the Base branch and the pull request will target it:

A fine-grained GitHub token needs Contents, Issues and Pull requests read and write, plus Actions and Commit statuses read. When check runs return HTTP 403, CI watch and Score packets use the latest GitHub Actions jobs and commit statuses; checks from non-Actions apps are unavailable through that fallback. Prerequisites.

cd ~/repos/widgets
thirdshift --no-merge https://github.com/acme/widgets/issues/7

In that clone, thirdshift 7 also starts the issue's Ticket run: a bare issue number is resolved from origin. Add --no-merge to leave it for review regardless of your defaults. Command forms.

--no-merge explicitly leaves the pull request for review, even if your User config normally requests merging. Before starting, install and authenticate GitHub CLI (gh) and your chosen Harness (the agent CLI, such as Claude Code or Codex), configure Git's commit identity and push access, and install the repository's test toolchain. thirdshift setup chooses machine defaults and offers to save a Claude setup token, made with claude setup-token, with hidden input. That token is reserved for Trials; ordinary Runs use the Harness's existing login.

02 / Where the work happens

Give the Ticket run its own checkout

thirdshift checks that the Issue URL matches the clone's origin, that the issue is open, and that the Base branch, Harness and Git identity are usable. It selects an Issue branch, marks the issue in-progress (its Claim, on only while the run is live), then acquires a sibling Git Worktree. A fresh Issue branch starts from the fetched Base branch on origin.

The work happens in the Worktree rather than switching your Launch directory to the Issue branch. If an existing Issue branch has no pull request or an open one, thirdshift continues it instead of starting over. An open pull request supplies its Base branch. Once a branch's pull request is closed or merged, later work uses a new numbered Issue branch.

A checkout is not a sandbox. Except Trials and Graders, which run in bwrap sandboxes with their own networks, sessions run unattended as your user. The Harness has access to that account's files, credentials and tools; the separate Worktree keeps edits apart, but does not confine the process. Read the permissions and cleanup details.

When a Harness session ends or is stopped, thirdshift stops its process tree and sweeps for detached survivors. Linux uses a separate systemd user scope where available. Linux without a user manager uses a per-session environment marker; clearing that marker can escape this best-effort cleanup. Other files the session created stay. What sessions leave behind.

03 / What the agent does

Let the agent implement and review

thirdshift starts a headless session in the selected Harness, in the Worktree. The Session prompt supplies the issue, Base branch, Issue branch and review instructions. Factory skills are linked where that Harness discovers them. The opening session carries the change from implementation through review to a committed branch and pull request.

The pull request's Evidence separates actual failing-before and passing-after execution output from visual captures. For visual changes with a headless browser available, implementation or diagnosis captures matching Before and After screenshots or recordings; the PR skill embeds them from a secret Gist. Responsive layout changes include desktop and mobile captures.

On Claude and Grok, a Session's completion line survives later background-task notifications. A later reply carrying a completion line takes precedence.

Command records and Session traces retain each run's Process name, whether it is Built-in or Custom, and its file's SHA-256 hash. Each child Ticket run records its selected Process separately from its parent, defaulting to ticket-run. A run awaiting a Built-in file keeps its run-type name without a hash. Status, the Console, the Activity log and Run notifications keep their existing names.

A session Step in a Custom process gets the same single Resume as a Ticket run when background work was killed as its turn ended. If the Resume ends the same way, a progress line names the work and the following Steps decide the outcome. A later Process failure names the killed work ahead of the failing Step. Resumes do not count against the Repair cap.

The Standards axis checks repository coding standards and code smells. The Spec axis checks the change against the issue. For findings that say behavior is wrong, the implementing agent must run the reviewer's reproducer before deciding: a demonstrated failure gets fixed with its test kept; a declined finding needs evidence that exercises it. Skipped findings go in the pull request's Unaddressed findings section, and decisions for the Day shift get a linked triage issue.

These are agent reviews, followed by deterministic Git and CI checks in Delivery. They do not guarantee correctness or replace your judgment. You can inspect the exact prompts and Factory skills, including the review procedure.

04 / From a published change to a checked result

Deliver against the latest Base branch

A running Command whose own GitHub call hits primary quota exhaustion waits until reset plus one minute and a random 0–60 seconds, then retries. If the quota has already reset, with at least 500 left, it records no wait and retries once, immediately. CI watch and Delivery share a two-hour total cap with child Ticket runs. A secondary limit gets up to five retries, 60 seconds apart. During a primary wait, status, show and the Console show Quota wait until <time>; Slow timing includes the wait. Stop interrupts ordinary waits; Claim ending and other completion work still finish within the cap. The Run notification totals primary waits in one Waited <duration> for the GitHub quota (<resource>) line. Waiting itself adds no agent-failed; agent sessions' own gh calls are unchanged.

A pull request existing is not the finish line. Delivery runs the opening session, then keeps the captured pull request mergeable and checks CI. This orchestration is thirdshift's code; a Repair is another agent session started when the branch needs work.

For an existing open pull request, thirdshift fix <PR URL or number> starts a Fix run directly at Delivery. Ready and draft PRs by Trusted accounts are accepted, with or without closing issues. It uses the PR's own Base branch, reserves the PR while running and gives each Repair trusted PR and linked-issue context. The usual merge, Base fix, Harness and email defaults apply; failure preserves work and offers thirdshift fix again.

Self-merge requires recorded agent authorship or review of the adopted head. Without it, a Fix Pass, even with merge, or a targeted Fix run asked to merge only by merge.always, still repairs the PR and checks CI, then finishes successfully Ready for review (exit 0) and logs the hold. A later Pass skips that mergeable, green PR. An explicit thirdshift fix <PR> merge still fails with the hold and leaves the repaired PR ready for review.

With no PR target, thirdshift fix [base <branch>] [--author <login>] is a Pass. Without --author, it first checks the Base branch's origin tip: a failed first push attempt gets one failed-jobs re-run, then PR selection continues without waiting. Persistent or non-rerunnable failures get a CI-fix session on fix-<base>-<short-sha> and a repair PR targeting the Base branch, treating every red check as its own; that Fix run ends the Pass. Existing PRs from that branch prevent duplicates, failed drafts included. Merge and email policy apply, and Self-merge closes the Base branch's CI-red reports and Base fix issues.

Otherwise the Pass selects the lowest-numbered open, non-draft, same-repository PR targeting the selected Base branch with a Merge conflict or CI red on its current head. It skips untrusted authors, in-progress PRs and pending CI without a conflict, passing over busy reservations and head branches already checked out locally. Local occupancy reasons name the PR and occupying path on stderr and, when no candidate can be taken, in the Activity log. The check preserves occupied worktrees; an explicit PR target still fails and names the occupying path. At the Command limit or with no eligible PR left, it records a skip, exits successfully and sends no Run notification. Failed Fix runs leave drafts that later Passes skip.

A Fix Pass checks every linked closing issue before and after reserving the PR. An in-progress Claim on a Spec or standalone Ticket run's issue, including on another host, makes it skip the PR and name the claimed issue on stderr. It can adopt the PR on a later Pass after the Claim ends. Unreadable links or labels fail closed; explicit PR targets keep their existing behavior.

A Fix run's Self-merge needs recorded agent authorship or review covering the exact adopted head, written by the GitHub account thirdshift acts as. Completed Ticket, Spec and Base CI Deliveries record their delivered heads for later Fix runs. Without that evidence the repaired PR stays ready for review; run thirdshift review <PR URL> before retrying Self-merge.

Pending or re-running Base branch checks, an occupied CI reservation, or an existing repair branch or PR skip only Base branch maintenance and leave PR selection available. Stderr and the Activity log record the reason, including when no eligible PR is found. Failed opening Base CI sessions publish preserved work as draft repair PRs with a Fix Recovery command; an existing repair branch also prevents another attempt if PR creation failed.

A Base branch CI-fix session that commits nothing ends successfully without pushing a repair branch or opening a PR. Stderr and the Activity log name the Base branch and commit where it found nothing to change. A local Git ref in the Launch repository remembers that attempt; later Passes there skip that CI-fix and continue PR selection. It requests no further Check re-run.

Fix CI sessions keep command and test logs in the worktree's Git-excluded .validation-logs/ directory, which cleanup discards. They reproduce with a failing test file or filter before a full suite, without full-suite debug output or sleep-and-tail polling loops. Review sessions check whether the PR is open at most once, immediately before a multi-minute validation suite; thirdshift also checks its state around the session and before Delivery.

Repair and upstream-move budgets keep the loop bounded. If a CI-fix Repair leaves the same failing head, that head gets one Check re-run; if its own checks stay red, the Ticket run fails rather than spending more Repairs on unchanged code.

An Inherited failure is a check that also failed under the same name on the Base branch commit last merged in. thirdshift does not ask a Repair to fix that on this Issue branch. It fails the Ticket run, or, when allowed, starts a separate Base fix and waits before trying again. Before it creates that Base fix, it confirms this pull request is still open. A closed or merged pull request, or one that cannot be read, fails the Ticket run and writes no Base fix issue.

An optional Security review runs after the opening session, including each Ticket, after the Spec review for a Spec PR, and after a Review run addresses its Standards and Spec findings. On a Review run, security-review or [security] review = true asks for it, no-security-review overrides the setting, and --recommend-only skips it. Its fixes are pushed with the others and unfixed introduced Security findings appear in the comment. It uses the User config's security.harness when set, and the Command's Harness otherwise. Preflight checks its Harness; an unavailable review Harness falls back to the default Harness. A Harness error before the first turn can also trigger that fallback once. The review fixes reproduced vulnerabilities introduced by this change; an introduced finding left unfixed holds Self-merge. Security review details.

Start work labels repositories by Fleet machine. Choose that machine's Cron jobs for Run now, or its User config and Update links for administration. Each control uses that machine's current run or admin scopes for the person signed in. The owning machine does the work and names the person and calling Console in its Activity log. The CLI's start <owner/repo> <issue>, config and update accept --machine <name>, acting as the token holder.

Choose Fleet schedules on Cron jobs, or thirdshift cronjobs --fleet [--json], for repository headings containing each machine's recognized Command kinds, original schedules and commands. On the page, each repository and Other for unknown entries starts folded closed on every load or reload. Expand or collapse headings independently by pointer or keyboard, with or without JavaScript; several groups can stay open during a visit. Machine statuses stay visible, including successful empty inventories, unavailable, refused, incompatible and link-only machines. Each owning machine resolves its repositories and authorizes reads. Scheduling remains with cron, in its original time zone; Last fired observations and Run now controls remain in the individual machine views.

Know what comes back

Use thirdshift console scopes --email <address> --scopes read from the serving machine's shell to narrow a Console account. An address absent from console.address_scopes has all five scopes. A token can name a person in X-Thirdshift-Person; the owning machine requires that address on its sign-in list and applies the intersection of their scopes. The page hides unauthorized controls, and refused API calls name the missing scope. No page or API route writes the sign-in list or address scopes.

The Console's read views are also available as JSON under /api/v1, authenticated by scoped bearer tokens or the page's sign-in session. Failed tokens and passwords share a per-address slowdown and cool-down; a refusal includes a retry time. Console API.

Pair machines from the shell with thirdshift console fleet add <name> <address>, giving the token through standard input. Pairing verifies the other machine before saving its identity and scopes; tokens stay in owner-only Credentials. console fleet list --json shows saved version and last contact, and console fleet remove <name> removes both entry and token. To let a machine report outward, create a report token for its Fleet name on the watching Console (console token create <machine> --scopes report) and save it on that machine with thirdshift console report add <name> <address>. That token uploads only its holder's own Run metrics summary; every other endpoint refuses it. Reporting outward.

thirdshift status combines the local Inbox with each live Fleet entry's Inbox, preserving the owning machine's groups and account tags. Rows name their machine, and active runs show a Fleet total and per-machine counts. status --machine <name> selects another machine; the local hostname behaves like plain status. Each remote read has a three-second timeout, with failures reported beside the other machines' results.

Stop, Dismiss and Undo on a remote row go to its owning machine, using the signed-in person's effective scopes there. Stop asks for confirmation; the owning machine's answer or refusal is shown. Other-account Commands remain read-only. The shell equivalents are stop <command> --machine <name> and dismiss <command> --machine <name> [--undo], attributed to the token's holder. Processes, Dismissals and Activity log entries stay on the owning machine.

The Console merges every Fleet machine into those Inbox groups, with machine tags, answer ages, a Fleet active-run total and per-machine counts. A page subscription starts independent reads every 15 seconds; with no page open there are none. Remote answers and errors stay in memory. After 60 seconds without a good answer, the machine is unreachable and its last rows turn grey. Refused tokens and older Consoles show their own status and a link. The Machine filter stays in ?machine=<name>; without it, every machine shows. Needs you counts and browser notifications cover the Fleet, including on phones. Remote Command details open in place with child Ticket runs, stages, Waterfall, Command logs and Session traces, fetched live and never saved on the caller. A Security run needs security on that machine; a refusal names the missing scope and machine. Remote rows and views also link to their owning Console. Use show or logs with --machine <name> for the owning machine's JSON.

On the Console's Inbox, Start work lets a person with run choose a known repository, issue number or URL and shared options. Review the request and its Harness before confirming Start now. Run now on Cron jobs confirms each recognizable Pass with its CLI arguments and reports a Command or skip reason. Both controls require JavaScript and are hidden without run.

thirdshift config [key [value]] [--json] reads or changes the User config with the same validation and comment preservation as Setup. The Console's User config page shows values and defaults: editable with admin, read-only with read. Saving returns to that setting and confirms the key, saved value and machine, including Fleet machines, with or without JavaScript. Export endpoints stay redacted. Its API twins at /api/v1/config require admin; changes record the caller, key and old and new values in the Console log. With admin, Update thirdshift shows current and latest versions and installs the release before the Console restarts; the API also imports Theme JSON and private Eval replay data. The sign-in list and address scopes stay under shell control. Machine administration.

Ready for review

The usual successful result: an open pull request into the Base branch, ready, mergeable and passing CI (or with no checks). You review the diff, tests and Unaddressed findings before merging.

Merged, when requested

A thirdshift merge <Issue URL> command requests a Ticket run that Self-merges. thirdshift itself merges the exact head whose CI it watched. Foreign commits on the Issue branch are reconciled and their resulting changes reviewed first. Required human reviews can still block it, leaving the pull request ready for review.

Failed ticket run, with work preserved

Unfinished work is committed and pushed; an open pull request normally becomes a draft. If pushing fails, the Worktree and local Issue branch are kept. Rerun the same Issue URL to continue. A stopped or failed run may need Day shift attention before scheduled Pickup takes it again.

Ordinary cleanup removes the factory-owned Worktree and local Issue branch after work reaches origin; the remote work remains available for review or continuation. Cleanup retains resources when ownership or preservation is uncertain. A successful Self-merge also deletes the remote Issue branch and closes the issue. A merge refused by repository policy can fail the Ticket run while leaving the pull request ready.

If a Harness reports exhausted usage, the saved or emailed Run notification highlights it near the failure cause. For a Spec run it names the affected Tickets, while keeping each Ticket's error and any provider-reported reset time in the details. Retry the Recovery command when usage is available.

Once Baseline Trial k and Candidate Trial k both finish, base-tests and cross-tests run each Arm's new test files offline on the unchanged base and against the other Arm's final commit, when the Eval task's process_grading.new_tests says how. They are evidence, never Scores: a cross-test failure is a disagreement to look into. Experiment JSON keeps them under pairs.

A Grader panel, when the Bar names seats with --panel-seat, then reads each pair blind in both presentation orders: the Ticket, both diffs, the Pair evidence and a rubric. Each seat rates each side, calls it ready to merge or not and gives a preference, with a call that flips with the order counted as a tie. One vote per family by default, or per Model; a seat from an Arm's family doesn't vote while another family sits. Experiment JSON keeps every seat's calls and the panel's result under panel, beside the Verdict unless the Bar counts them. The estimate before the Trials lists each seat's expected cost, priced from the frozen table; panel spend is reported apart from the Arms and never counts toward an Arm's cost or the cost ceiling. --panel-spending-limit pauses grading once a run's panel sessions reach it, and a resume continues from the calls already made. Before estimating or starting paid work, resume decodes every expected saved panel call; an unreadable or malformed call names its pair, seat and order and stops even behind an earlier missing order or with --yes.

Each such pair can be read blind on its own Console page or with thirdshift experiments <id> --pair <pair-id>. The page shows the Ticket, its numbered acceptance checklist and both changes side by side, code before tests, with their evidence, on sides drawn for the pair from the Bar's seed and with no Arm, Harness, Model or model call. The reader seals a merge call per side, then gives a preference (A, B, tie or both bad) and optionally the rubric. Records are append-only and attributed. Only after the preference does the page show which Arm made each side and the Grader panel's calls. People's calls, people–people and people–panel agreement show beside the Verdict.

The Bar fixes who decides before the first Trial: the panel and the people are each off, beside or counted (--panel, --people). Named readers get queues drawn by pair from the Bar's seed, with a set overlap; a shared pair is ready only if every reader says so. When counted, a Trial passes only if its code Grader passes and its pair is called ready. People counted on a sample decide on the sampled pairs alone. With both counted the panel stands in on unread pairs: a voting panel spanning too few families is refused at start, and people–panel agreement below the Bar's level makes the Verdict inconclusive. The Verdict waits on people while a reader has pairs to call.

Ordinary Runs keep running at warnings. thirdshift experiments [id] --json lists or shows saved results. --name names an Experiment, and thirdshift experiments <id> --name renames it in any state without touching the Bar; an unnamed one reads “A/A at <ref>”, “Release <ref>” or what changed between its Arms. Provider capacity and overload errors void a Trial with rate_limit and pause the Experiment. Start the same Experiment again to retry under its saved Bar.

A suite with fewer than 20 discriminating Eval tasks is an Advisory suite: it keeps its Verdict and intervals, but cannot pass or block a release. The Bar saves this minimum before the first Trial; --min-discriminating-tasks sets it for one Experiment, and changing it refuses resume. Only suites that are not advisory decide the overall Verdict, Void dropout guard and required rechecks. When every suite is advisory, the Verdict is inconclusive. CLI text, JSON and the Console mark Advisory suites; the Console also shows judged and measurement counts. The release summary lists each Advisory suite and its Verdict, and asks whether to release when the overall Verdict is fail or inconclusive, including when all suites are advisory. Saved Experiments without the minimum keep their original Bar and Verdict.

Dismissals keep the Trial and remain auditable; confirmation makes it Void. Decisions retain the reviewer, time and reason.

Optional --cost-ceiling and --time-ceiling fix Candidate/Baseline ratio limits in the Bar before Trials. Both default off; a paired median above either ceiling fails the Experiment. The Bar has a pass level and a fail level, 70% and 95% by default. Set them with --pass-level and --fail-level before the first Trial. Each metric fails if its interval at the fail level is wholly below zero; otherwise it passes if its interval at the pass level sits above the margin, and is otherwise inconclusive. A pass whose pass-level interval lies wholly below zero is marked worse, within the margin, without changing the decision. The Verdict shows both intervals, and the forecast uses the same decision. Saved Experiments retain their original Bar and Verdict, including the older rule that a pass also reach zero. At the 70% default, a simulated A/A Experiment passes about 67% of the time on today's 10 code-review Eval tasks and 56% on 30 Spec-review tasks; reaching 80% needs about 20 and about 80 tasks.

Proposed Eval tasks appear on the Experiments list and, for its suites, on each Experiment page. Each Trial and each Grader runs in its own memory-capped scope and raises its OOM score to give way before the factory. The User config defaults to 1 GiB for throttling, 2 GiB for killing and 1 GiB of swap per scope. thirdshift experiment --release <commit> compares touched suites with the last release tag. The release script skips Experiments by default. Add --with-experiment to scripts/release.sh on each invocation to run one: it waits for rechecks before pushing and asks whether to release on a fail or inconclusive Verdict. Reruns with the flag reuse the Experiment, including before opening a pushed branch’s PR. It selects the newest main commit descending from the last release tag whose latest push CI passed, tags that content plus the version bump, waits for publication, then merges the bump PR. A saved Candidate is selected again if a new release tag on main invalidates its ancestry; the requested version must still be higher than main. An untagged branch or open bump PR predating that tag is re-cut from a green main descendant, with a new summary and version diff, honoring --review before force-pushing the branch and updating the open PR body. Tagged or merged releases keep their resume behavior. After a failed unpublished release, rerunning re-cuts from newer green main content or automatically reruns failed jobs; published releases are never moved. If the publication check cannot be completed, the script refuses and moves nothing. Recovery retains the prior release boundary for the summary and Experiment.
