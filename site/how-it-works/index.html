An engineer's guide · from issue to pull request

How thirdshift works

You describe the work. thirdshift runs an unattended coding agent in its own Git checkout, asks it to implement and review the change, then checks the pull request against the repository's latest state. By default, you review before merging. A Merge run merges it when asked.

Start with one issue below, then follow the same process into larger Specs and scheduled work. This guide describes the source on main; an installed release may differ.

01 / The human handoff

Start with work you can describe

The Day shift is you: settle what should change, what success looks like, and what is out of scope. Put that in a GitHub issue. One session's worth of work can stand alone; a larger Spec is an issue with Tickets as GitHub sub-issues. We'll follow a standalone issue first.

From a clone of the issue's repository, normally checked out on your intended Base branch, start a Run. In this example, main is the Base branch and the pull request will target it:

cd ~/repos/widgets
thirdshift --no-merge https://github.com/acme/widgets/issues/7

In that clone, thirdshift 7 also starts the issue's Run: a bare issue number is resolved from origin. Add --no-merge to leave it for review regardless of your defaults. Command forms.

--no-merge explicitly leaves the pull request for review, even if your User config normally requests merging. Before starting, install and authenticate GitHub CLI (gh) and your chosen Harness (the agent CLI, such as Claude Code or Codex), configure Git's commit identity and push access, and install the repository's test toolchain. thirdshift setup chooses machine defaults and offers to save a Claude setup token, made with claude setup-token, with hidden input. That token is reserved for Trials; ordinary Runs use the Harness's existing login.

02 / Where the work happens

Give the Run its own checkout

thirdshift checks that the Issue URL matches the clone's origin, that the issue is open, and that the Base branch, Harness and Git identity are usable. It selects an Issue branch, marks the issue in-progress (its Claim), then acquires a sibling Git Worktree. A fresh Issue branch starts from the fetched Base branch on origin.

The work happens in the Worktree rather than switching your Launch directory to the Issue branch. If an existing Issue branch has no pull request or an open one, thirdshift continues it instead of starting over. An open pull request supplies its Base branch. Once a branch's pull request is closed or merged, later work uses a new numbered Issue branch.

A checkout is not a sandbox. Sessions run unattended as your user. The Harness has access to that account's files, credentials and tools; the separate Worktree keeps edits apart, but does not confine the process. Read the permissions and cleanup details.

03 / What the agent does

Let the agent implement and review

thirdshift starts a headless session in the selected Harness, in the Worktree. The Session prompt supplies the issue, Base branch, Issue branch and review instructions. Factory skills are linked where that Harness discovers them. The opening session carries the change from implementation through review to a committed branch and pull request.

The Standards axis checks repository coding standards and code smells. The Spec axis checks the change against the issue. For findings that say behavior is wrong, the implementing agent must run the reviewer's reproducer before deciding: a demonstrated failure gets fixed with its test kept; a declined finding needs evidence that exercises it. Skipped findings go in the pull request's Unaddressed findings section, and decisions for the Day shift get a linked triage issue.

These are agent reviews, followed by deterministic Git and CI checks in Delivery. They do not guarantee correctness or replace your judgment. You can inspect the exact prompts and Factory skills, including the review procedure.

04 / From a published change to a checked result

Deliver against the latest Base branch

A pull request existing is not the finish line. Delivery runs the opening session, then keeps the captured pull request mergeable and checks CI. This orchestration is thirdshift's code; a Repair is another agent session started when the branch needs work.

Repair and upstream-move budgets keep the loop bounded. If a CI-fix Repair leaves the same failing head, that head gets one Check re-run; if its own checks stay red, the Run fails rather than spending more Repairs on unchanged code.

An Inherited failure is a check that also failed under the same name on the Base branch commit last merged in. thirdshift does not ask a Repair to fix that on this Issue branch. It fails the Run, or, when allowed, starts a separate Base fix and waits before trying again.

An optional Security review runs after the opening session, including each Ticket, and after the Spec review for a Spec PR. It uses the User config's security.harness when set, and the Command's Harness otherwise. Preflight checks its Harness; an unavailable review Harness falls back to the default Harness. A Harness error before the first turn can also trigger that fallback once. The review fixes reproduced vulnerabilities introduced by this change; an introduced finding left unfixed holds Self-merge. Security review details.

05 / The result and your next move

Know what comes back

Ready for review

The usual successful result: an open pull request into the Base branch, ready, mergeable and passing CI (or with no checks). You review the diff, tests and Unaddressed findings before merging.

Merged, when requested

A thirdshift merge <Issue URL> command requests a Merge run. thirdshift itself merges the exact head whose CI it watched. Foreign commits on the Issue branch are reconciled and their resulting changes reviewed first. Required human reviews can still block it, leaving the pull request ready for review.

Failed, with work preserved

Unfinished work is committed and pushed; an open pull request normally becomes a draft. If pushing fails, the Worktree and local Issue branch are kept. Rerun the same Issue URL to continue. A stopped or failed run may need Day shift attention before scheduled Pickup takes it again.

Ordinary cleanup removes the factory-owned Worktree and local Issue branch after work reaches origin; the remote work remains available for review or continuation. Cleanup retains resources when ownership or preservation is uncertain. A successful Self-merge also deletes the remote Issue branch and closes the issue. A merge refused by repository policy can fail the Run while leaving the pull request ready.

You can watch progress without interrupting the agent:

thirdshift status
thirdshift show https://github.com/acme/widgets/issues/7
thirdshift logs https://github.com/acme/widgets/issues/7 --follow

The Console shows this machine's Commands, opening on its Inbox. Beside the CLI, you can watch their stages and logs there. For this machine on localhost, start it with:

thirdshift console --no-sign-in

For a server, thirdshift console install prints an installation script to read and run with sudo, putting its Console behind a sign-in. Console installation and machine status.

A signed-in Console account can Stop a live Command or Requeue it for Pickup. The CLI does the same:

thirdshift stop <command>
thirdshift stop <command> --requeue

Stop waits for cleanup and leaves the issue for the Day shift, labelled needs-triage. With --requeue, it releases the Claim and puts ready-for-agent back so Pickup can continue the work. Stopping a Command.

The Command log records the whole command; a Session trace records each agent session, and the Activity log records starts and outcomes per repository. Export a Command's whole Trace for another tool with thirdshift logs <command> --export <dir>. Optional email notifications report how the Run ended. Inspecting logs and exporting Traces.

06 / The same primitive, composed

Scale one Run into a Spec run

When the Issue URL has Tickets as GitHub sub-issues, thirdshift starts a Spec run. GitHub's “blocked by” links determine when a Ticket can start. Independent Tickets can run in parallel, each in its own Worktree; a blocked Ticket waits for its prerequisites to land.

Each Ticket is a Merge run into the Spec branch, not directly into main. The Spec PR gathers the result into the Base branch. A Ticket closing means its work landed on the Spec branch; the whole Spec has not shipped yet.

A failed Ticket stops only its dependents; other reachable Tickets can still run. Tickets marked for human work or triage also hold their dependents. An incomplete Spec leaves a draft Spec PR with a Tickets checklist. Rerunning continues existing branches. Spec run controls and limits.

07 / Where the next issue comes from

Choose how the next work starts

A direct Issue URL starts work you have already chosen. Other commands find work, then dispatch the same Run or Spec run you just followed. Each invocation makes one pass; your operating system's scheduler starts the next one.

Pickup respects issue readiness, open blockers and the Claim limit. Architect and Security runs yield to ready human-shaped work. Gates can skip a pass without failure, and unresolved plans, ideas or findings can leave the next decision with the Day shift. This is scheduled CLI work on your machine, using your authenticated tools.

Before dispatch, Pickup reserves its selected issue on origin and checks that it is still Ready. Competing Pickup runs on two machines cannot take the same issue: only the reservation's owner can dispatch it. After a crash, the reservation waits for the Day shift to confirm its owner has stopped and release it. Pickup's reservation and readiness checks.

For offline Eval data, thirdshift evals list lists private suites and proposed Eval tasks, evals touched selects suites by their declared dependencies, and evals prepare prepares approved Eval tasks with only base history. Spec-review repositories get a local bare origin. evals prepare-arms caches each Arm's build by commit and records its Harness's real path and version before Trials, keeping symlink updates from switching the Harness between Arms. On the host holding #429's private material, evals import-replays imports its manifests and grading files into the code-review and Spec-review suites. Rerunning adds missing Eval tasks and completes missing Code review Trial inputs, preserving local edits. These commands start no agent sessions. Eval task commands and format.

thirdshift experiment runs Code review and Spec review Trials. A Code review uses the production review skill on the historical diff, retaining both reports without fixing or publishing anything. The code-review suite runs three Trials per Arm per Eval task and reports pass^3, the share where all three passed; the Spec-review suite runs one. Experiments.

thirdshift experiment <candidate> builds the Baseline and Candidate Arms and runs their Trials with two workers, keeping the Bar fixed. Code Graders score mechanical checks, then fresh model Graders score written criteria from one blind packet per Eval task. Scores retain reasons, wrong findings and borderline marks; the paired Verdict shows each suite's interval with each Arm's minutes, tokens by Model, reported cost and Void causes. Trial and model Grader Session traces and code Grader spans join the Command's Trace. Void Trials retry fresh up to twice; an exhausted task drops out of both Arms, and more than a tenth dropped makes the Verdict inconclusive. Repeated Trial-only memory-cap stops appear as an Arm finding. A plan-limit warning pauses new Trials and makes any Trial cut short void; the same command resumes paused or interrupted work. Ordinary Runs keep running at warnings. thirdshift experiments [id] --json lists or shows saved results. A pass goes in Done; a fail or inconclusive Verdict goes in Needs you. Experiments accept Stop. Trials and Graders currently run without a sandbox until #1014. Experiment commands.
