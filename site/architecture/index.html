Architecture

thirdshift turns a GitHub issue into a pull request by running unattended agent sessions against it. The agents write and review the code. Everything else is thirdshift, one deterministic program: it decides what an agent works on, checks its work, and never lets an agent mark its own work ready. These figures show what runs where, who does each step, and where the boundaries are.

Drawn from the manual for the source on main; an installed release may differ. For the same process told step by step, read How thirdshift works.

Figure 1 · the whole system

Agents write the code; thirdshift decides when it counts

An agent session can do anything your user account can, with nobody there to approve it. So every decision that matters is made outside the session, by thirdshift, before the session starts and after it ends. The Day shift is you: you shape the issues and review the pull requests.

The deterministic orchestrator outside the agent loop is written in Rust (ADR-0001). Its statically linked binary embeds the Factory skills, so target machines need neither a language runtime nor a checkout of thirdshift, unlike an interpreted script.

Rust's data-carrying enums represent the unattended Ticket run, Claim and CI states. Exhaustive match means adding a state fails compilation until every match handles it. Pickup's reservation protocol across competing hosts is model-checked with stateright inside cargo test (ADR-0017). These checks matter when nobody is watching the control flow.

Console and host resources

Inbox Ticket progress comes from typed Ticket records: merged Tickets over all recorded Tickets, including those closed before the Spec run. It updates with existing record notifications, uses the owning machine's records for Fleet, and stays visible on a Pass that dispatched a Spec. Empty accounting has no counter; completing Tickets does not finish Spec review or Delivery.

Fleet starts and administration call the owning machine's API. Start choices and cron Passes come from its /api/v1/start-options, gated by run; User config and Update require admin. Controls use live whoami scopes for the signed-in person. Page forwarding names that person; the owner intersects their scopes with the token's, starts the Command and records the person and calling Console. CLI start, config and update --machine use the token holder. API endpoints stay local and cannot borrow another Console's Fleet credentials.

Cron jobs' explicit Fleet schedules page and cronjobs --fleet [--json] share request-owned aggregation of local and owning-machine inventories. Repository metadata and nullable Command kinds come from each owner; the client groups by repository and machine without resolving remote paths or converting cron time zones. On the page, native disclosures for each repository and Other start closed on every load, expand independently without JavaScript and save no expansion choices; machine statuses stay visible. Independent bounded reads preserve healthy results alongside unavailable, refused, incompatible and link-only states; link-only entries receive no requests. Page reads forward the signed-in person and require effective read access. /api/v1/cronjobs stays local and refuses Fleet selection, and Run now keeps its separate authorization.

Fleet metrics follow the same pattern: metrics --fleet, metrics --machine <name> and the Metrics page's Fleet view read each paired machine's local /api/v1/metrics in bounded parallel requests and merge outcome buckets, comparison tallies and Where runs failed, each Command counted on its owning machine. Each successful read atomically replaces that machine's summary under the watching account's logs/fleet-metrics/; an unreachable or retired machine shows its saved summary for the same view, badged cached with its last-seen time, while a refusal shows none. /api/v1/metrics stays local and refuses fleet and machine. A machine that cannot be reached inbound pushes its summary instead to POST /api/v1/metrics/report under a report token, the one scope a person never holds: the Console saves it only in the token holder's own reported slot beside the per-reader snapshots, refuses a report naming another machine, and shows it read-only with its pushed_at age. metrics --push and a bounded, best-effort push after each top-level Command send it, from destinations kept under console.report with their tokens in Credentials.

The Inbox polls live Fleet entries every 15 seconds only while a page subscription is open. Each request runs independently off the async executor with its own three-second timeout, so a bad machine never holds up a good one or a page request. Last good rows and the last error stay in memory only. Rows carry machine tags; each machine shows its answer age and active-run count. After 60 seconds without a good answer it is unreachable, with grey rows. Refused tokens and older Consoles have distinct diagnostics and links. ?machine=<name> filters the Inbox; its absence includes the Fleet in every group, the tab's Needs you count and browser notifications. Remote details use a request-owned client to fetch the owning machine's /api/v1 and render with the local Peek, Waterfall and log templates. Nothing is cached beyond the request or written to disk. The owning machine enforces security for Security run details and findings; the caller renders its refusal. Detail links retain the Fleet entry, and each row and view also links to the owning Console. The CLI's show and logs use the same remote reader with --machine <name>, returning the owner's JSON.

console fleet add pairs another machine through its /api/v1/whoami, with a token supplied on standard input. The named Fleet list and saved hostname, version, scopes and last contact live in User config; tokens live in owner-only Credentials, keyed by entry name. console fleet list --json reads that saved metadata; live means a token is stored, and an entry without one is link-only. console fleet remove deletes both. These commands have no API endpoints. The header links every entry. Legacy other_consoles addresses become link-only entries and are rewritten as fleet on a settings write. Fleet.

status uses one blocking fetch-and-merge path for the Fleet: each live entry's own /api/v1/status, a three-second timeout and no redirects. It preserves the owning Inbox's groups, GitHub facts and account tags. JSON version 2 adds each Command's machine and per-machine fetch times, reachability, errors and active runs. --machine <name> selects another machine; the local hostname keeps the whole Fleet. Failed reads contribute diagnostics without failing status. The API Inbox is the twin of status --local --json, so reciprocal pairings never recurse; the Console poller reuses the validated fetch path independently for each machine.

Fleet Inbox answers and live whoami scopes are kept per signed-in person. Remote Stop, Dismiss and Undo POST to the owning machine's /api/v1 with X-Thirdshift-Person; its token/person intersection decides access and its response reaches the caller. Stop retains confirmation. CLI stop and dismiss --machine omit the person and use the token holder's identity. Only the owning machine signals processes, stores Dismissals or writes Activity log entries. Other-account Commands remain read-only.

The run scope allows POST /api/v1/runs to start Ticket, Spec, Architect, Pickup, Security, Review, Fix, Custom process, skill, Scoring, Triage and Experiment runs. The CLI parser checks their structured options; Passes keep cron's skip gates, and triage receives Report text through stdin. The Console resolves the repository through known Launch directories from cron and User config's launch_directories, also listed by thirdshift launch-directories --json and GET /api/v1/launch-directories. It starts the current binary with CLI arguments in a new OS session and login environment, appending output to the cron command's output path, or <logs.dir>/cron.log when none is given. It returns the recorded Command name or an early skip after a bounded wait; a skill run has no Command record and returns its process ID after preflight. Starts survive Console restarts and name the requester in the Activity log; each attempt enters the Console log (ADR-0026). Experiment starts put the CLI options in an experiment object, including candidate, baseline and the suite list; OpenAPI lists every option.

The Inbox's Start work form and Cron jobs' Run now controls are clients of POST /api/v1/runs. A person with run reviews the structured request and Harness before confirming a start. Cron Pass arguments are preserved; shell expressions stay display-only. The page shows the Command name or skip reason, and the Inbox reads the new Command through its usual updates. Both controls require JavaScript and are hidden without run.

The CLI's thirdshift config [key [value]] [--json], the Console's User config page and /api/v1/config share one inventory, validator and comment-preserving writer. API reads and writes need admin; the page also offers a read-only view with read. After a page save, a redirect anchors the saved setting and a status message names its key, saved value and machine. This also works without JavaScript and preserves the Fleet machine; confirmation values come from the redacted inventory. Changes append the caller, key and old and new values to the Console log. Update uses the CLI's installer, answers after binary replacement, then drains connections and re-executes the Console. The page shows current and latest versions; updates, Theme imports and Eval replay imports require admin and record who asked. The sign-in list and address scopes remain shell-controlled; Credentials are separate and export endpoints are redacted. Machine administration.

Console accounts carry per-address scopes in console.address_scopes, all five when absent. Only the shell can set or show them with console scopes. Sessions use their address's scopes; the page hides unauthorized controls. A token's X-Thirdshift-Person header names a person on the owning machine's sign-in list, and the effective scopes are the token's intersected with that address's. Activity log entries for their Stops and Dismissals say by <person> from the Console on <holder>. No route writes the sign-in list or address scopes.

The Console's route table pairs each page with its CLI command, an /api/v1 path and a scope. Shared handlers render HTML or return the CLI's JSON. The same table generates /api/v1/openapi.json and thirdshift console openapi, with each served operation's scope, CLI twins and JSON shape; a parity test checks the description against registered routes. The read scope shows Security run rows and stages; details, findings and Security Session traces need security. The act scope permits Stop, Dismissal and Undo, eval judgments, Theme selection and hidden-section POSTs. Each attempted API change records its caller, endpoint and outcome in the Console log. Token Stops and Dismissals name by token <holder> in the Activity log. Other-account Commands stay read-only. The API accepts scoped bearer tokens, the page's sign-in session and --no-sign-in. Tokens contain 256 random bits; the machine retains only SHA-256 hashes in an owner-only file beside the Credentials. Issuing, listing and revoking them stays CLI-only. Authentication checks HTTPS forwarding or a direct connection to 127.0.0.1 before reading the token store, and route scopes gate requests. Failed tokens and passwords share an in-memory per-address slowdown and cool-down, returning 429 with a retry time. Only a proxy at 127.0.0.1 may supply the forwarded client address; restarting clears the limiter. console whoami and its API twin report machine and caller identity. Unauthenticated calls return 401 JSON; missing scopes return 403 naming the scope. Console API.

The Console reads its Fleet's Commands and opens on its Inbox. Filesystem changes wake its Inbox and log readers; process exits and elapsed-time boundaries have their own wakeups. A slow recovery check catches missed notifications and expired sessions. A signed-in account can Stop or Requeue a live Command. Its API starts work only when a person or token holder asks, using the same CLI behavior (ADR-0026).

The Inbox's batched pull request read also captures titles and the latest head commit's combined checks and status. Ready for review subjects link to the recorded PR and show its cached title, including Review runs without an issue. Missing titles keep the PR link with “(title unavailable)”; rows without a PR use their issue or Command subject. Title changes wake open pages without a network read during rendering. Ready for review rows show CI green, red, pending, no checks or unknown, using the same saved answer as status. CI changes wake open pages without changing the row's Ready state; failed reads keep the last answer with the existing freshness warning.

The same query captures pull request mergeability independently of head CI. A conflicting pull request stays Ready for review with a separate Merge conflict pill beside CI, even when CI is green. Mergeability changes also wake open pages; unknown answers show no conflict pill. status --json includes github_mergeable, and show --json reads the locally kept GitHub facts and observation times without refreshing them over the network.

The Console reads ready rows' pull requests and Needs you rows' issues and pull requests in a batched GraphQL query in the background once a minute, with blocking gh calls off its async thread. It keeps one answer per machine beside the logs. A changed answer or warning wakes open Inbox pages through the file watcher; unchanged reads update freshness without rendering or waking pages. thirdshift status uses that answer and reads GitHub itself only when it is missing or five minutes old. Failed reads retain the last facts and failure; after five minutes without a good read, both readers warn with when GitHub last answered and why the latest read failed. Both share a quota gate: fewer than 500 GraphQL points or REST requests holds off all their reads until reset, with a warning, preserving the rest for the factory. These limits and timings are not User config settings. An ended Needs you row moves to Done, Resolved or History when its issue closes or its pull request merges; a Triage row also moves when needs-triage is removed. Architect and Security runs use their dispatched Spec run's or Ticket run's issue and pull request. GitHub settlement does not move live Silent or step-2 Slow rows. A Slow run stays in Working or Landing until its stage reaches both twice the top of its Usual range and at least five minutes past it; only then does it enter Needs you, count toward notifications and use the urgent favicon. Ready rows leave on a merged or closed pull request. Resolved counts from the settlement time, and only rows GitHub cannot speak for age out while still waiting. Reopening brings back rows still in Done or Resolved. Rows in History retain the last facts without further reads, including when another row shares their issue or pull request. Dismissals hold across GitHub changes, and Undo uses the latest kept facts. These reads never write to GitHub (ADR-0023).

Local and Fleet Commands share the compact Working-row presentation, including Overview: live Fix and Review runs show a clickable PR #number beside the repository and run type on desktop and phone, for explicit and Pass-selected targets. Base branch CI repairs retain an optional base_branch in the Command record before the session starts. The row shows that exact selection before a PR exists and keeps it alongside the PR link once recorded, without deriving it from the repair branch or requesting GitHub. Older records keep their existing fallback.

Compact Needs you Review and Triage headers, including Overview, link the recorded PR first, falling back to the recorded issue, on desktop and phone and across the Fleet. Existing-issue Triage retains its explicit or Pass-selected issue when its Command record starts, before investigation can fail. Fleet subject links validate the visible repository and number against the GitHub URL. Older records and Report-based Triage without a single target retain their repository and Command fallback; failure text never supplies a target.

Security fix dispatch stores advisory metadata in the dispatched Command record’s security_fix_findings list before launch checks. Command details links each advisory with its title and severity (or “ungraded”), and the parent Security run marks the advisories it dispatched a fix for using that same list. Failed and interrupted fixes retain their links. The list is also exposed by thirdshift show <command> --json. Older records need no migration and no advisory links are inferred from issue bodies.

Any signed-in account can use Dismiss on the row in Needs you or Ready for review, always visible beside Copy where available. With JavaScript, d dismisses the selected row and selects the next; text fields and open dialogs keep their keys. An inline dismissal shows a temporary notice with Undo for that Command, outside the live Inbox so row replacement cannot remove it. The notice stays while hovered, focused, saving or showing an error. Without JavaScript, rows keep their full Dismiss form. Command details also offers Dismiss and Undo for a dismissed row. Command details shows each CLI form: thirdshift dismiss <command> or thirdshift dismiss <command> --undo. Both use the Console's session and CSRF checks. The browser keeps pending feedback and disables duplicate submissions through live updates; failed requests show their error and allow a retry. The dismissal lives beside the Command record and changes only the row's group; filesystem notifications update open pages, and the Activity log names the account and the Console. A live Command keeps running, and nothing is written to GitHub.

A dismissal accumulates covered kinds for the whole row, across child Ticket runs, and status --json exposes them as dismissal.kinds. An uncovered kind brings the row back, including a Finding behind a dismissed Security failure only while GitHub still shows its findings waiting. Each read adds one paginated REST list per repository with a Security run whose findings were waiting, respecting the quota reserve and using the Security run’s private-storage selection. The kept answer holds only finding URLs and waiting flags, with the first observed triage time; it retains no finding title, severity or write-up. A Finding leaves saying “findings triaged” once its records no longer wait: a draft advisory without severity or an open security-finding issue labelled needs-triage waits, and a record closed by a merged fix does not.

status --json exposes each row's kept issue, pull request and finding facts with their observation times in github. History freezes those times alongside the facts. Unchanged reads update observation times without waking pages. A dismissed row's Resolved clock stays anchored to its dismissal even if GitHub settles it later.

Before each agent session, host resource limits delay its start while available memory is too low, one-minute CPU load is too high or free disk space is too low. The memory and load limits are optional; the disk limit waits below 5120 MB free by default. thirdshift resources and the Console's Resources page show the current snapshot and configured limits. The Console header uses that same admission policy below the notification control, refreshing every ten seconds while visible and linking to Resources. Disabled limits and unavailable measurements have explicit states. Existing sessions continue; the indicator reserves no capacity.

Processes and Session traces

Review markers are read only from comments by the GitHub account thirdshift acts as. Delivery compares the base's recorded fix commits with the upper pull request and warns when it needs updating before merge. It never merges or rebases the stack.

The Base branch may advance during a Review run, including with --recommend-only. The captured Base commit still sets the review and CI comparison scope. Retargeting the pull request, renaming its head branch or losing eligibility stops publication; a changed head prevents pushing fixes. Delivery checks mergeability before pushing and again before reporting ready. An observed conflict requires an author update and blocks further pushes and readiness.

Review acquisition publishes paired durable ownership evidence for head-branch worktrees. Retries verify checkout, administrative and common-directory identities, the token, the captured PR head, clean tracked state and descendant history under both worktree and refs locks before adoption. Author Pass admission uses the same checks, skips unrecoverable conflicts and persists notification fingerprints under ~/.thirdshift/review-conflicts/, allowing later PRs through without repeated failure emails.

When a Review run or pull-request Custom process captures its pull request, it persists the target URL in its Command record and names it in the Command log before starting a session. thirdshift status and the Console's Working row read that URL from the live Command record.

Addressing Review Delivery gates readiness on checks and commit statuses for the exact published full head, including unchanged branches and Security-review commits. One CI watch retains re-run allowances across the delivery; at most five CI-fix Repairs address branch-owned failures, with any lower Custom-process cap respected. Repairs validate their final commits before guarded publication and another watch. An unchanged Repair gets one eligible Check re-run without repeated sessions on the same red head. Inherited failures, unreadable observations and unresolved red CI end failed with evidence in the review result and Run notification. Pending CI cannot trigger readiness. PR identity, eligibility and expected head are reobserved throughout; author changes stop publication. A final conflict requires an author update. Review owns no stack reconciliation, replacement PR or Self-merge; --recommend-only remains report-only.

The Review run's session owns validation after addressing findings: repository agent instructions supply final validation and review.commands_by_repo in the User config adds per-repository shell commands. Delivery posts the session's results for each command, including failures and commands it could not run. Suites invalid in worktrees are not run against the branch, never passing; no extra list still means repository final validation. Recommendation-only sessions validate after reviewing too. If a later Step commits more changes, Delivery repeats validation on the final head before pushing and reports those results. When that report includes private Security review material, the comment says the results were withheld instead of quoting the session.

thirdshift review --author <login> selects one author's lowest-numbered eligible open pull request before the Review run. Its Pass gate holds one Command-limit slot. Selection skips heads a Review-run marker names as reviewed or pushed, in-progress pull requests, and bases that are open pull requests without a reviewed current head. It pages linked closing issues and checks each for an in-progress Claim or issue reservation in that issue's repository, before and after reserving the PR, ahead of worktree inspection. A hold logs the PR, issue and observed signal, then selection continues. Failed observations cannot admit a PR. Holds cover direct and reserved Ticket and Spec Delivery across machines; retained reservations require operator recovery. This read-only guard does not exclude Delivery started after selection, so captured-head checks remain necessary. Explicit PR URLs keep their existing behavior. An origin reservation serializes Review runs on each pull request; in-progress spans the run and is removed on ending. The Sweep clears the label from closed pull requests.

The review-run Built-in process starts on a pull request: review-and-address → security-review → delivery, on a pull-request worktree at its captured head branch. thirdshift review <PR URL> filters input to the body, linked closing issues and Trusted-account comments, reviews against the PR's own base and addresses findings with the Ticket run's shared rules. The Security review runs only with security-review or [security] review = true, after findings are addressed, on security.harness with the usual fallback. no-security-review overrides the setting and --recommend-only skips it. Delivery pushes its fixes with the others without force and posts one comment listing fixes and every Unaddressed finding, including unfixed introduced Security findings, with a hidden marker naming the reviewed head and the head after a push. A linked Spec departure explained only by the PR body stays unaddressed with that reason and no triage issue. If the branch moves before the push, Delivery posts the findings and proposed fixes, says the branch moved and leaves it alone. --recommend-only posts findings without changing the branch. Eligibility is checked before sessions and again before publication. The Command record, Activity log, notification and Inbox name the Review run. Copy its file with thirdshift process show review-run for a Custom process started with pull-request <PR URL>.

Every session Step gets one Resume for killed background work, in Custom processes as in Ticket runs. Killed background work after a Resume is named in progress while following Steps decide the outcome. If the Process fails later, its cause names that work first. A Resume does not spend the Process's Repair budget.

Every Harness session stops its process tree and sweeps for survivors when it ends, fails or is stopped. Linux sessions use their own systemd user scopes where a user manager is reachable, catching detached and reparented work. Linux without a user manager uses a unique THIRDSHIFT_SESSION environment marker and signals only the same OS user's matching processes. This fallback is best effort: clearing the environment escapes it. Cleanup reports survivors killed, warns on sweep failures and preserves the Command's outcome. What sessions leave behind.

Command records retain process_name, process_kind (built-in or custom) and process_hash (SHA-256 of the exact file bytes). Session traces carry the same facts as thirdshift.process.* attributes. A Custom process hashes the source loaded for execution; a Ticket run hashes the compiled-in ticket-run file by default. Dispatched runs and child Ticket runs keep their own Process identity within the shared Trace. Runs without a Process file retain their run-type name with no hash, and older records need no migration. Displayed run types stay unchanged.

Ticket runs, including those started by Spec, Architect and Security runs, default to the compiled processes/ticket-run.toml: implement → security-review → delivery → self-merge, inheriting the Command's Harness, Model and Effort, Child asks and Limits. A run-published-issue Step may select a different Ticket Process with process = "<name>"; process check requires that it exists and declares an Issue-branch worktree. Spec dispatch and Claim-before-worktree ordering stay in front of the file. The Command retains its Ticket run identity and Session-trace names. thirdshift process show ticket-run prints a copyable file; thirdshift process check ticket-run issue <issue> validates it.

Architect runs execute processes/architect-run.toml: architecture-review → run-published-issue. The Command limit, the lock of its kind and the open-plan, waiting-idea and Ready-or-settling-issue gates remain before the file. The first Step owns the session, conclusion and labels and ends successfully on an idea in the repository at origin, or with --plan-only. An idea outside that repository is refused before it is viewed or labelled. Otherwise the next Step runs the plan. The Architect run keeps its name, progress, logs, endings, Run notification, Console view and Recovery, and records the compiled file's hash. thirdshift process show architect-run prints the file and thirdshift process check architect-run validates it. A copy under a new Custom process name follows the Command limit without a lock of a kind.

A Custom process's spec-branch worktree shares the Spec run's land-tickets loop: push, dependency scheduling, Trusted-account checks, draft Spec PR and checklist, and Failed spec run accounting. Its process setting selects every Ticket's Process, defaulting to ticket-run. A file declares one Issue-branch or one Spec-branch worktree, never both; dispatch refuses the wrong issue shape before any session and makes the Claim before the worktree.

The following spec-review catalogue Step uses the Spec run's whole-Spec prompt and report contract on that worktree. security-review, delivery and self-merge share the existing Delivery and Failed-run path for its Spec PR, restoring the Tickets checklist before readiness and removing the Claim after Delivery. Security review and Self-merge keep the command and User config gates. A refused or incomplete Security review leaves the PR ready and holds the merge. Each Custom process Step resolves its own Harness, Model and Effort.

Spec runs execute the compiled-in spec-run file: land-tickets → spec-review → security-review → delivery → self-merge, on a spec-branch worktree. Every starter uses it: an Issue URL, Pickup, Architect and Security runs, and run-published-issue. Dispatch, the Claim, Child asks and Limits stay in front of the file. The run keeps its sessions, progress lines and Spec run name, and records the compiled file's hash. Inspect it with thirdshift process show spec-run or validate it with thirdshift process check spec-run issue <spec>; its name is reserved against Custom processes.

Security runs execute the compiled-in security-run file: security-audit → reproduce-findings → fix-findings → close-findings. The Command limit, the lock of its kind and Ready-issue, failed-fix and unchanged-Base skip gates stay before the file, followed by a check that the repository has Issues turned on: with Issues off, the run fails before any session and says to turn them on or remove its Security schedule. An earlier reproduced finding awaiting an allowed fix makes the first two Steps skip. The run fixes at most one finding and closes only that finding after its fix merges and its proof passes. Sessions, progress, logs, Run notifications and the Security run name stay the same, with the compiled file's hash recorded. Inspect it with thirdshift process show security-run or validate it with thirdshift process check security-run; its name is reserved against Custom processes. A copy under a new name follows the Command limit without a lock of a kind and can fix several findings.

Pickup has no Built-in process file. It selects and reserves a Ready issue, then dispatches ticket-run or spec-run.

Ticket runs and Custom processes share the security-review catalogue Step. A Custom process places it on the Issue branch after editing and before delivery, outside parallel groups. The command or User config decides whether it runs. Harness fallback, private pre-existing findings and holds on Self-merge follow the Ticket run's rules; a Harness explicitly named in the file must start at preflight.

The architecture-review catalogue Step owns a fresh Architecture review worktree at the Base branch, its conclusion, plan checks and plan-or-idea labels. A following run-published-issue starts the child run on a Strong plan. An idea in the repository at origin, or the command's --plan-only, ends the Process successfully, skips later Steps and records the reason in progress and the Ending. An idea outside that repository is refused before it is viewed or labelled. The Step runs outside parallel groups and takes no Architect skip gates; those remain in front of an Architect run.

A Custom process can run security-audit → reproduce-findings to audit the Base branch and reproduce each finding at its audited commit. Both required Steps use throwaway worktrees outside parallel groups, take their own Harness, Model and Effort, preserve private records and completed reproductions, and keep their traces out of OTLP export. With security-fix or the User config allowing fixes, both skip themselves when a recorded finding awaits a fix, unless the repository has issues turned off and so cannot hold one. The Security run executes security-run after its existing skip gates.

A Custom process can use fix-findings → close-findings to fix reproduced Security findings and close only merged fixes whose proof-of-concept passes against the merged Base branch. The Steps keep private records and the Security run’s fixing and closing permissions. fix-findings can select a child Ticket Process with process; it defaults to ticket-run. Failed fixes and failed rechecks stay with the Day shift. Their sessions and the Ticket runs they start stay off any configured OTLP endpoint, as a Security run's do. The Built-in Security run still fixes at most one finding per invocation.

A Session trace records each agent session. A Command's whole Trace includes its child Ticket runs and stages; export it with thirdshift logs <command> --export <dir>. Logs and Trace export.

Experiments and Scores

Custom process and home-skill content hashes enter Arm identity and cost-estimate history. Changing either starts a new Experiment; unchanged inputs resume their frozen Experiment. Process grading shares one Bar deadline across snapshot preparation and all test selectors.

A factory Command whose every allowed route has no Plan usage records a Paused Command too, and exits 75; a Spec run reads that exit code from a Ticket's child Run, the one fact of its pause no agent could write. The pause comes only from structured Harness wire frames and the machine's saved Plan usage, never from session text. Its Claim is released without agent-failed, and a record whose Claim put ready-for-agent back is marked retaken_by_pickup, so the Inbox puts it in Done rather than Needs you. Passes read the same saved Plan usage before any GitHub work and skip when every route is held.

An Experiment or Scoring run stopped by a plan limit records a Paused Command. Needs you and Command details name its stopping Harness, window, utilization and reset time when reported, with a resume command to copy. Starting the same work clears that pause from Needs you, keeping finished Trials and Scores. Pauses count as neither success nor failure.

thirdshift score also creates a Command: a Scoring run with a machine-wide lock, sampling merged factory work across configured GitHub owners. Samples, seeds and blind packets stay under ~/.thirdshift/evals/scoring/; thirdshift scores --json lists them by week. A packet holds historical issue text, the merged diff, pull request and CI conclusions, plus merge-time repository files without Git metadata. An independent Grader runs in the Experiment sandbox and checkpoints five criterion Scores per pull request, with its Harness and Model and a local Command-record link when available. A Claude or Codex quota window at 85%, or a Claude rejection, leaves unscored packets for the next Scoring run; a Claude warning with no readable utilization also stops grading. Its record and logs belong to thirdshift's own repository, and the Inbox and Stop read them through the same Command interface. Closed bugs also get proposed Bug origins through the shared Eval sandbox: fix and earlier history → introducing commit or none → GitHub pull requests → local Command record or Built-with line. The first proposal run backfills all closed bugs; Security fixes are excluded. thirdshift bug-origins [issue] --json reads the retained evidence and settlement; --confirm, --correct <pull request> and --none share Scoring’s writer lock. Confirmed origins contribute to their exact retained Ticket run’s show --json metrics and atomically publish proposed code-review Eval task folders. Each pins the PR head and its historical merge-base, keeps historical issue text (or the PR body when no issue was linked) and a draft catch criterion, and requires explicit Eval approval before running. A Fix Pass checks every linked closing issue before and after reserving the PR. An in-progress Claim on a Spec or standalone Ticket run's issue, including on another host, makes it skip the PR and name the claimed issue on stderr. It can adopt the PR on a later Pass after the Claim ends. Unreadable links or labels fail closed; explicit PR targets keep their existing behavior.

Pending or re-running Base branch checks, an occupied CI reservation, or an existing repair branch or PR skip only Base branch maintenance and leave PR selection available. Stderr and the Activity log record the reason, including when no eligible PR is found. Failed opening Base CI sessions publish preserved work as draft repair PRs with a Fix Recovery command. An existing repair branch prevents another attempt if PR creation failed.

When the adopted head has no recorded agent authorship or review, a Fix Pass, including one asked to merge, repairs the PR and finishes successfully Ready for review (exit 0), logging why Self-merge was held. A targeted Fix run asked to merge only by merge.always does the same. An explicit thirdshift fix <PR> merge still fails with the hold and leaves the repaired PR ready. A later Pass skips the mergeable, green PR, allowing a Review Pass to take it.

Before publication, Base branch maintenance compares the head before and after its CI-fix session. An unchanged head ends successfully with no repair branch push, PR or further Check re-run; stderr and the Activity log record that it found nothing to change on that Base branch at that commit. A local Git ref in the Launch repository records the Base branch and full commit while the CI reservation is held. Later Passes there skip that CI-fix and leave PR selection available.

The Inbox reads a later Command's pull request URL as well as its issue number to take up earlier rows waiting in Ready for review or Needs you. A Fix run therefore takes over an earlier waiting row even without a linked issue; the row records “taken up by a later Command started at <time>”. Ready for review rows with CI red or Merge conflict offer Start Fix run when the destination currently permits run and knows the repository's Launch directory. The existing confirmation submits the PR identity to /api/v1/runs locally or the Fleet forwarding route for its owning machine, using that machine's User config and CLI defaults. Other-account Commands stay read-only. Copy fix command, thirdshift fix <PR URL>, remains on the row and in Command details.

thirdshift triage

A Triage run: investigate a Report or an existing issue

Every input mode accepts base <branch>, including piped Reports and --file; it defaults to the checked-out Base branch. When the existing issue carries security-finding, its Run notification contains only the recorded title and link, even on failure. The private investigation, questionnaire and failure diagnostics remain in the issue or local output and logs.

Existing-issue triage prepares images on the host before launching the session: up to ten unique HTTPS images from the trusted body and comments on github.com or *.githubusercontent.com, each limited to 20 MiB and 30 seconds. Successful downloads live under .thirdshift-issue-images/ in the throwaway worktree and are listed by original URL and local path in .thirdshift-issue.md. The session inspects these local files, including with --read-machine; failed downloads warn and leave the issue text available.

thirdshift triage <Issue URL or number> [base <branch>] updates an existing open issue in place. It checks the repository, Trusted-account author and title/body edit history, then supplies only Trusted-account comments to the session. The Base branch defaults to the checked-out branch. Unless --recommend-only is set, an origin reservation spans its Claim, publication and cleanup. The Claim replaces prior triage state and agent-failed with in-progress; one AI-attributed comment and the resulting state complete it, preserving category labels and closing wontfix. Readiness without permission becomes ready-for-human. Failure uses ready-for-human and agent-failed; Stop uses ready-for-human, or needs-triage with --requeue, without a failure label. Recommendation-only mode validates without reserving or writing to GitHub. An issue cannot be combined with --file.

Report and existing-issue sessions receive the repository's available category labels, using the same factory-label exclusions as publication. A valid recommended category is required even when an existing category will be preserved; any other category gets the one correction turn. A Security finding keeps its security-finding label and gains the recommended repository category when it has none.

With no issue or --file, thirdshift triage [base <branch>] is a Pass when stdin is a terminal or empty at EOF, including cron. Command-limit admission precedes the Sweep and pickup.failure_limit. The search takes one open needs-triage issue in pickup.order, passing over contradictory triage states, Claims, failures, parent Specs with sub-issues and untrusted authors or edits. It reserves on origin and rechecks state and trust before in-place triage, continuing to the next candidate if reserved or stale. Skips exit zero without notification and deduplicate their Activity log reason, honouring activity.quiet_skips.

A Triage run, thirdshift triage, takes a Report from stdin or --file. A Report is work already given, so it always takes a Command slot, even at the Command limit, and is never skipped. The embedded thirdshift-triage skill investigates read-only in a unique throwaway worktree and searches the repository's open issues before proposing new issues. It returns category, state, proposed issues, existing-issue comments and investigation as JSON. thirdshift comments on an open issue already covering the Report, quoting the Report and source with new evidence, and keeps its labels. It files new issues with a disclaimer, collapsed verbatim Report and source, exactly one category and state, and cross-links between separate problems. thirdshift owns readiness: ready-for-agent becomes needs-triage unless --allow-ready-for-agent or the User config permits it. thirdshift setup asks whether Triage runs may file ready-for-agent issues by default; the initial answer is No, and rerunning Setup keeps the saved answer as the default. Confirmation needing credentials or production access becomes ready-for-human with a reason, and a wontfix issue is closed once filed. With --recommend-only, it publishes nothing and names any issue it would comment on, but still makes filing's checks against GitHub, so it fails wherever filing would. Its full JSON result goes to stdout. The Run notification summarizes the investigation, issue titles with category and state, and comment target URLs as readable text, omitting the full JSON and issue and comment bodies. Every filed or commented-on issue link reaches stdout and the Run notification. The session uses the ordinary trusted Harness with instructions to stay within its worktree, preserve code and write nothing to GitHub; it starts no implementation.

A Triage run's needs-info issue carries a questionnaire written with the embedded thirdshift-to-questionnaire skill for whoever has the answer. thirdshift includes it in the issue body and as readable text in the Run notification for the Day shift to forward. Other outcomes, including ready-for-human, get none; the issue body describes any needed decision or operator action. Empty or whitespace-only questionnaires count as absent before state validation. Publication stays in the repository; thirdshift never contacts the reporter outside it. With --recommend-only, the questionnaire stays in the proposal and notification.

The opt-in --read-machine, or the repository named in the User config's triage.read_machine, wraps that Harness invocation, including a Resume, in Bubblewrap. The host filesystem is mounted read-only and only the throwaway worktree is writable; the session can read outside it with the account's normal permissions. Unix-domain sockets are refused, so a host service cannot write for the session. TCP stays available. Sandbox startup failures fail the Triage run with their diagnostics, without an unsandboxed fallback. This requires bwrap and working Linux user namespaces. Without either, the ordinary launch and worktree-only prompt remain.

Containment: where the boundaries are

Ticket run, Spec run and Security sessions can do what your user account can. So containment comes from where you run it. The boundary that holds is the machine: best a virtual machine with nothing from production on it. Security sessions may run target code only inside an OS-enforced sandbox, as the Security audit skill requires. thirdshift ships a sandbox runner for Trials and Graders; Ticket run, Spec run and Security sessions run unsandboxed.

Your machine
holds · your setup Keep production data, keys and unrelated logins off it, and assume a session can read or change anything on it.
Your user account
enforced, but shared It separates thirdshift from other users, not from its own sessions: a session can read the gh and git logins and push with them (#691).
The Worktree
not a security boundary It keeps your checkout and other Ticket runs apart. Every Harness runs with its own sandbox and approvals off (ADR-0013). Claude Code's auto mode screens risky actions, but enforces no boundary.
Setup's sandbox probe
shipped · capability check With security.review or security.fix on, Setup checks this machine's bubblewrap sandbox: network isolation, a read-only host home and scratch writes with a dummy home directory. Before running target code, each Security session must enforce no external network; an empty environment populated from an explicit allowlist with safe values, with scratch-local HOME, temporary directories and caches; a read-only target and toolchain, with writes only inside scratch; and explicit low CPU, memory, process, file-size, disk and wall-clock limits. If it cannot enforce every control, Security runs and Security reviews on this machine report findings as needs-validation instead of reproducing them. The probe result does not stop Setup. Passing the probe is a capability check, not isolation for later sessions. Setup and User config.
An OS sandbox
required for Security target code · runner not shipped The Security audit skill requires an OS-enforced sandbox before running target code, with network, credential, write and resource isolation. If those controls cannot be enforced, the session must leave execution for validation. thirdshift ships no runner for Security target code yet (#726). Trials and model Graders run in bwrap sandboxes with provider-only networks; Code Graders run offline. Graders see their packets and, for Code Graders, a private grading repository; raw Trial logs and Arm mappings stay hidden. Ticket run, Spec run and Security sessions run unsandboxed; sandboxed Codex sessions remain open work (#398, ADR-0013).
Trusted accounts
issue input, not process isolation The repository's owner, organization members and collaborators. A session gets its issue's title, body and only these accounts' comments. Pickup takes only issues a Trusted account wrote and whose latest ready-for-agent label a Trusted account applied, with no later title or body edit by another account. Pickup's trust checks.
