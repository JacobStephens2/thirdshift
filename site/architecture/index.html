Architecture

thirdshift turns a GitHub issue into a pull request by running unattended agent sessions against it. The agents write and review the code. Everything else is thirdshift, one deterministic program: it decides what an agent works on, checks its work, and never lets an agent mark its own work ready. These figures show what runs where, who does each step, and where the boundaries are.

Drawn from the manual for the source on main; an installed release may differ. For the same process told step by step, read How thirdshift works.

Figure 1 · the whole system

Agents write the code; thirdshift decides when it counts

An agent session can do anything your user account can, with nobody there to approve it. So every decision that matters is made outside the session, by thirdshift, before the session starts and after it ends. The Day shift is you: you shape the issues and review the pull requests.

The Console reads this machine's Commands and opens on its Inbox. A signed-in account can Stop or Requeue a live Command. It does nothing the CLI can't do and starts no work (ADR-0016).

A Session trace records each agent session. A Command's whole Trace includes its child Runs and stages; export it with thirdshift logs <command> --export <dir>. Logs and Trace export.

For Evals, the hidden --trial flag runs one Spec review through the same session code in a prepared repository. Its versioned JSON result and separate output folder keep Trials out of the Inbox and the Usual ranges. Trial protocol.

  1. Pre-flight checks stop a Run before anything is created: the Issue URL must match the clone's origin, the issue must be open, and the Base branch must be on origin.
  2. The Claim labels the issue in-progress, so the issue list shows what the factory is working on.
  3. A Worktree gives the Run its own checkout beside your clone, so yours is never touched.
  4. Delivery pushes the branch and checks that the pull request exists and targets the Base branch. thirdshift, not the agent, marks it ready.
  5. Keeping it green merges the Base branch in and watches CI. A conflict or the branch's own red check starts a Repair, at most 5 a Run.
  6. The Self-merge, in a Merge run only, merges exactly the head commit whose CI thirdshift watched.
  7. Cleaning up removes the Worktree. A Failed run pushes its work first and turns the pull request back into a draft.

Figure 2 · thirdshift <Issue URL>

A Run: one issue in, one pull request out

Work reaches a Run as a Ready issue, labelled ready-for-agent. You write most of them, but thirdshift writes some too: an Architect run publishes its plan, a Security run allowed to fix files the fix, and a Base fix files the red CI on the Base branch. One agent session writes, tests and reviews the change, then opens the pull request. A second session reviews it for security, if you ask for that. Then thirdshift checks, pushes and watches.

Figure 3 · thirdshift merge <Issue URL>

A Merge run: the Run, then thirdshift merges it

The same Run, one step further. Once the pull request is open, ready, mergeable and green, thirdshift merges it with a merge commit, on exactly the head whose CI it watched. Commits someone else pushed to the branch are reviewed first. A required human review still stops it, leaving the pull request ready for you.

Figure 4 · thirdshift <Spec URL>

A Spec run: many Merge runs, one pull request

An issue with sub-issues is a Spec, and its sub-issues are Tickets. Each Ticket gets its own Merge run, not into main but into the Spec branch, in the order GitHub's “blocked by” links allow. Independent Tickets run at once, each in its own Worktree. The Spec ends as one pull request for you to review.

Figure 5 · thirdshift pickup, architect, secure

The Passes: the factory finds its own work

A Pass takes no Issue URL, so your operating system's scheduler can start it; thirdshift never schedules itself. Only one Pass runs on a repository at a time, and a Pass with nothing to do is skipped, not failed. Architect and Security runs wait while a Ready issue is open, so work you shaped goes first.

Figure 6 · from the outside in

Containment: where the boundaries are

thirdshift draws no security boundary around its agents: every session can do what your user account can. So containment comes from where you run it. The boundary that holds is the machine: best a virtual machine with nothing from production on it. Security sessions may run target code only inside an OS-enforced sandbox, as the Security audit skill requires. thirdshift ships no sandbox runner of its own yet; other sessions run unsandboxed.

Your machine
holds · your setup Keep production data, keys and unrelated logins off it, and assume a session can read or change anything on it.
Your user account
enforced, but shared It separates thirdshift from other users, not from its own sessions: a session can read the gh and git logins and push with them (#691).
The Worktree
not a security boundary It keeps your checkout and other Runs apart. Every Harness runs with its own sandbox and approvals off (ADR-0013). Claude Code's auto mode screens risky actions, but enforces no boundary.
Setup's sandbox probe
shipped · capability check With security.review or security.fix on, Setup checks this machine's bubblewrap sandbox on Linux: network isolation, a read-only host home and scratch writes with a dummy home directory. On macOS it reports the check unavailable. Passing is a capability check, not isolation for later sessions. Setup and User config.
An OS sandbox
required for Security target code · runner not shipped The Security audit skill requires an OS-enforced sandbox before running target code, with network, credential, write and resource isolation. If those controls cannot be enforced, the session must leave execution for validation. thirdshift ships no runner of its own yet (#726). Other sessions run unsandboxed; sandboxed Codex sessions remain open work (#398, ADR-0013).
Trusted accounts
issue input, not process isolation The repository's owner, organization members and collaborators. A session gets its issue's title, body and only these accounts' comments. Pickup takes only issues a Trusted account wrote and whose latest ready-for-agent label a Trusted account applied, with no later title or body edit by another account. Pickup's trust checks.
