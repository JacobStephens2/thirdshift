Reference architecture · six figures

Architecture

thirdshift turns a GitHub issue into a pull request by running unattended agent sessions against it. The agents write and review the code. Everything else is thirdshift, one deterministic program: it decides what an agent works on, checks its work, and never lets an agent mark its own work ready. These figures show what runs where, who does each step, and where the boundaries are.

Drawn from the manual for the source on main; an installed release may differ. For the same process told step by step, read How thirdshift works.

Figure 1 · the whole system

Agents write the code; thirdshift decides when it counts

An agent session can do anything your user account can, with nobody there to approve it. So every decision that matters is made outside the session, by thirdshift, before the session starts and after it ends. The Day shift is you: you shape the issues and review the pull requests.

thirdshift score also creates a Command: a Scoring run with a machine-wide lock, sampling merged factory work across configured GitHub owners. Samples, seeds and blind packets stay under ~/.thirdshift/evals/scoring/; thirdshift scores --json lists them by week. A packet holds historical issue text, the merged diff, pull request and CI conclusions, plus merge-time repository files without Git metadata. An independent Grader runs in the Experiment sandbox and checkpoints five criterion Scores per pull request, with its Harness and Model and a local Command-record link when available. A plan-limit warning leaves unscored packets for the next Scoring run. Its record and logs belong to thirdshift's own repository, and the Inbox and Stop read them through the same Command interface. Closed bugs also get proposed Bug origins through the shared Eval sandbox: fix and earlier history → introducing commit or none → GitHub pull requests → local Command record or Built-with line. The first proposal run backfills all closed bugs; Security fixes are excluded. thirdshift bug-origins [issue] --json reads the retained evidence and settlement; --confirm, --correct <pull request> and --none share Scoring’s writer lock. Confirmed origins contribute to their exact retained Ticket run’s show --json metrics and atomically publish proposed code-review Eval task folders. Each pins the PR head and its historical merge-base, keeps historical issue text (or the PR body when no issue was linked) and a draft catch criterion, and requires explicit Eval approval before running. Rejecting or correcting withdraws an old unapproved proposal. A plan-limit warning during Bug-origin analysis advances no window; a failed Bug-origin session records that bug with no commit, keeps its artifacts, and lets the window carry on.

Scoring samples, Bug-origin proposals and settlements, and Run metrics share retained pull-request attribution. Matching ignores ASCII letter case and trailing slashes. Latest means chronological RFC 3339 time, including UTC offsets, then greatest lexical record path and Command name for ties; invalid times sort before valid ones. Saved local record-path/name pairs select that exact Command under the matching pull request. Missing or mismatched local identities count for nothing; only absent or cross-host attribution selects the latest local Command, so Continuations never multiply a count.

The first sample adds a historical draw of 20 for human calibration; later weeks mark two for you. thirdshift scores <pull request> --mine --json takes the same writer lock and saves your five Scores atomically before returning them beside the model's as JSON. Ordinary CLI and Console reads share a view that withholds model Scores until human Scores exist. Calibration uses the stored assessments before withholding them, taking the latest 20 distinct paired pull requests separately for each criterion, with 18 agreements required.

The Console reads this machine's Commands and opens on its Inbox. Filesystem changes wake its Inbox and log readers; process exits and elapsed-time boundaries have their own wakeups. A slow recovery check catches missed notifications and expired sessions. A signed-in account can Stop or Requeue a live Command. It does nothing the CLI can't do and starts no work (ADR-0016).

The Console reads ready rows' pull requests and Needs you rows' issues and pull requests in a batched GraphQL query in the background once a minute, with blocking gh calls off its async thread. It keeps one answer per machine beside the logs. A changed answer or warning wakes open Inbox pages through the file watcher; unchanged reads update freshness without rendering or waking pages. thirdshift status uses that answer and reads GitHub itself only when it is missing or five minutes old. Failed reads retain the last facts and failure; after five minutes without a good read, both readers warn with when GitHub last answered and why the latest read failed. Both share a quota gate: fewer than 500 GraphQL points or REST requests holds off all their reads until reset, with a warning, preserving the rest for the factory. These limits and timings are not User config settings. An ended Needs you row moves to Done, Resolved or History when its issue closes or its pull request merges; a Triage row also moves when needs-triage is removed. Architect and Security runs use their dispatched Spec run's or Ticket run's issue and pull request. Live Silent and Slow rows stay until their Commands end. Ready rows leave on a merged or closed pull request. Resolved counts from the settlement time, and only rows GitHub cannot speak for age out while still waiting. Reopening brings back rows still in Done or Resolved. Rows in History retain the last facts without further reads, including when another row shares their issue or pull request. Dismissals hold across GitHub changes, and Undo uses the latest kept facts. These reads never write to GitHub (ADR-0023).

Security fix dispatch stores advisory metadata in the dispatched Command record’s security_fix_findings list before launch checks. Command details links each advisory with its title and severity (or “ungraded”), and the parent Security run marks the advisories it dispatched a fix for using that same list. Failed and interrupted fixes retain their links. The list is also exposed by thirdshift show <command> --json. Older records need no migration and no advisory links are inferred from issue bodies.

Any signed-in account can use Dismiss on the row in Needs you or Ready for review, always visible beside Copy where available. With JavaScript, d dismisses the selected row and selects the next; text fields and open dialogs keep their keys. An inline dismissal shows a temporary notice with Undo for that Command, outside the live Inbox so row replacement cannot remove it. The notice stays while hovered, focused, saving or showing an error. Without JavaScript, rows keep their full Dismiss form. Command details also offers Dismiss and Undo for a dismissed row. Command details shows each CLI form: thirdshift dismiss <command> or thirdshift dismiss <command> --undo. Both use the Console's session and CSRF checks. The browser keeps pending feedback and disables duplicate submissions through live updates; failed requests show their error and allow a retry. The dismissal lives beside the Command record and changes only the row's group; filesystem notifications update open pages, and the Activity log names the account and the Console. A live Command keeps running, and nothing is written to GitHub.

A dismissal accumulates covered kinds for the whole row, across child Ticket runs, and status --json exposes them as dismissal.kinds. An uncovered kind brings the row back, including a Finding behind a dismissed Security failure only while GitHub still shows its findings waiting. Each read adds one paginated REST list per repository with a Security run whose findings were waiting, respecting the quota reserve and using the Security run’s private-storage selection. The kept answer holds only finding URLs and waiting flags, with the first observed triage time; it retains no finding title, severity or write-up. A Finding leaves saying “findings triaged” once its records no longer wait: a draft advisory without severity or an open security-finding issue labelled needs-triage waits, and a record closed by a merged fix does not.

status --json exposes each row's kept issue, pull request and finding facts with their observation times in github. History freezes those times alongside the facts. Unchanged reads update observation times without waking pages. A dismissed row's Resolved clock stays anchored to its dismissal even if GitHub settles it later.

Before each agent session, optional host resource limits delay its start while available memory is too low or one-minute CPU load is too high. thirdshift resources and the Console's Resources page show the current snapshot and configured limits. Existing sessions continue.

Every session Step gets one Resume for killed background work, in Custom processes as in Ticket runs. Killed background work after a Resume is named in progress while following Steps decide the outcome. If the Process fails later, its cause names that work first. A Resume does not spend the Process's Repair budget.

Every Ticket run, including those started by Spec, Architect and Security runs, executes the compiled processes/ticket-run.toml: implement → security-review → delivery → self-merge, inheriting the Command's Harness, Model and Effort, Child asks and Limits. Spec dispatch and Claim-before-worktree ordering stay in front of the file. The Command retains its Ticket run identity and Session-trace names. thirdshift process show ticket-run prints a copyable file; thirdshift process check ticket-run issue <issue> validates it.

Ticket runs and Custom processes share the security-review catalogue Step. A Custom process places it on the Issue branch after editing and before delivery, outside parallel groups. The command or User config decides whether it runs. Harness fallback, private pre-existing findings and holds on Self-merge follow the Ticket run's rules; a Harness explicitly named in the file must start at preflight.

A Session trace records each agent session. A Command's whole Trace includes its child Ticket runs and stages; export it with thirdshift logs <command> --export <dir>. Logs and Trace export.

The Experiments list and live Experiment page read the same retained view as thirdshift experiments [id] --json. The grid opens Trial and Eval task Peeks with Scores and Grader reasons. Session links and thirdshift experiments <id> --session <session-id> share the Experiment's confined Session evidence reader. It validates saved Experiment metadata and reads the selected contents independently of Trial metadata, usage accounting and legacy Verdict upgrades, so unrelated corruption does not hide healthy evidence. Session IDs survive conversion from raw logs to Session traces. Rechecks remain CLI commands, and their updated Verdict appears on the page.

These pages also read proposed Eval tasks from the private suites listed by thirdshift evals list. Their approval action shares thirdshift evals approve <suite> <task> --json's manifest update, behind the Console's sign-in and CSRF checks. Approval changes only the state and starts no work. Future Experiments may select the task; existing Experiments retain their fixed inputs on resume.

The Console's Scores and Bug origins pages read the CLI's retained weekly samples and origin views. Human Scores use the same validation, machine lock and atomic checkpoint write as scores <pull request> --mine; model Scores are withheld from the form response until all five human Scores are saved. Bug-origin Confirm, Correct and Reject call the CLI settlement operation, including its Eval-task proposals and withdrawals. Both pages keep the Console's sign-in, CSRF checks and Themes, and start no work.

For Evals, the hidden --trial flag runs one Code review or Spec review through the same session code in a prepared repository. A Code review reviews the historical diff and keeps both axis reports without fixing or publishing anything. Its versioned JSON result and separate output folder keep Trials out of the Inbox and the Usual ranges. Trial protocol.

thirdshift experiment <candidate> owns the two Arms, the fixed Bar and an alternating Trial queue with two workers. Before building an Arm, apart from the release Baseline probe, it shows the remaining Trials, their worst case under the Bar's timeout and an estimate from earlier Experiments' completed Trials per suite and Harness, and asks on a terminal unless given --yes. Code Graders retain mechanical Scores; fresh model Graders score written criteria from shuffled blind packets on a configured Model outside both Arms when available. Scores retain reasons, wrong findings and borderline marks. The Verdict module computes paired suite intervals, with borderline counts, Arm minutes, tokens by Model, reported cost and Void counts and causes shown beside the Experiment's Verdict. Trial and model Grader Session traces and code Grader spans share its Command's Trace. Void Trials retry fresh up to twice, exhausted tasks leave both Arms, and more than a tenth dropped makes the Verdict inconclusive. Repeated Trial-only memory-cap stops produce an Arm finding. Its Command outcome puts a pass in Done and a fail or inconclusive Verdict in Needs you. Its Command record and logs live under thirdshift's repository; private Trial results and Grader artifacts stay under ~/.thirdshift/evals/experiments/. Both workers stop scheduling at a plan-limit warning, and a Trial cut short is void. It supports resume after that pause or interruption, Inbox observation and Stop. Experiments.

A prepared Trial runner owns retries, pauses and ordered publication; the two workers submit an Eval task, Arm and Trial index. Fresh execution and recovery follow the saved Bar's cause list and remaining retry budget. Recovery publishes already terminal pending history without another attempt, including after a publication failure, and never replays a retained pause. Attempt results, pending history and terminal results publish while the Trial's execution evidence remains live.

Before either Arm is built, Experiments report approved Eval tasks missing Trial inputs, including in release mode. Spec review Trials keep the production prompt, with no PR service: gh calls fail inside the sandbox and only the reports are graded.

The Verdict module derives intervals at the Bar's pass level and fail level from one set of paired draws, and shares its decision with the additional-task prediction. The pass level defaults to 70% and the fail level to 95%. The Bar records --pass-level and --fail-level before the first Trial and refuses changes afterwards. A pass needs only the pass-level lower bound above the margin (ADR-0025), and a pass wholly below zero is annotated as worse, within the margin. New Verdicts use paired-dirichlet-v3; readers preserve the Bar, Verdict and rule of saved paired-dirichlet-v2 and single-level Experiments. At today's suite sizes no pass level from 70% to 95% lets an A/A Experiment pass 80% of the time, so the default stays at the 70% floor; that needs about 20 code-review and about 80 Spec-review Eval tasks.

An A/A Experiment uses the same commit and Harness, Model and Effort choices in both Arms, with suites selected explicitly by --suite. It follows the same build, separate Trial, Grader and Verdict path to measure variation when nothing differs. thirdshift experiments <id> --record-difficulty pools its retained non-void Trials into each Eval task's optional Difficulty table, replacing earlier readings atomically per manifest under the suite lock shared with approval. It refuses unfinished Experiments and differing Arms. thirdshift evals lists Difficulty and whether the Eval task is discriminating: 0.15–0.95 inclusive, over at least 6 Trials. Fewer Trials or no table means unmeasured. A/A command example.

Trial integrity protects the issue text, declared inputs and commits under review. Review commits, local-origin pushes and report files are allowed. Code Graders receive a private copy of the prepared repository captured before the session, so session edits cannot change the code its checks grade.

Trial completion removes Harness caches from each attempt's Session home, retaining native transcripts and Session evidence. Once grading and all rechecks finish, the Experiment removes every attempt's repository copy. Paused and interrupted Experiments retain repositories for resume. Requests, results, traces, reports, Grader packets and Scores stay readable; pruning failures only warn.

Each Trial, code Grader and model Grader gets its own systemd-run --user --scope with MemoryHigh, MemoryMax, MemorySwapMax and OOMPolicy=kill. Its process raises oom_score_adj before starting work. The User config defaults are 1 GiB, 2 GiB and 1 GiB; scopes require a reachable user manager with lingering enabled for logged-out work.

The Experiment owns recheck history beside its immutable Grader Scores. thirdshift experiments <id> --json exposes pending borderline and decisive Scores, naming each decisive flip and its resulting provisional Verdict. thirdshift recheck <id> <trial> pass|fail --reason '…' takes the Experiment's exclusive lock and atomically saves the history, recalculated Verdict and pending list. thirdshift recheck <id> --pending lists the pending Scores and their fingerprint; thirdshift recheck <id> --batch <fingerprint> pass|fail --reason '…' checks that list under the same lock and records every listed Score in one atomic save. A stale fingerprint changes nothing. Rechecks stay in the CLI. They also update the latest invocation's Command outcome and Inbox group, preserving its completion time. The Verdict waits until the list is empty; flipping either pass/fail or a wrong-finding flag can make a Score decisive. Waiting rechecks place that invocation in Needs you; a confirmed pass moves it to Done.

thirdshift experiment --release <commit> compares the content commit with the last release tag on touched suites. The release script skips Experiments by default. Add --with-experiment to scripts/release.sh on each invocation to run one: it waits for rechecks and asks permission for a fail or inconclusive Verdict before pushing. Reruns with the flag reuse the Experiment, including before opening a pushed branch's PR. It refuses different main content before pushing or merging and checks the merged tree before tagging, including without an Experiment. No touched suite or a last release without the Trial flag carries on with a note. Releasing.

Each Ticket run's own process saves its Run metrics at completion in its Command record, including Ticket runs and Base fixes: outcome, Repairs, CI rounds, Unaddressed findings by Standards, Spec and Security, stage times against their Usual ranges, and minutes by stage and in total. Unaddressed findings counts retain Delivery's final PR body and the Security review's count, so later edits do not change them. Each Session stage keeps the review's Standards and Spec finding counts from its summary, with missing counts left missing. thirdshift show <command> --json includes these retained facts. The Console reads the same details, showing each Ticket run's available metrics and marking unavailable signals as Missing. thirdshift metrics <command> [--json] reads a Ticket run with its children; without a Command it groups weekly trends by repository, Harness, requested Model and Effort, Ticket run kind and session kind. Week and repository filters narrow that view. Historical metrics are computed from Command records without writing back, and missing signals stay missing. No combined score is produced.

Run metrics and Experiments share one Session usage module for tokens by observed Model and Harness-reported cost. Its normalized-event and retained-span readers resolve call amendments and partial totals, retaining fields a total omits. Input includes cache reads and writes. Reported Session cost wins; otherwise each Model's reported cost replaces its call costs. The metrics reader separately counts tool errors, permission denials, killed work and repeated tool calls within that session. Completion metrics sum these by session kind, and weekly Session trends split by the Harness version from each trace's resource. Saved completion metrics stay fixed. Historical metrics also read converted Session traces, leaving missing traces and unreported measurements missing.

Console and CLI readers share the User config's [console] other_accounts choice: "none" by default, "readable", or named local accounts. Discovery uses passwd home directories and readable logs.dir overrides, limited by filesystem permissions or ACLs. Other-account Commands carry their owner through Inbox grouping, Needs you counts and log readers. Shared Stop and Dismissal checks refuse them before any write or signal; the page offers those controls only for the serving account's own Commands. thirdshift console other-accounts shows or changes the setting.

Command details opens with the same subject and issue title as the Inbox, before Stop and Dismiss. The subject links to the issue and long titles wrap. Unknown titles say “(title unavailable)”; Commands without an issue show only their Inbox subject. The recorded issue title comes from the same details JSON as thirdshift show <command> --json.

Command details reconstruct Session signals only for the selected Command and its nested Ticket runs and dispatches; all records still contribute to Usual ranges and health. Weekly metrics read signals for every Command. A bounded memory cache retains derived signals by the resolved Session trace's path, length, modification time and file identity, checking the identity again after parsing. Disposable *.signals-cache.json files beside each Session trace also retain them across CLI processes and Console restarts. Per-trace locks coordinate readers. Appends, replacements and a different binary invalidate the saved signals; an unwritable cache falls back to parsing. Historical Command records are never rewritten.

Confirmed Bug origins are joined when metrics are read, from local Scoring checkpoints under ~/.thirdshift/evals/scoring/. The latest window's decision for each bug wins. Its retained local Ticket run identity selects the exact Ticket run; cross-host pull-request attribution selects the latest local Ticket run for that URL, as in Scoring, so Continuations never multiply a count. The Scoring data covers both hosts; metrics read no remote records. Late confirmations count in the Ticket run's start week, corrections move the count to the settled pull request, and rejected or unsettled origins count for nothing. Command details in show --json and the Console share this projection and reconstruct available historical metrics. Command records are never rewritten.

The same reader checks each session's shell commands against one code-owned destructive-command pattern list. Force pushes, shared-branch history rewrites and recursive deletes outside the Worktree are retained with their commands in Run metrics, with flag counts in weekly Session trends. This check is advisory: it never blocks or fails a Ticket run.

  1. Pre-flight checks stop a Ticket run before anything is created: the Issue URL must match the clone's origin, the issue must be open, and the Base branch must be on origin.
  2. The Claim labels the issue in-progress, so the issue list shows what the factory is working on.
  3. A Worktree gives the Ticket run its own checkout beside your clone, so yours is never touched.
  4. Implementation runs the implement session, also available to a Custom process as the implement catalogue Step on its Issue-branch worktree. On issues labelled bug, diagnosis comes first: a reproduced bug gets a failing regression test and fix; a Continuation whose Issue branch is ahead of the Base branch reproduces at their merge base, and a fix already on the branch goes on to review and the pull request; an unreproduced bug ends successfully with triage notes and needs-info, skipping later Steps and cleaning up the Claim and worktree. Security fixes and Base fixes keep their own flow. Delivery then pushes the branch and checks that the pull request exists and targets the Base branch. thirdshift, not the agent, marks it ready.
  5. Keeping it green merges the Base branch in and watches CI. A conflict or the branch's own red check starts a Repair, at most 5 a Ticket run.
  6. The Self-merge, when asked, merges exactly the head commit whose CI thirdshift watched.
  7. Cleaning up removes the Worktree. A Failed ticket run pushes its work first and turns the pull request back into a draft.

Figure 2 · thirdshift <Issue URL>

A Ticket run: one issue in, one pull request out

Work reaches a Ticket run as a Ready issue, labelled ready-for-agent. You write most of them, but thirdshift writes some too: an Architect run publishes its plan, a Security run allowed to fix files the fix, and a Base fix files the red CI on the Base branch. One agent session writes, tests and reviews the change, then opens the pull request. A second session reviews it for security, if you ask for that. Then thirdshift checks, pushes and watches.

Figure 3 · thirdshift merge <Issue URL>

A Ticket run that Self-merges

The same Ticket run, one step further. Once the pull request is open, ready, mergeable and green, thirdshift merges it with a merge commit, on exactly the head whose CI it watched. Commits someone else pushed to the branch are reviewed first. A required human review still stops it, leaving the pull request ready for you.

Figure 4 · thirdshift <Spec URL>

A Spec run: many Ticket runs, one pull request

An issue with sub-issues is a Spec, and its sub-issues are Tickets. Each Ticket gets its own Ticket run that Self-merges, not into main but into the Spec branch, in the order GitHub's “blocked by” links allow. Independent Tickets run at once, each in its own Worktree. The Spec ends as one pull request for you to review.

Figure 5 · thirdshift pickup, architect, secure

The Passes: the factory finds its own work

Before selecting a Ready issue, Pickup files one ordinary bug Ticket when the Base branch's latest push CI failed more than 30 minutes ago and no CI-red Ticket is open. Concurrent hosts reserve filing on origin. CI read failures warn and leave Pickup running; this check does not hold Self-merges.

Once a Pickup run, an Architect run or a Security run knows its repository, it replaces that kind's last-fired time under the repository's log folder, before launch checks or the local Pass lock. Repeated skips update the time without adding Activity log lines. thirdshift status, thirdshift cronjobs and their Console views read the same per-repository times; no reader starts work. A Custom process started with no issue, and no Issue-branch worktree, shares the lock and does not record a last-fired time. A file that declares an Issue-branch worktree is refused when no issue is given, before the lock.

A Pass takes no Issue URL, so your operating system's scheduler can start it; thirdshift never schedules itself. Only one Pass runs on a repository at a time, and a Pass with nothing to do is skipped, not failed. Architect and Security runs wait while a Ready issue is open, so work you shaped goes first. A Custom process started with no issue is a Pass for that one-at-a-time rule and does not wait on a Ready issue or an Architect idea, unless the file declares an Issue-branch worktree: that is refused before any session, rather than skipped. One started with an issue is not a Pass. Your scheduler can start Architect runs every few minutes and Security runs on a schedule, with fixing allowed.

Containment: where the boundaries are

Ticket run, Spec run and Security sessions can do what your user account can. So containment comes from where you run it. The boundary that holds is the machine: best a virtual machine with nothing from production on it. Security sessions may run target code only inside an OS-enforced sandbox, as the Security audit skill requires. thirdshift ships a sandbox runner for Trials and Graders; Ticket run, Spec run and Security sessions run unsandboxed.

Your machine
holds · your setup Keep production data, keys and unrelated logins off it, and assume a session can read or change anything on it.
Your user account
enforced, but shared It separates thirdshift from other users, not from its own sessions: a session can read the gh and git logins and push with them (#691).
The Worktree
not a security boundary It keeps your checkout and other Ticket runs apart. Every Harness runs with its own sandbox and approvals off (ADR-0013). Claude Code's auto mode screens risky actions, but enforces no boundary.
Setup's sandbox probe
shipped · capability check With security.review or security.fix on, Setup checks this machine's bubblewrap sandbox on Linux: network isolation, a read-only host home and scratch writes with a dummy home directory. On macOS it reports the check unavailable. Passing is a capability check, not isolation for later sessions. Setup and User config.
An OS sandbox
required for Security target code · runner not shipped The Security audit skill requires an OS-enforced sandbox before running target code, with network, credential, write and resource isolation. If those controls cannot be enforced, the session must leave execution for validation. thirdshift ships no runner for Security target code yet (#726). Trials and model Graders run in bwrap sandboxes with provider-only networks; Code Graders run offline. Graders see their packets and, for Code Graders, the prepared repository; raw Trial logs and Arm mappings stay hidden. Ticket run, Spec run and Security sessions run unsandboxed; sandboxed Codex sessions remain open work (#398, ADR-0013).
Trusted accounts
issue input, not process isolation The repository's owner, organization members and collaborators. A session gets its issue's title, body and only these accounts' comments. Pickup takes only issues a Trusted account wrote and whose latest ready-for-agent label a Trusted account applied, with no later title or body edit by another account. Pickup's trust checks.
