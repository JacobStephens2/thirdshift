# Isolating a Run: the Trial sandbox, containers, microVMs and hosted providers

Research date: 2026-10-27.

**Question.** [#1486](https://github.com/JacobStephens2/thirdshift/issues/1486) asks how thirdshift should isolate **Runs** — the Ticket run, Spec run, Architect run, Security run, their **Repairs**, reviews and **Resumes** — and whether a hosted sandbox provider (Daytona, E2B and comparable) is a good way to do it, measured against local options: reusing thirdshift's own Trial sandbox, rootless containers, gVisor and microVMs. Today the **Worktree** is the only boundary ([ADR-0013](../adr/0013-every-harness-runs-unattended-and-fully-trusted.md)), and a **Session** runs with the user account's full permissions, `sudo` included ([guide.md, "Unattended sessions"](../guide.md#unattended-sessions)). The host constraint is lifted: a bigger Linux host with room for container images can be provided ([eval-build-vs-buy.md §8.1](eval-build-vs-buy.md)).

## TL;DR

- **Isolate Runs locally, by reusing the Trial sandbox's launcher. Don't buy a hosted sandbox.** The Trial sandbox is already the architecture the vendor ships for this exact problem, and a hosted provider breaks the three things a Run needs most: the shared `.git`, the subscription logins, and the terms they sit under. (§3, §4.1, §7)
- **Isolation cannot protect the two credentials that matter, and no option changes that.** A Run's session must hold a Harness login that can spend the plan, and a git credential that can push. Anthropic says this in its own words about its own dev container: it "does not prevent a malicious project from exfiltrating anything accessible inside the container, including the Claude Code credentials stored in `~/.claude`" ([dev container](https://code.claude.com/docs/en/devcontainer)). What isolation buys is the *rest* of the machine: the other repositories, the other Runs' worktrees, `~/.ssh`, the Console on loopback, and `sudo`. That is worth having, and it is the honest claim to make. (§2)
- **ADR-0013's reasoning has gone stale in one direction and held in another.** It rejected each CLI's own sandbox in 2026 because stock Ubuntu's `kernel.apparmor_restrict_unprivileged_userns` stopped bubblewrap, and because agy's and Grok's sandboxes make the shared `.git` read-only.
  - **Stale:** the AppArmor block has a documented per-binary fix, and this factory host already runs it for bwrap ([sandcastle-fit.md §3.2](sandcastle-fit.md)). Claude Code now ships a configurable sandbox with a *per-session* `--settings` path, which thirdshift already uses for attribution. Codex's `workspace-write` grew a domain-allowlisting command proxy.
  - **Held, and this is the load-bearing part:** every Harness's own sandbox confines *commands*, not the session, and each one protects `.git` as read-only — exactly the directory a Run must write. So the Harnesses' sandboxes still cannot be the boundary for a Run. An outer boundary that thirdshift controls can. (§4.2)
- **The outer boundary thirdshift should build is the one it already has.** `src/sandbox.rs` plus `src/proxy.rs` is bwrap with its own PID and network namespaces, a fresh home holding only the login, and an allowlisting CONNECT proxy that checks the allowlist before DNS and refuses names resolving to loopback or the host's own addresses. `anthropics/sandbox-runtime` (`srt`) is the same design — bubblewrap plus a netns-removed sandbox reached only through host-side proxies on bind-mounted Unix sockets, Seatbelt on macOS — and Anthropic's own guidance is to "run Claude Code (local mode) inside the sandbox runtime with a network allowlist limited to the hosts you approve" for unattended work ([sandbox environments](https://code.claude.com/docs/en/sandbox-environments)). thirdshift converged on the vendor's answer independently. (§4.1)
- **The seam is small and already exists.** `Sessions::within_sandboxed` takes a `sandbox::Prepared` and wraps every session, Resume included, in `Launch::command`. `Outside` is the trait, and `OnMachine` its one implementor, holding `sandbox: Option<Launch>`. A Run sandbox is a second `prepare()` request with different binds, not a new execution path. (§1.3, §7)
- **What a Run needs that a Trial does not** is the whole of the work: the main checkout's shared `.git` read-write, `gh` with the user's GitHub auth, the real Harness home rather than a fresh one, package registries and toolchains rather than one provider host, and hours rather than thirty minutes. Each of those widens the boundary, and two of them widen it a lot. (§1.2, §5)
- **The shared `.git` is the hard problem, and it is a code-execution hole, not just a file-access one.** A Worktree's `.git` file points at `<main>/.git/worktrees/<name>`, while objects and `refs/` live in `<main>/.git`, and "By default, the repository `config` file is shared across all worktrees" ([git-worktree](https://git-scm.com/docs/git-worktree)). So a Run must write a directory whose `config` and `hooks/` run code as the user on the next git command in *any* worktree. Sandcastle shipped this hole knowingly; `srt` and Claude Code's sandbox both deny `.git/config` and `.git/hooks` by default for this reason; Anthropic's self-hosted runner docs say it plainly: "Git in your hook reads configuration files that a session can write, and a credential helper or filter driver named in one of them runs with your hook's privileges" ([deploy](https://code.claude.com/docs/en/self-hosted-environments-deploy)). Any Run sandbox must deny those paths inside an otherwise-writable `.git`. (§5.1)
- **Hosted providers: no, and the reason is the shared `.git`, not the price.** (§3)
  - **They are remote filesystems.** Every one works as "code in, commits out" — Sandcastle's remote providers use `git format-patch` and `git am`. A Run's delivery path assumes a local Worktree over a shared `.git`, with `src/worktree.rs` and `src/worktree/` running to 9,783 lines, 7,342 of them acquisition, preservation, synchronization and recovery tests, behind that assumption. Adopting a provider is a rewrite of how thirdshift delivers work, not a sandbox change.
  - **The terms are unsettled for three of six Harnesses, and one is an outright prohibition.** Anthropic ships `claude setup-token` for exactly this and acknowledges "managed sandbox and remote execution services", yet its Consumer Terms bar automated access except via an API key "or where we otherwise explicitly permit it", and **no Anthropic page addresses a subscription credential on a third-party cloud VM**. OpenAI permits a ChatGPT `auth.json` on "trusted private infrastructure" but says "Do not share the same file across concurrent jobs or multiple machines" — which parallel Runs in per-Run sandboxes is. **Google's Antigravity terms are explicit**: "Using third party software, tools, or services to access the Service … is a breach of this Agreement". That last one is a finding about the agy Harness generally, hosted or not, and belongs in the grill (§8.2).
  - **The feature they charge for is one thirdshift doesn't need.** Pause-and-resume-hours-later is the headline — E2B keeps paused sandboxes "indefinitely" and resets the runtime clock; Fly Sprites resume in 100–500 ms with "processes pick up mid-thought". thirdshift's **Resume** is immediate and in-process, and a **Continuation** is a new Run (§1.2).
  - **Runloop is out entirely:** "Runloop is winding down its services", transition support ending 2026-11-13. **Cloudflare is out on two counts:** "Cloudflare does not guarantee that an instance runs for a set time", and "When a Container instance goes to sleep, the next time it starts, it uses a fresh disk from the container image" — so a `$HOME` login dies on every sleep.
  - **Cost, for the record, is unremarkable:** roughly $0.06–0.24 per sandbox-hour across E2B, Vercel, Daytona, Fly Sprites and Modal, though E2B needs $150/month Pro to exceed a one-hour session and Daytona gates open egress behind a $500 top-up.
  - **One thing to check first:** Vercel ships a first-party integration with a project called **Herdr** that "runs each agent in its own persistent Vercel Sandbox", and this factory's worktrees live under `~/.herdr/worktrees/`. If it is the same Herdr, its credential model — "The plugin never copies Vercel or coding-agent credentials from your machine" — is prior art the Day shift may already run (§3.4). **[unverified]**
- **The other local options lose to bwrap on this problem, for reasons that are not about disk any more.**
  - **Rootless Podman** gives a cleaner per-session filesystem and `podman exec` re-entry, and its rootless pasta default already assumes `--no-map-gw` "to avoid direct access from container to host using the gateway address" ([podman-run](https://docs.podman.io/en/latest/markdown/podman-run.1.html)). It costs `loginctl enable-linger`, `--userns=keep-id` for the shared repo, an image per target repository, and no stronger kernel boundary than bwrap. `idmap` mounts are rootful-only. Checkpoint/restore is out: CRIU needs root ([rootless.md](https://github.com/containers/podman/blob/main/rootless.md)).
  - **gVisor** costs exactly this workload's profile. Its own performance page says "many small file operations" give "predictably poor results" and that its VFS "needs improvement" — a Node agent CLI plus `npm install` plus `cargo test` is that workload. It needs Linux 5.6+, x86_64 or arm64, and **does not run on macOS** ([install](https://gvisor.dev/docs/user_guide/install/)).
  - **microVMs** give the only real kernel boundary and the worst fit. Firecracker has no host directory sharing out of the box (block devices are host files), "does no network traffic filtering", needs root for its jailer and TAP, is Linux-only, and its own snapshot docs say "we consider resuming execution from the same state more than once insecure" ([snapshot support](https://github.com/firecracker-microvm/firecracker/blob/main/docs/snapshotting/snapshot-support.md)). Kata is a containerd-shaped answer and gives no overhead numbers.
- **macOS gets weaker isolation, and that should be stated rather than papered over.** For a native CLI process there is one mechanism: `sandbox-exec`/Seatbelt, which its own man page on this machine marks `DEPRECATED` and whose profile language Apple does not document — and which is nonetheless what both `srt` and Claude Code use. `apple/container` 1.6.1 runs "each Linux container inside of its own lightweight virtual machine" but needs macOS 26 and Apple silicon, and isolates *Linux* workloads, not a macOS process. (§4.4)
- **Credential scoping is the highest-value change that needs no sandbox at all.** A GitHub App installation token expires "after 1 hour" and can be narrowed to named repositories and named permissions at mint time ([GitHub docs](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-an-installation-access-token-for-a-github-app)). Anthropic's own posture for unattended runners is "Don't bake long-lived or broadly scoped push credentials into a shared runner image… Instead, mint a short-lived, least-scoped token per session". thirdshift could do this today, before any sandbox ships. (§5.2)
- **Recommendation: a staged, opt-in local sandbox, Security run first.** Reuse the Trial launcher; make it opt-in per Run kind; start with the Security run's proof-of-concept execution, which is the one place the factory already *wants* a boundary and already fights for one by hand. Fold #726 in, keep #398 as a narrow live check, and amend ADR-0013 rather than replace it. (§7, §8)

## 1. What a Run does today

### 1.1 The six Harnesses, unattended

ADR-0013 fixes the flags: `--permission-mode auto` for Claude Code, `--dangerously-bypass-approvals-and-sandbox` for Codex, `--dangerously-skip-permissions` for agy, `--always-approve` with `GROK_FOLDER_TRUST=0` for Grok Build, `--yolo` for Muse Code, and `--auto --standalone` for OpenCode. No user setting changes them. Claude Code's auto mode is the one case with any per-action control, and Anthropic is explicit that it is not a boundary: "The classifier is a per-action control, not an isolation boundary, so an isolation boundary still adds defense in depth for unattended runs, and is not required the way it is for `--dangerously-skip-permissions`" ([sandbox environments](https://code.claude.com/docs/en/sandbox-environments)). Anthropic speaks only for its own CLI, but the distinction it draws is the useful one: a classifier reviewing each action, versus no review at all. ADR-0013 puts Claude Code in the first category and the other five Harnesses — approvals off, sandbox off — in the second. Anthropic's rule for the second category is "Always run `--dangerously-skip-permissions` sessions inside a container, a VM, or the sandbox runtime". Applied by analogy, five of thirdshift's six Harnesses are in the category that always needs an outer boundary **[interpretation]**.

### 1.2 What a Run's session touches

Verified in the code and the guide:

| Need | Where it lives | Consequence for a boundary |
|---|---|---|
| Harness login, on a **subscription** | `~/.claude/.credentials.json` or `CLAUDE_CODE_OAUTH_TOKEN`; `$CODEX_HOME/auth.json`; `~/.config/muse/auth.json`; `~/.gemini/antigravity-cli/…`; `$GROK_HOME/auth.json`; OpenCode's `auth.json` ([eval-sandboxes.md §4](eval-sandboxes.md)) | Must be inside. Codex rotates `auth.json` **in place**, so bind the real file, never a copy |
| Commits and pushes | The agent commits and pushes; `src/git.rs` also pushes (the **Pickup** reservation of [ADR-0017](../adr/0017-pickup-reserves-issues-on-origin.md)) | The main checkout's `.git` must be writable (§5.1) |
| `gh`, with the user's GitHub auth | `src/github.rs` shells out to `gh`; the agent uses it too | A GitHub token that can push is inside |
| CI polling | `src/ci.rs`, `src/poll.rs`, through `gh` | `api.github.com` must be reachable |
| **Factory skills** | Written to a temp directory, symlinked into the worktree by `skills::link_into`, excluded through `.git/info/exclude` | The link target is outside the worktree and must be bound in |
| Toolchains, registries, caches | Whatever the target repository needs; the guide tells operators to install them up front rather than let agents download their own | A provider-only allowlist is far too narrow (§4.1) |
| Long sessions, and **Resume** | `Sessions::run` gives one Resume, in the same process, immediately | **The sandbox only has to outlive one Run process.** No pause-and-resume-hours-later is needed **[interpretation]** |
| **Session traces**, OTLP | `src/session/trace.rs`; `otlp.endpoint` streams ended spans live | Already redacts sandbox launcher environment values from retained arguments |
| Many Runs at once | `spec.parallel` (default 3) bounds Spec run Tickets; `src/resources.rs` checks RAM and load before each session | The guide already warns "container quotas are not measured" |

Two facts here are load-bearing and easy to get wrong. **Resume is immediate and in-process**, so the whole hosted-provider pause/snapshot feature set is answering a question thirdshift does not ask. And a **Continuation** is a *new Run*, not a resumed session, so it needs no sandbox continuity either.

### 1.3 The seam

`src/session.rs` has one trait and one implementor:

- `trait Outside` has `run_session(purpose, label, resume, prompt, log)`.
- `struct OnMachine` implements it, holding `worktree`, `harness`, `adapter`, `recording` and `sandbox: Option<crate::sandbox::Launch>`.
- `run_session` asks the adapter for `invocation.args`, then branches: with `Some(launch)` it builds `launch.command(&invocation.args)`, otherwise it runs the Harness binary directly.
- `Sessions::within_sandboxed` is the sandboxed constructor; `Sessions::checked_within` is the one every Run uses, and it passes `sandbox: None`.

So isolating Runs is not a new execution path. It is a `sandbox::Request` for a Run, and threading the resulting `Prepared` through `checked_within`. Everything downstream — Resume, the Security review's Harness fallback, recording policy, progress lines — already runs over the same seam. That is the single strongest argument for the local option, and it is an argument about thirdshift's code rather than about any vendor.

## 2. The threat model

### 2.1 What a boundary would buy

Against a session that goes wrong — a prompt injection in an issue or a dependency, a confused agent, or a malicious dependency's build script:

- **The rest of the disk.** Today a session can read and write every repository the user owns, `~/.ssh`, the **Credentials** file, other Runs' worktrees, `~/.thirdshift/` with its Session traces and Scoring data, and the Day shift's own notes.
- **Other Runs.** With `spec.parallel` at 3, a Spec run's Tickets run beside each other as the same user, in sibling worktrees of the same checkout.
- **Host loopback.** [eval-sandboxes.md §1](eval-sandboxes.md) counted the Console on 8711, Caddy's admin API on 2019 and a dozen other listeners. Abstract Unix sockets go with it: network namespaces "isolate the UNIX domain abstract socket namespace", and "Socket permissions have no meaning for abstract sockets".
- **`sudo`.** The guide says sessions run "with the full permissions of that user account, including `sudo` if the user has it".
- **Host command lines.** /proc has no `hidepid` and thirdshift passes each **Session prompt** as an argument, so a concurrent session's prompt is readable without a PID namespace ([eval-sandboxes.md §2](eval-sandboxes.md)).
- **Unbounded egress.** Nothing today stops a session reaching any host on the internet.
- **Processes left behind.** `--unshare-pid` makes the kernel SIGKILL everything in the namespace when its init dies, which is strictly better than the guide's current "anything else an agent does as your user stays".

### 2.2 What no boundary can buy

- **The Harness login.** It must be inside to spend the plan. Anthropic's dev container warning is the first-party statement of this, and it names the credential: a `--dangerously-skip-permissions` session can exfiltrate "the Claude Code credentials stored in `~/.claude`". Their advice follows from it: "Avoid mounting host secrets such as `~/.ssh` or cloud credential files into the container; prefer repository-scoped or short-lived tokens."
- **A git credential that can push.** This is the irreducible one, and §5.2 is the only real answer.
- **Egress through an allowed host.** Both Anthropic pages say the filter is hostname-only: `srt`'s threat model says "Broad domains such as `github.com` can allow exfiltration, and domain fronting may bypass filtering", and Claude Code's docs warn that "Allowing broad domains such as `github.com` can create paths for data exfiltration". A Run must allow `github.com`. So a Run sandbox's egress allowlist bounds *where* data can go, not *whether* it can go.
- **What reaches the model.** "Isolation also does not change what is sent to the model" ([sandbox environments](https://code.claude.com/docs/en/sandbox-environments)). This matters for a **Security run** under [ADR-0015](../adr/0015-security-findings-stay-private-until-fixed.md): the finding's write-up goes to the provider either way, and no sandbox changes that.
- **A kernel exploit.** bwrap, rootless Podman and gVisor all share the host kernel. Ubuntu's own note on relaxing the userns restriction says it "does not mitigate against kernel exploits that abuse the unprivileged user namespaces feature". Only a microVM changes this, and §4.3 says what that costs.

### 2.3 The honest claim

A Run sandbox is a blast-radius reduction, not a containment guarantee. It turns "a bad session owns the account" into "a bad session owns this worktree, this issue's branch, and whatever the plan and the push token can reach". That is a real improvement and the right thing to promise. Promising more would be wrong, and bubblewrap's own README makes the general point: "the level of protection between the sandboxed processes and the host system is entirely determined by the arguments passed to bubblewrap."

## 3. Hosted sandbox providers

### 3.1 What they are

All of them sell the same product: an API that boots an isolated Linux environment, runs commands in it, and bills by the second. The isolation their docs claim:

| Provider | Isolation, as the docs state it | Max single run | Resume |
|---|---|---|---|
| **E2B** | Firecracker microVM, own kernel | 24 h Pro, 1 h Hobby | Filesystem **and memory**; "A paused sandbox is kept indefinitely"; "the continuous runtime limit is reset" ([persistence](https://docs.e2b.dev/sandbox/persistence)) |
| **Vercel Sandbox** | Firecracker microVM, dedicated kernel | 24 h per session, Pro | Filesystem only, "Persistence is the default", total lifetime "effectively unbounded" ([persistent sandboxes](https://vercel.com/docs/sandbox/concepts/persistent-sandboxes)) |
| **Modal Sandboxes** | gVisor **or** a VM runtime, selectable | 24 h | Filesystem snapshots; memory snapshot is experimental, has a 7-day TTL, and "Taking a memory snapshot currently terminates the Sandbox" ([sandbox snapshots](https://modal.com/docs/guide/sandbox-snapshots)) |
| **Daytona** | Containers with namespaces by default; a VM class has its own kernel, hypervisor unnamed | No documented max | Filesystem on stop; memory only on the VM class |
| **Fly Sprites** | "dedicated microVM" | 1 h per Task, must be refreshed | Warm pause, 100–500 ms resume, "processes pick up mid-thought" ([lifecycle](https://docs.fly.io/sprites/concepts/lifecycle)) |
| **Fly Machines** | Firecracker | No documented max or guarantee | `stop` resets the rootfs; `suspend` keeps memory but needs ≤2 GB RAM |
| **Cloudflare Sandbox** | Firecracker microVM | **No guarantee** | "Restored processes do not continue"; a fresh disk from the image on every start |
| ~~**Runloop**~~ | VM, unnamed | — | **Disqualified: "Runloop is winding down its services"**, transition support ends 2026-11-13 ([transitions](https://docs.runloop.ai/docs/transitions/overview)) |

Indicative cost, from the pricing pages: E2B "$0.000014 per vCPU-second" and "$0.0000045 per GiB-second" but **$150/month Pro** to exceed a one-hour session; Vercel "Active CPU $0.128/hour" plus "$0.0212/GB-hour", with their own worked example of a mostly-idle 1 vCPU / 2 GB sandbox at "$31.45/30 days"; Daytona "$0.0504/h" per vCPU and "$0.0162/h" per GiB; Fly Sprites "$0.0385/CPU-hour" and "$0.021875/GB-hour"; Modal Sandboxes at "3x list price", about $0.238/hour for 1 core and 4 GiB **[interpretation, derived]**.

### 3.2 Why none of them fits a Run

The cost is not the problem. Five things are, in rising order of severity.

1. **They are remote filesystems, so the shared `.git` cannot exist.** Every provider's model is "code goes in, commits come out". Sandcastle's remote providers bring work back with `git format-patch` and `git am` ([sandcastle-fit.md](sandcastle-fit.md)). A Run's whole delivery path — the Worktree on an Issue branch, objects and refs in the main checkout's `.git`, `git worktree` ownership and cleanup, the ADR-0017 Pickup reservation, `src/worktree.rs` and `src/worktree/` with their 9,783 lines, 7,342 of them tests — assumes a local checkout. Moving a Run into a hosted sandbox is not a sandbox change; it is a rewrite of how thirdshift delivers work (§5.1).
2. **The subscription token leaves the machine, and that is the one thing every vendor's text is nervous about.** This is the concern [sandcastle-fit.md §2.4](sandcastle-fit.md) recorded, and it has not improved:
   - **Anthropic** ships the headless credential — `claude setup-token` makes a one-year `CLAUDE_CODE_OAUTH_TOKEN` and "authenticates with your Claude subscription" ([authentication](https://code.claude.com/docs/en/authentication)) — and acknowledges hosted sandboxes in general: "Several managed sandbox and remote execution services can host the container for you. The same checklist applies as for any container you operate: review what is mounted writable, what credentials and tokens are reachable inside it" ([sandbox environments](https://code.claude.com/docs/en/sandbox-environments)). Against that, the Consumer Terms bar accessing the Services "through automated or non-human means, whether through a bot, script, or otherwise" except "when you are accessing our Services via an Anthropic API Key or where we otherwise explicitly permit it", and bar making your Account "available to anyone else" ([consumer terms](https://www.anthropic.com/legal/consumer-terms)). **No Anthropic page addresses whether a subscription credential may sit on a third-party cloud VM.** The likely reading is that `setup-token` is the explicit permission the clause contemplates, but that is **[interpretation]**, not stated.
   - **OpenAI** is the clearest and the most conditional. Its CI/CD guide permits reusing a ChatGPT `auth.json` only when "the runner is trusted private infrastructure", says "Do not use this workflow for public or open-source repositories", and — decisively for thirdshift — "Use one `auth.json` per runner or per serialized workflow stream. Do not share the same file across concurrent jobs or multiple machines" ([CI/CD auth](https://learn.chatgpt.com/docs/auth/ci-cd-auth)). thirdshift already shares one `auth.json` across parallel Runs ([eval-sandboxes.md §4](eval-sandboxes.md)). A hosted sandbox per Run makes that worse, not better: it becomes concurrent jobs on multiple machines, which is the sentence's exact prohibition **[interpretation]**.
   - **Google is the one outright prohibition, and it bears on thirdshift itself, not just hosted sandboxes.** Antigravity's terms, clause 6: "Using third party software, tools, or services to access the Service … (e.g. using OpenClaw with Antigravity OAuth) is a breach of this Agreement", and such actions "may be grounds for suspension or termination of your Antigravity and/or Gemini CLI accounts" ([terms](https://antigravity.google/terms/)). Whether invoking the *official, unmodified* `agy` binary from a wrapper counts is the live question and **the terms do not resolve it**. This is a finding about the agy Harness generally, and it belongs in the grill (§8) whatever happens to #1486.
   - **xAI**'s pages return 403 to automated fetches; its AUP reportedly prohibits "Accessing the Services through unauthorized automated or non-human means" with no API-key carve-out in the visible text **[unverified — confirm in a browser]**.
3. **Sandcastle's evidence that these providers are broken for exactly our two main Harnesses still stands.** Its Vercel and Daytona providers drop stdin, so "claudeCode gets an empty prompt" ([#936](https://github.com/mattpocock/sandcastle/issues/936)), and Codex reads its prompt from stdin too. thirdshift passes prompts as arguments rather than stdin, so it would not hit that bug the same way — but the signal is that the remote path is the least-exercised one in the one project that ships it **[interpretation]**.
4. **The feature they compete on is one thirdshift does not need.** Pause-and-resume-hours-later is the headline capability — E2B's indefinite paused sandboxes, Sprites' "mid-thought" resume, Modal's memory snapshots. thirdshift's **Resume** is immediate and in-process (§1.2), and a **Continuation** is a new Run. The provider feature that would justify the price is answering a question thirdshift does not ask.
5. **Privacy and residency are worse, and ADR-0015 cares.** E2B has a SOC 2 Type II report but no data-residency commitment; Cloudflare publishes **no region list and no residency statement** for Containers; Modal routes function inputs through Virginia by default and `routing_region` "doesn't apply to Sandboxes". A **Security run** handling an unfixed vulnerability's write-up under ADR-0015 would put that write-up, and its proof-of-concept, on a third party's disk. The finding already goes to the model provider (§2.2); adding a second vendor is a decision, not a side effect.

### 3.3 The first-party hosted options, and why they are the wrong shape

Both model vendors now run their own sandboxes, and both own the agent loop:

- **Anthropic cloud sessions** run in "an isolated, Anthropic-managed VM", with a default-allowlist network proxy and — the genuinely enviable part — "git credentials and signing keys stay outside the sandbox, and a proxy authenticates on the session's behalf with scoped credentials" ([claude-code-on-the-web](https://code.claude.com/docs/en/claude-code-on-the-web)). There is no separate charge for the VM. But Anthropic drives the session: `claude -p --cloud <id>` only "queues a message into that existing session", and there is no way to boot the VM and run thirdshift in it. It is also one Harness of six.
- **Claude Code self-hosted environments** invert it — Anthropic's runner on your hardware — and are "public beta on Team and Enterprise plans", which this factory is not on.
- **Codex Cloud** runs in "isolated OpenAI-managed containers" with a setup phase that has network and an agent phase that does not by default. Same shape, same problem.

These are worth reading for their *design*, not for adoption. Three ideas transfer directly, and §5.2 and §7 take them: a credential proxy that keeps the git token outside the sandbox; "ephemeral, per-session containers … with `--capacity 1`" so nothing outlives its session; and "default-deny egress at the network layer" because "Session code is model-directed and can attempt connections to arbitrary hosts" ([deploy](https://code.claude.com/docs/en/self-hosted-environments-deploy)).

### 3.4 One thing to check before anything else

Vercel ships a first-party integration with a project called **Herdr**: "a terminal workspace that runs coding agents in parallel, one per pane (tmux for agents)", whose plugin "runs each agent in its own persistent Vercel Sandbox" ([ecosystem/herdr](https://vercel.com/docs/sandbox/ecosystem/herdr)). This factory's worktrees live under `~/.herdr/worktrees/`. If that is the same Herdr, then its credential model is prior art the Day shift may already be running, and it answers our question in the opposite direction from this note: "The plugin never copies Vercel or coding-agent credentials from your machine. You authenticate the agent inside its sandbox, where the credential persists across stops and resumes." Whether the two Herdrs are the same is **[unverified]** and is the first question in §8.

Vercel's own harness docs are also worth reading for one warning that reads as a direct comment on thirdshift's architecture: "Claude Code and Codex are command-line tools built for one user, and they keep their state on disk. Today's versions can be kept apart, but they ship often, and nothing promises that the next version won't keep state that one session leaves behind for another" ([agent harnesses security](https://vercel.com/docs/agent-harnesses/security)). Their conclusion — one sandbox per session — is the same as Anthropic's `--capacity 1`, and the same as what §7 recommends locally.

## 4. The local options

### 4.1 Reusing the Trial sandbox

**What exists.** `src/sandbox.rs` (2,010 lines) and `src/proxy.rs` (794 lines) already do, for a Trial:

- bwrap with its own PID and network namespaces, so the session sees no unbound path and no host process, and everything it starts dies with it.
- A network holding only its own loopback. A Harness that ignores the proxy finds no route, and even DNS has none.
- A fresh home holding the login and the four read-only user-level instruction files, with ambient environment cleared and Cargo registry credentials hidden.
- An allowlisting CONNECT proxy outside the sandbox on a Unix socket bound in, with a socat relay inside, reached through `HTTPS_PROXY`. The allowlist is checked *before* DNS, and names resolving to loopback or the host's own addresses are refused.
- A documented failure mode: `sandbox_unavailable`, plus `THIRDSHIFT_TRIAL_NO_SANDBOX` as the escape hatch when bwrap breaks on a machine.

**That this is the vendor's architecture is the strongest single finding in this note.** `anthropics/sandbox-runtime` 0.0.81 is "a lightweight tool that enforces filesystem and network restrictions on arbitrary processes at the OS level, without a container", and on Linux it is "bubblewrap with network namespace isolation" where the netns is removed entirely and the only route out is host-side proxies over bind-mounted Unix sockets, with resolved addresses re-checked against loopback and link-local ranges. Claude Code's built-in Bash sandbox is built on the same package: Seatbelt on macOS, "bubblewrap (`bwrap`) and `socat`" on Linux and WSL2. thirdshift built the same thing for Trials before reading any of it.

**What `srt` has already paid for that thirdshift has not.** This is the list worth stealing, and it is the concrete work item behind §7:

- **Mandatory write denies inside writable trees.** `srt` and Claude Code's sandbox both deny `.git/hooks`, `.git/config`, `.gitconfig`, `.gitmodules`, `.mcp.json`, `.claude/commands`, `.claude/agents` and shell startup files even where the enclosing directory is writable, because "a command that could edit those files could grant itself permissions, or add a hook or MCP server that Claude Code runs outside the sandbox". A Run needs exactly this, over the shared `.git` (§5.1).
- **A Linux caveat thirdshift would inherit.** On Linux `srt` "builds the deny list once at launch", covers the project root reliably, makes a best-effort shallow scan for nested repositories, and "does not cover anything the session creates later, such as `git init`, `git clone`, or scaffolding". macOS checks at write time instead. A Run that clones a dependency would slip through on Linux **[interpretation]**.
- **Credential handling as a first-class setting.** `sandbox.credentials` can `deny` a file or variable, or `mask` it — substituting a sentinel inside and letting the proxy inject the real value on allowed hosts. That is a better answer than binding a token in, and it is the shape §5.2 wants.
- **A Unix-socket seccomp filter** (x64 and arm64), because an allowed socket such as `/var/run/docker.sock` "effectively grants access to the host system through the Docker socket".
- **The Ubuntu 24.04 install story, shipped rather than documented.** The release notes say "the Ubuntu kernel now restricts the use of unprivileged user namespaces", and the documented per-binary fix is a profile in `/etc/apparmor.d/` with `flags=(unconfined)` and a `userns,` permission line. The alternative — `kernel.apparmor_restrict_unprivileged_userns=0` — is the one Ubuntu warns about. This host already has the bwrap profile in place ([sandcastle-fit.md §3.2](sandcastle-fit.md)); `thirdshift setup` (#608) should put it there rather than leave the operator to flip a sysctl.

**What has to change to make it a Run sandbox.** The Trial sandbox is deliberately narrow, and each of these widens it:

| Trial today | Run needs | Cost |
|---|---|---|
| The prepared repository only | The worktree **and** the main checkout's `.git`, read-write | The code-execution hole of §5.1 |
| A fresh home with only the login | The real Harness home, or at least the real `auth.json` for Codex's in-place rotation, plus `~/.config/gh` | Harness homes hold every session's history ([eval-sandboxes.md §4](eval-sandboxes.md)) |
| One provider's hosts on the allowlist | Provider hosts **plus** `github.com`, `api.github.com`, crates.io, npm, PyPI, rustup, and whatever the target repository fetches | A much wider allowlist, and `github.com` is the exfiltration path of §2.2 |
| Web search off by each Harness's flag | Web search on, as a Run has it | More egress thirdshift does not see |
| 1,800-second timeout, 1–2 GB caps | Hours, and whatever a build needs | `src/scope/` caps would need Run-sized values |

The widening is real, and it is why this should be opt-in per Run kind rather than switched on everywhere at once. A **Security run**'s proof-of-concept execution is the narrow end: the Security skill already demands "no external network", an allowlisted environment, a read-only toolchain and "explicit low CPU, memory, process, file-size, disk, and wall-clock limits" ([eval-sandboxes.md §2](eval-sandboxes.md) quoting `skills/thirdshift-security-audit/SKILL.md`). A **Ticket run**'s implement session is the wide end.

### 4.2 The Harnesses' own sandboxes, re-checked

ADR-0013 rejected these for two reasons. One has moved; the other has not.

**What moved.** Claude Code now ships a configurable sandbox ([sandboxing](https://code.claude.com/docs/en/sandboxing)): off by default, Seatbelt on macOS and bubblewrap plus socat on Linux and WSL2, with `sandbox.filesystem.allowWrite`/`denyWrite`/`denyRead`/`allowRead`, `sandbox.network.allowedDomains`, `sandbox.credentials`, `sandbox.failIfUnavailable`, `sandbox.allowUnsandboxedCommands` and `sandbox.excludedCommands`. Crucially for thirdshift, the docs list `--settings '{"sandbox": {...}}'` as the way to "Change sandbox settings for one session" — and every factory session on Claude Code already passes `--settings` for attribution, so the mechanism is in place. Codex likewise grew a command network proxy with allowlist-first domain rules, on `bwrap` plus `seccomp` on Linux and Seatbelt on macOS, though its own docs note the proxy "does not filter web search" and that the DNS check "reduces DNS rebinding risk, but it does not eliminate it" ([approvals and security](https://learn.chatgpt.com/docs/agent-approvals-security)).

**What did not move, and settles it.** Three things:

1. **They sandbox commands, not the session.** Claude Code's docs are explicit that built-in file and web tools, hooks, local MCP servers, plugin monitors and LSP servers "run outside it", and that the Bash sandbox "on its own constrains only shell commands, so it is not sufficient for fully unattended runs in either mode". A session that can Edit any readable file is not contained by a Bash sandbox.
2. **Every one of them protects `.git`.** Codex's `workspace-write` keeps `.git` read-only "including gitdir pointers", and its source protects a worktree's `.git` file and the gitdir it points to ([codex-headless-harness.md §3.2](codex-headless-harness.md)). agy's and Grok's sandboxes do the same ([harness-candidates.md](harness-candidates.md)). `srt` and Claude Code's sandbox deny `.git/config` and `.git/hooks` by design. A Run must write that directory. The carve-out that makes these sandboxes safe is the thing that makes them unusable here.
3. **Only two of six have one worth having.** agy has no documented sandbox control, Muse's cannot start on this userland, and OpenCode's is undocumented. A per-Harness answer would cover a third of the Harnesses and behave differently on each.

So the conclusion is the same as ADR-0013's, for a better reason: **the boundary has to be outside the Harness, because the Harness's own boundary is built to exclude exactly what a Run must write.** #398 should survive only as a narrow live check (§7).

### 4.3 Rootless containers, gVisor and microVMs

[eval-sandboxes.md §3.3–§3.7](eval-sandboxes.md) ruled these out for Trials largely on disk and this host's setup. Disk is no longer the reason. These are:

- **Rootless Podman.** Genuinely better than bwrap in two ways: a per-session filesystem from an image, and `podman exec` re-entry into a container whose lifetime is not tied to the launching process. Its rootless pasta default already passes `--no-map-gw` "to avoid direct access from container to host using the gateway address". The costs: `loginctl enable-linger` or detached containers are stopped at logout; `--userns=keep-id` for the shared repo, since "The idmap option is only supported by Podman in rootful mode" and `:U` would chown the real repository recursively; an image per target repository, rebuilt whenever a Harness version changes; resource limits need cgroups v2; and no stronger kernel boundary than bwrap. Checkpoint/restore is out — `rootless.md` says "Checkpoint and restore don't work, because CRIU requires root" — but §1.2 showed thirdshift does not need it.
- **Rootful Docker.** Still out, and not for disk: the docker group is root-equivalent, and every unattended session runs as the factory's user.
- **gVisor.** The right threat model and the wrong workload. Its security page describes a user-space kernel that "implements the System API instead" of passing calls through, with a separate Gofer owning the filesystem. But its performance page says the bad cases are "many small file operations" with "predictably poor results", that the VFS "needs improvement", and that "gVisor may not be an appropriate solution for every workload, for reasons other than performance". A Node agent CLI, `npm install` and `cargo test` are that workload **[interpretation]**. It also "does not pass through specialized APIs" — some ioctls, extended attributes, raw sockets. Linux 5.6+, x86_64 or arm64, **no macOS**. Checkpoint/restore exists via raw `runsc` but is not claimed production-ready.
- **Firecracker.** The only real kernel boundary here, and the worst fit for a Run. "Each Firecracker process encapsulates one and only one microVM"; the jailer needs root; block devices are host files that must already hold a filesystem, so there is **no host directory sharing out of the box** and the shared `.git` would need virtio-fs or a network mount **[unverified]**; it "does no network traffic filtering, so all guest egress is untrusted and must be filtered at the host"; Linux hosts only. Its snapshot support, which looked like the answer to Resume, is not: "Guest network connectivity is not guaranteed to be preserved after resume", and "we consider resuming execution from the same state more than once insecure", with secret state "replicated across multiple microVMs resumed from the same snapshot".
- **Kata Containers 4.3.1.** OCI-compatible, each workload in a lightweight VM with its own kernel, QEMU / Cloud-Hypervisor / Firecracker underneath. It is the right shape if you already run containerd, and thirdshift does not. Its site gives no overhead numbers **[unverified]**.

### 4.4 macOS

macOS is a supported platform ([guide.md](../guide.md#supported-platforms): Tahoe 26.5.2 and later, Apple Silicon), and it gets a weaker boundary. That should be documented, not hidden.

- **Seatbelt is the only option for a native process, and it is deprecated.** The man page on this machine (macOS 26.5.2) reads `sandbox-exec – execute within a sandbox (DEPRECATED)` and directs developers to App Sandbox instead; every named profile constant is marked DEPRECATED too, and the profile language is undocumented by Apple. It has been deprecated for about nine years, still ships, still works, and is what both `srt` and Claude Code use on macOS.
- **App Sandbox is the sanctioned replacement and the wrong shape.** It applies to a signed app bundle through entitlements in its code signature; there is no supported way to apply it to an arbitrary `node` process thirdshift spawns **[unverified from a primary source; Apple's page renders as JavaScript and the Design Guide URL 404s]**.
- **`apple/container` 1.6.1 is real and matches thirdshift's macOS floor.** "Containerization executes each Linux container inside of its own lightweight virtual machine" on Virtualization.framework, consuming and producing OCI images; "You need a Mac with Apple silicon" and "`container` is supported on macOS 26". But it isolates *Linux* workloads: using it means running macOS Runs inside a Linux VM, which changes the execution environment a Run is meant to reproduce.
- **Lima/Colima and Docker Desktop** are the same trade: a Linux VM, with the same consequence.

**So:** on macOS, reuse `srt`'s Seatbelt approach — a generated profile plus egress forced through a localhost proxy — and accept that the macOS boundary is weaker than the Linux one. The alternative is to tell macOS operators their Runs now execute in Linux, which is a different product **[interpretation]**.

## 5. Git, GitHub and credentials

### 5.1 The shared `.git`

This is the part a hosted provider cannot do and a local sandbox must do carefully.

A linked Worktree's `.git` is a file reading `gitdir: /path/main/.git/worktrees/<name>`; `$GIT_COMMON_DIR` points back at `/path/main/.git`; "refs are shared across all worktrees" apart from `refs/bisect`, `refs/worktree` and `refs/rewritten`; objects are shared; and "By default, the repository `config` file is shared across all worktrees" ([git-worktree](https://git-scm.com/docs/git-worktree)). So:

- **A Run cannot commit without write access to `<main>/.git`.** Not just the private `worktrees/<name>` subdirectory: objects and `refs/heads/` live in the common directory.
- **Writable `<main>/.git` is host code execution.** `config` can name a `credential.helper`, a filter driver or `core.fsmonitor`; `hooks/` runs on the next commit in *any* worktree, including the Day shift's own. Sandcastle's container path has this hole open and known ([sandcastle-fit.md](sandcastle-fit.md)). Anthropic's runner docs state the mechanism directly, and add that "Settings in those files can also change where a push goes, whatever remote you name."
- **The mitigation is a deny list inside the bind.** Bind `<main>/.git` read-write, then `--ro-bind` or deny `<main>/.git/config`, `<main>/.git/hooks`, `<main>/.git/info/exclude` and the other worktrees' `worktrees/*` subdirectories. This is what `srt` does and what a Run sandbox must do. Whether bwrap can layer a read-only bind inside a read-write one for every path git needs is **[needs live check]**.
- **`extensions.worktreeConfig`** gives a per-worktree `config.worktree`, which is a possible refinement; it does not remove the shared `config`.
- **The alternative is a clone per sandbox,** with commits coming back as patches the way Sandcastle's remote providers do (`git format-patch` and `git am`). That removes the hole entirely, at the cost of a full clone per Run, losing the shared object store, and putting a deterministic apply step between the agent and the branch. It is the cleanest design and the biggest change; it is also the one change that would make a hosted provider conceivable **[interpretation]**.

### 5.2 Scoping the push credential

The session must hold something that can push. The question is how much that something can do. This is worth doing **whether or not a sandbox ships**, and it is the recommendation's cheapest item.

- **Today** it is the user's `gh` login, which can reach every repository that account can reach.
- **A GitHub App installation token** is the tightest option: it "will expire after 1 hour", and both `repositories`/`repository_ids` and `permissions` can be narrowed at mint time, below what the app itself holds. One minted per Run, scoped to that Run's repository with `contents: write` and `pull_requests: write`, would bound a leak to one repository for one hour.
- **A fine-grained PAT** is second best: "Each token is limited to access resources owned by a single user or organization" and "can be further limited to only access specific repositories", with `expires_in` from 1 to 366 days. But "Tokens always include read-only access to all public repositories on GitHub", which for a factory working on public repositories is most of the exposure anyway.
- **Anthropic's own posture for unattended runners** is the same conclusion from a different direction: "Don't bake long-lived or broadly scoped push credentials into a shared runner image: a credential in the image is available to every session the image runs… Instead, mint a short-lived, least-scoped token per session from your wrapper script… Pair it with an ephemeral per-session container, which requires `--capacity 1`, so no credential outlives the session that minted it." Their hosted path goes further: in Anthropic-hosted cloud sessions "git credentials and signing keys stay outside the sandbox, and a proxy authenticates on the session's behalf with scoped credentials."
- **The proxy-injection variant** is the strongest and the most work: keep the token outside the sandbox entirely and have thirdshift's own CONNECT proxy attach it, which is exactly `sandbox.credentials`' `mask` mode and exactly what Anthropic's GitHub proxy does. It needs TLS termination in `src/proxy.rs`, which Anthropic flags as experimental in their own implementation. Worth recording as the end state, not the first step **[interpretation]**.

### 5.3 ADR-0015 and ADR-0017

- **[ADR-0015](../adr/0015-security-findings-stay-private-until-fixed.md).** A Security run's sessions handle an unfixed vulnerability's write-up. A sandbox helps here more than anywhere else: a Security session needs no access to other repositories, and its proof-of-concept code is attacker-influenced by construction. It also helps *less* than it looks, because the write-up goes to the provider regardless (§2.2), and because `otlp.endpoint` already exports no Security sessions. The one real gain is that a reproduction's code stops being able to read the rest of the machine.
- **[ADR-0017](../adr/0017-pickup-reserves-issues-on-origin.md).** Pickup's reservation push happens in thirdshift's own code, not a session, so it can stay outside the sandbox and keep the full credential. That is a useful split: the deterministic steps hold the strong credential, the session holds a weak one **[interpretation]**.

## 7. Recommendation

**Isolate Runs locally, by reusing the Trial sandbox's launcher, opt-in per Run kind, Security run first. Do not buy a hosted sandbox.** **[interpretation]**

The case in one paragraph: the thing thirdshift would buy from a provider is isolation, and the thing it would pay with is the shared `.git`, the subscription logins and a terms question nobody has answered. It already owns an isolation mechanism that is, independently, the design the vendor ships for this exact problem — and the seam to plug it into Runs is one `Option<Launch>` field that already exists. The honest gain is blast-radius reduction (§2.3), and it is available locally for a fraction of the work.

### 7.1 A staged path

1. **Scope the push credential (no sandbox needed).** Mint a per-Run GitHub App installation token, scoped to that Run's repository and to `contents: write` and `pull_requests: write`, expiring in an hour. Keep the user's `gh` login for thirdshift's own deterministic steps, including the ADR-0017 Pickup reservation. This bounds the worst outcome today and is independent of everything below (§5.2).
2. **Ship the AppArmor profile in Setup.** `thirdshift setup` (#608) should install `/etc/apparmor.d/` with `flags=(unconfined)` and `userns,` for the launcher, rather than leaving the operator to flip `kernel.apparmor_restrict_unprivileged_userns`. This is a prerequisite for every bwrap path and is useful on its own.
3. **Sandbox the Security run's proof-of-concept execution, and fold #726 into it.** This is the narrow end, and the one place the factory already wants a boundary and fights for one by hand: six of eight reviews rebuilt a bwrap invocation by trial and error, and the working recipe lives in an operator memory note (#726). A `thirdshift sandbox -- <cmd>` built on `sandbox::Launch`, with the Security skill's existing isolation requirements as its contract, closes #726 and gives the Run sandbox its first real user. Code Graders already run offline with no network at all, so the proxy work is minimal here.
4. **Add an opt-in Run sandbox for the Architecture review and the Security review, which write least.** An Architecture review runs in a detached worktree and publishes an issue; a Security review reads a diff and writes a report. Neither needs the wide allowlist a build needs. This is where the shared-`.git` deny list (§5.1) gets its live check at low stakes.
5. **Then the implement session, behind a User config setting, default off.** This is the wide end: the full registry allowlist, hours, builds and the writable shared `.git`. It should not be first, and it should not be default until a few hundred Runs have gone through steps 3 and 4.
6. **Only then consider a clone-per-Run design.** If step 5's deny list proves unmaintainable, §5.1's alternative — a clone per sandbox with commits applied back deterministically — is the clean answer, and it is also the only thing that would make a hosted provider conceivable. Revisit #1486 at that point, not before.

### 7.2 What happens to #398 and #726

- **#726 (a tested sandbox runner for Security review PoC execution): fold in.** It is step 3 above, and it should become the first Ticket of this work rather than a separate effort. Its ask — "Provide a supported sandbox runner, either a script or a thirdshift command" with "real namespace availability, toolchain/linker access, certificate access when needed, filesystem mounts, resource limits, and actionable failure diagnostics" — is a description of `sandbox::Prepared` with a Run-shaped request.
- **#398 (a sandboxed mode for Codex sessions): keep, narrowed to a live check, and expect it to close as won't-do.** §4.2 argues the Harnesses' own sandboxes cannot be the boundary, because every one of them protects `.git` as read-only. #398's own open question — "does workspace-write let git write a worktree's `.git` paths, which Codex protects as read-only?" — now has a documented answer: no, the carve-out covers the `.git` file "including gitdir pointers" and the gitdir it points to. The remaining value in #398 is a single live check of whether `--add-dir <main .git>` defeats that carve-out. If it does not, close it and point at this note.
- **#838 stays closed.** Its stated reason — the host had no Docker or Podman — is gone, but §3 gives better reasons, and its own closing comment already routed the useful idea to #398 and #726.
- **#1486 becomes the local work**, with the hosted-provider question answered no and recorded here.

### 7.3 What ADR-0013 would need to change

ADR-0013 should be **amended, not superseded**. Its decision is still right and its flag table is unchanged: every Harness runs with approvals off and its own sandbox off, because the worktree's commits and pushes go through the shared `.git`. What changes is the last sentence of its decision — "The worktree is the only boundary" — and one of its rejected options.

A minimal amendment:

- **Keep** the flag table and the reasoning for it, and add the sharper reason from §4.2: a Harness's own sandbox cannot be the boundary for a Run because every one of them protects `.git` as read-only, which is the directory a Run must write. That is a stronger argument than the AppArmor one, which has a documented fix.
- **Replace** "The worktree is the only boundary" with: the worktree is the only boundary by default, and an opt-in outer sandbox that thirdshift controls may wrap the session without changing its arguments. The Trial sandbox already works this way — `src/sandbox.rs` states "the sandbox wraps the session, it does not change its arguments" — so the amendment describes existing behaviour rather than inventing a new rule.
- **Record** that the AppArmor premise has a fix, and that Setup ships it, so a future reader does not re-derive the 2026 conclusion from a stale fact.
- **Add a consequence:** a session's credentials are inside whatever boundary is used, so credential *scoping* (§5.2), not isolation, is what bounds a credential leak.

## 8. Open questions for the grill

### 8.1 About isolation

0. **Is Vercel's "Herdr" this factory's Herdr?** §3.4. If yes, a hosted-sandbox-per-agent credential model may already be in use on this machine, which changes the baseline this note argues from. Cheapest question here, and it should be answered first.
1. **Which Run kind first?** §7 argues Security run. The counter-argument is that the Security review is the Run kind whose Harness already varies (`security.harness`), so it is the least uniform place to start.
2. **Deny list or clone-per-Run?** §5.1 gives two designs. The deny list keeps the shared object store and leaves a hole to get right; the clone removes the hole and costs a clone per Run plus a patch-apply step. Which one is thirdshift's answer, and is the answer the same for a Security run as for a Ticket run?
3. **How wide is the egress allowlist allowed to get, and who maintains it?** A Run needs the provider, GitHub, and every registry its target repository uses. The Trial allowlist is six hostnames maintained by hand from live checks. A Run allowlist is per-repository and will rot. Does it live in the User config, a per-repository file, or `AGENTS.md`?
4. **Is `github.com` on the allowlist an acceptable exfiltration path?** Both Anthropic pages say it is one. If it is not acceptable, the answer is TLS termination in `src/proxy.rs`, which is a large piece of work.
5. **What happens when the sandbox cannot start?** A Trial becomes void with `sandbox_unavailable`. A Run has no void. Does it fail, or fall back to today's unsandboxed behaviour with a warning? `sandbox.failIfUnavailable` exists precisely because silently running unsandboxed is a trap.
6. **Does macOS get a weaker boundary, or no boundary?** §4.4 says Seatbelt or a Linux VM. A third option is to ship the sandbox on Linux only and say so.
7. **Does the push credential change land first, on its own?** §5.2 needs no sandbox and bounds the worst outcome. It also needs a GitHub App, which is new operational surface.
8. **What does ADR-0013 become?** §7 proposes an amendment. The alternative is a new ADR that supersedes it, which would need to restate the flag table.
9. **Is the `srt` package a dependency or a reference?** Adopting `@anthropic-ai/sandbox-runtime` would add Node to the factory's own runtime, against ADR-0001 and ADR-0003, and it is a "beta research preview" whose "APIs and config formats may change". Reading it as a reference costs nothing. §7 assumes the latter.
10. **How many sandboxed Runs fit on the new host?** `src/resources.rs` checks RAM and load before each session, and the guide already says container quotas are not measured. A per-Run `systemd-run --user --scope` like the Trial's would make this measurable.

### 8.2 Two terms questions this note turned up that are not about isolation

These came out of §3.2 and are worth deciding separately, because they apply to thirdshift today, hosted sandbox or not.

11. **agy and Antigravity's clause 6.** "Using third party software, tools, or services to access the Service … (e.g. using OpenClaw with Antigravity OAuth) is a breach of this Agreement", with suspension or termination named as a consequence ([terms](https://antigravity.google/terms/)). thirdshift spawns the official, unmodified `agy` binary under the user's own login, which is the route [warp-factories-and-alternatives.md §2](warp-factories-and-alternatives.md) calls (a) and which Anthropic's legal page explicitly allows for Claude Code. **Google's terms do not draw that distinction.** Options: read it as not covering the unmodified binary and record the reasoning; move agy to API-key billing; or drop agy as a Harness. This is a decision for the maintainer, not research.
12. **Codex's one-`auth.json`-per-runner rule and `spec.parallel`.** "Use one `auth.json` per runner or per serialized workflow stream. Do not share the same file across concurrent jobs or multiple machines" ([CI/CD auth](https://learn.chatgpt.com/docs/auth/ci-cd-auth)). With `spec.parallel` at 3 and `harness.default = "codex"`, the factory shares one file across up to three concurrent sessions, which [eval-sandboxes.md §4](eval-sandboxes.md) already flagged and attributed to Codex re-reading the file before refreshing on a 401. It works today. Is "it works" the recorded position, or should a Run get a `CODEX_HOME` of its own the way Grok Trials get a Trials home?
