# Experiments against off-the-shelf eval tools: a retrospective build-vs-buy

Research date: 2026-10-27.

**Question.** thirdshift built its own eval system after [#698](https://github.com/JacobStephens2/thirdshift/issues/698): Experiments (#977), the Scoring run (#978) and their roughly thirty Tickets. Five notes surveyed the off-the-shelf tools *before* the build. This note asks the question again now that the code exists: measured against what thirdshift actually shipped, would replacing any part with an off-the-shelf tool be worth it, in whole or in part? It also checks what changed in those tools since the surveys.

**Method.**

- **The prior notes were read first and are cited rather than re-derived:** [eval-tools.md](eval-tools.md) (2026-10-16), [eval-tools-landscape.md](eval-tools-landscape.md) (2026-10-17), [eval-runners.md](eval-runners.md) (2026-10-21, the key prior: promptfoo 0.124.1, Inspect AI 0.3.282, MLflow 3.17.2 and Mira 0.5.0 each read at a pinned commit), [eval-sandboxes.md](eval-sandboxes.md), [eval-viewers.md](eval-viewers.md), and the decisions in [`698-evals/settled.md`](../grill-with-docs/done/698-evals/settled.md). Where a fact about an outside tool is unchanged since 2026-10-21, this note cites that note's pinned-commit source instead of repeating the link trail.
- **thirdshift was read at `1df25aea` on the `evals` branch** (`main` merged 2026-10-27): `docs/guide.md`, [`docs/trial.md`](../trial.md), [`docs/eval-tasks.md`](../eval-tasks.md), `GLOSSARY.md`, `src/evals*`, `src/trial*`, `src/scoring*`, `src/verdict*`, `src/sandbox*`, `src/proxy.rs`, `src/scope*`, `src/console/experiments*`, `scripts/release.sh`, and `tests/`. Sizes are `wc -l`; the cost figures are `git log --numstat` over 2026-10-21..27.
- **Outside tools were checked live on 2026-10-27** against official documentation sites, GitHub release and tag pages, npm and PyPI registry metadata, and — for Harbor's auth handling, Inspect's CLI commands and MLflow's docs — source files read in the repositories. `claude plugin eval` was additionally checked against `claude plugin eval --help` from the installed CLI (2.1.311). Where a tool's source was read rather than its docs, the note says so.
- **Two of the three §5 corrections came from re-checking a prior note's conclusion against a different surface** (MLflow's API rather than its UI; Harbor's source rather than its README). Where this note and a prior note disagree, this note says which surface each read.
- Nothing was installed or run except the local `claude` CLI's help. **[interpretation]** marks a judgment; **[unverified]** marks something no primary source settled.

**Out of scope.** Statistical power (tasks versus Trials), synthetic bug injection and contamination are the subject of the concurrent [eval-suite-scaling.md](eval-suite-scaling.md); this note only flags, in one line each, where a tool happens to ship a relevant feature. New Eval suites, the implement suite and the plan-check suite are out of scope too, as is anything about Security sessions beyond [ADR-0015](../adr/0015-security-findings-stay-private-until-fixed.md)'s constraint.

## TL;DR

- **Keep it. Replace nothing.** The shipped Experiments and Scoring code is 13,248 non-test lines plus 8,565 lines of integration tests, built in six days over 139 commits and about thirty Tickets. Almost all of it is in components no off-the-shelf tool offers. Replacing the commodity remainder would remove perhaps 2,000–3,000 lines and add a second language, a package tree and glue of about the same size. (§1, §4, §7)
- **The pre-build estimate was five to eight times too small, and it was too small in the right direction.** [eval-runners.md](eval-runners.md) put every option at 1,500–3,100 lines. The overrun sits in the sandbox and proxy (3,072), the scopes (685), the Scoring run (2,034), the Console pages (1,363) and, inside `src/evals/`, the resume, checkpoint, pause, void-cause and recheck bookkeeping — parts no candidate covered. The framework comparison compared the wrong fifth of the problem. (§1.2)
- **More changed in the tools than expected, and four facts in the prior notes are now wrong** — none of them enough to flip the answer, but they matter. (§5)
  1. **Subscription login is no longer rare.** Three tools document it: `claude plugin eval`, promptfoo's `anthropic:claude-agent-sdk` (via `apiKeyRequired: false`) and `openai:codex-sdk`, and Harbor's `claude-code` (via `CLAUDE_FORCE_OAUTH` and `claude setup-token` — thirdshift's own mechanism) and `codex`. **All of them cover Claude and Codex only**, and all drive the vendor SDK rather than thirdshift's session code.
  2. **A paired comparison with a gate now exists off the shelf.** MLflow 3.17's `compare_evaluations` pairs rows across two runs and reports a BCa bootstrap CI of the mean difference, a p-value, **McNemar's test**, Wilcoxon signed-rank, a paired t-test and Cohen's d_z, with `assert_improved` gating. `eval-runners.md §5.3` said MLflow had no paired statistic; it read the UI, and this is an API.
  3. **ATIF is real**: an Active RFC with MUST/MAY language, a validator and golden fixtures, explicitly for external producers. This note's first draft called it unverified.
  4. **Inspect Scout exists** (MIT, 0.6.1) and was in no prior note. It already imports Claude Code session files and Harbor ATIF, and `scout db schema` publishes its transcript schema in JSON Schema, Avro and PyArrow **explicitly for writers outside Python** — the only such format in the field, and the only one that carries Scores.
- **Version bumps, for the record:** Inspect AI 0.3.282 → 0.3.285 (one breaking change, three log-format fixes in one release, **still no significance test and no power analysis, which its docs state**); promptfoo 0.124.1 → 0.125.1; Harbor 0.25.0; Terminal-Bench v4.0.0. OpenAI's hosted Evals shuts down 2026-11-30 with promptfoo as the migration target, and **METR's task-standard and vivaria were both archived 2026-10-07**, redirecting to Inspect.
- **`claude plugin eval` is the genuinely new *option*, and it is for a different job.** Native two-arm ablation with a delta, `runs` per case, a bubblewrap-and-socat sandbox with granted domains, six grader types, documented CI exit codes. But `claude -p` only, no Effort axis, no custom-code graders, no blinding across Arms, no interval or Bar, no void model, no resume, no time-safe repository. Worth knowing if thirdshift ever ships a plugin; not a replacement for any Experiments part. (§2)
- **Blinding is thirdshift's single strongest differentiator, and that is now a checked claim.** Across Inspect, promptfoo, Harbor, MLflow, Braintrust, LangSmith and Weave, **no tool documents hiding which system produced an output.** Every "blind review" feature in the field is *peer* blinding — hiding other reviewers' scores. LangSmith's pairwise queues come closest in shape, with fixed left/right positions and no documented randomisation. The field's own recommended workaround is what thirdshift already does. (§5.4)
- **Differentiating** (nothing off the shelf does these): time-safe repositories, the **six**-Harness subscription Trial protocol, the bwrap sandbox with its pre-DNS allowlisting proxy (no eval tool has a bwrap backend), per-Trial memory scopes, blind packets, the fixed void-cause list, the Bar as a *pre-registered* object, rechecks of decisive Scores, dependency-based suite selection, the release gate, the Scoring run, and Bug origins. (§4.1)
- **Commodity** (where any saving would come from): Trial scheduling, resume, `pass_cubed`, descriptive and agreement statistics, the Experiments pages, a log schema, case authoring. Inspect covers most of it natively. The catch is that swapping it in moves the retries, caches, timeouts and resume rules — the documented sources of silent inaccuracy — outside the Bar's guarantee. `inspect_swe`'s `_BRIDGE_SAFE_ENV` table, which disables five Claude Code client-side watchdogs, is the field's own evidence that this risk is real. (§4.2, §4.3)
- **Interop is already mostly done.** `thirdshift logs <command> --export <dir>` writes the Experiment's whole Trace, Trial and Grader sessions included, as OTLP JSON Lines, so any OTLP consumer reads the trajectories today — and OTLP/HTTP ingest is universal across MLflow, Braintrust, LangSmith and Weave. What it does not carry is the Scores and the Verdict. There is also **no trajectory standard outside ATIF**: OpenTelemetry's GenAI conventions are still Status Development with no releases and define no trajectory document. (§6.1)
- **Three things to do.** (a) Adopt a hard cost ceiling in the Bar, borrowed from `claude plugin eval --max-cost-usd` — the only feature in the comparison that a tool has and thirdshift lacks. (b) Write a versioned output-format document for the per-Trial result, the Score with its recheck history and the Verdict, the way `docs/trial.md` versions the Trial protocol. (c) Cross-check a finished Experiment's Verdict against MLflow's McNemar and bootstrap CI in a throwaway script — the strongest available validation of 150 lines of statistics with no reference implementation. Decline `.eval` log writing, Docker/image-based harnesses and every hosted platform. (§6.2, §6.3, §7)
- **Update 2026-10-27: disk is no longer a constraint.** The Day shift can provide a bigger host with room for container images. That meets §8's first trigger, without changing the main answer. It changes three narrower ones: the implement suite, container sandboxes, and a re-check of Harbor. See §8.1.
- **What would change the answer:** more disk (not Docker specifically — Harbor runs on podman and singularity, but its tasks still need images); **Harbor wiring its `resolve_auth_file` helper through `grok-build` and `opencode`**, which would take it from two of six Harnesses to four — the most watchable change in the field; `claude plugin eval` growing `--agent` or an effort axis; an Inspect scorer that can see two Arms at once; a concrete outside consumer of Experiment results; eval maintenance outgrowing factory capacity; a second maintainer; or AISI's `hibayes`/`optstop` getting real releases. (§8)

## 1. What was built, and what it cost

### 1.1 The parts

From `docs/guide.md`, [`docs/trial.md`](../trial.md), [`docs/eval-tasks.md`](../eval-tasks.md) and the modules themselves:

- **Eval suites and Eval tasks.** TOML manifests under `~/.thirdshift/evals/suites/<suite>/`, format 1, with a per-suite `trials_per_arm` and five declared dependency categories (Factory skills, Session prompts, Harness, Model and Effort defaults). Code review (3 Trials) and Spec review (1 Trial) exist; #429's material is imported by `thirdshift evals import-replays`.
- **Time-safe repositories.** `evals prepare` builds a throwaway repository holding only base history, applies the change under review without its commit objects, and gives Spec-review Eval tasks a local bare origin. `evals verify` refuses history beyond the base commit.
- **Arms.** `evals prepare-arms` caches a release build per commit under `~/.thirdshift/evals/builds/`, and records each Arm's commit, binary, and the Harness's *real path and version*, so a symlink update cannot change the Harness between Arms. An Arm is a thirdshift build (with its embedded Factory skills) plus Harness, Model and Effort.
- **The Trial protocol.** `thirdshift --trial <request.json>`, version 1, a hidden flag that runs one session through the same session code a Run uses and prints one JSON line. Both Arms' builds must support it.
- **The sandbox.** bwrap with its own PID and network namespaces, a fresh home holding only the login and the four read-only user-level instruction files, the pinned Rust toolchain provisioned before the session, and an allowlisting CONNECT proxy on a Unix socket outside the sandbox that checks the allowlist *before* DNS and refuses names resolving to loopback or the host's own addresses (`src/proxy.rs`, `src/sandbox.rs`).
- **Memory.** Each Trial and each Grader runs in its own `systemd-run --user --scope` with the `[trial]` caps and a maximised `oom_score_adj`, so it dies before the factory (`src/scope/`).
- **Graders.** Code Graders first, offline, on a private copy of the prepared repository captured before the session; a `repository_changed` void rule. Then one blind packet per Eval task to a fresh model Grader: every Trial's reports with shuffled neutral labels and the Harness, Model, Effort and Arm lines removed, graded in the same sandbox on a Model from neither Arm when one is installed.
- **Void Trials.** A fixed cause list (sandbox failure, provider connection or login failure, provider server error before work, provider capacity or overload, plan-limit stop, host kill or the Trial-only memory cap), up to two fresh retries, and a drop-out rule: a task void in either Arm leaves both, and more than a tenth dropped makes the Verdict inconclusive.
- **Plan-limit pausing.** Claude's warning and rejection events and Codex quota reports at 85% pause scheduling immediately; the Experiment supervises Session traces with the *current* detectors even when an Arm's build predates them.
- **The Verdict and the Bar.** A paired Bayesian Dirichlet interval per suite with a pre-registered Bar: margin `-0.10`, credible level `0.95`, prior `1`, seed `0`, 20,000 draws, Trials per Eval task, an 1800-second per-Trial timeout and the void-retry count. A changed Bar is refused after the first Trial. `pass_cubed` for three-Trial suites. `verdict/prediction.rs` answers "how many more Eval tasks".
- **Rechecks.** The Verdict stays `waiting_on_rechecks` until the Day shift has rechecked every borderline Score and every *decisive* Score — one whose flip would change the decision under the fixed Bar. `thirdshift recheck` appends to a Score's history, never reruns a Trial, and recalculates atomically.
- **Dependency-based selection and the release gate.** `evals touched <path>...` selects suites from the manifests' declarations. `thirdshift experiment --release <commit>` takes the last reachable `v<version>` tag as Baseline and the touched suites; `scripts/release.sh --with-experiment` starts it and waits, with `release_skip` reasons (`no_suites`, `baseline_without_trial`).
- **The Scoring run.** `thirdshift score`: weekly windows over merged pull requests carrying the Built-with marker, a seeded random sample across Harness/Model pairs, packets with attribution and Generated-with lines stripped and no commit messages, five independent pass/fail criteria (Correct, Scoped, Tested, Honest, Standards), human scoring that must be entered before the model's Scores are revealed, a rolling 18-of-20 calibration per criterion, and Bug origins proposed for each closed bug.
- **The Console.** An Experiments list and page (`src/console/experiments/`), which renders the suite intervals, the Bar, each Arm's builds, a plain-words "What it tests" section, proposed Eval task approval, and the Experiment's Trace through the shared Command machinery.
- **Interop that already exists.** `thirdshift logs <command> --export <dir>` writes the whole Command Trace as OTLP JSON Lines (`spans.jsonl`, `logs.jsonl`), and Trial and model Grader Session traces and code Grader spans join the Experiment invocation's Trace. `otlp.endpoint` streams ended spans live. `thirdshift experiments <id> --json` is the Experiment's own machine-readable view.

## 2. `claude plugin eval`: the one genuinely new option

This is the clearest change since the prior notes. [eval-tools-landscape.md §2.1](eval-tools-landscape.md) screened it as a "strong narrow skill/plugin option" with no public docs page; there is now a full one.

Verified on 2026-10-27 against [the plugin-evals docs](https://code.claude.com/docs/en/plugin-evals), [the plugin CLI reference](https://code.claude.com/docs/en/plugins/cli-reference), [`measure.md`](https://code.claude.com/docs/en/plugins/measure) and [the changelog](https://code.claude.com/docs/en/changelog), plus `claude plugin eval --help` from the installed CLI 2.1.311.

**What it covers that thirdshift also has:**

- **Arms, natively.** `--ablation with-without` runs a no-plugin baseline arm and reports `WITH`, `W/OUT` and `Δ`. Graders marked `arm: with-only` (including `tool_used: Skill`) become indicators rather than part of the score. That is the same shape as a Baseline arm and a Candidate arm, for one axis.
- **Trials per task.** `runs` per case, default 3, range 1–50, with `--runs` to override. Each is a separate `claude -p` child.
- **Subscription auth.** "The same authentication and model provider your normal Claude Code sessions use" — no API key needed. It is not alone in this any more (§5.2 and §5.3 below), but it is the only one where the agent under test *is* the tool's own harness, so there is nothing to wire up.
- **A sandbox with no Docker.** Each run gets a temporary home, working directory and Claude Code configuration; user settings, hooks, `CLAUDE.md`, MCP servers, other plugins and memory are absent, most of the environment is withheld, runs never prompt, and only read-only tools run unless `--allow-tools` grants more. When `Bash` is granted it runs under Claude Code's OS-level sandbox, writes confined to the workspace and network limited to granted domains. On Linux it needs `bubblewrap` and `socat` — the same two dependencies `src/sandbox.rs` and `src/proxy.rs` use.
- **Model and code Graders.** Four deterministic grader types (`regex`, `tool_used`, `tool_order`, `file_exists`) and two model-graded ones (`llm`, which needs 2 of 3 judge votes, and `baseline`, which compares to a reference transcript). `--judge-model` picks the judge.
- **A CI gate.** Exit 0 passes, 1 means a case below `--threshold` (default 1.0) or a load/start/API failure, 2 a partial run from `--max-cost-usd` or a rejected credential, 130 interrupted, 143 terminated. `--max-cost-usd` is a hard ceiling checked before each run launches.
- **A viewer and a stable-ish report.** `aggregate-result.json` with `schemaVersion: 1`, camelCase, documented as additive ("write your script to ignore fields it doesn't recognize"), plus a self-contained `report.html` with no external requests. Note that the report is published as a private claude.ai artifact by default where the account allows it; `--no-publish` keeps it local, which [`settled.md`](../grill-with-docs/done/698-evals/settled.md)'s "nothing leaves the host but the sessions" would require.

**Where it cannot reach thirdshift's requirements:**

- **Claude Code only.** The runner is `claude -p`. codex, agy, grok, muse and opencode are not supported, and no matrix runner is documented. thirdshift's Arms span six Harnesses.
- **No Effort axis.** No `--effort` option appears in the help. A Model × Effort matrix is undocumented **[unverified]**; it would mean one invocation per cell and your own aggregation.
- **No custom-code graders.** The docs say so explicitly. thirdshift's Code Graders run the Eval task's mechanical checks on a private pre-session copy of the repository; `file_exists` and `regex` cannot express that.
- **No blinding across Arms.** Graders see one run's output. There is no packet holding both Arms' Trials with shuffled neutral labels, which is the whole point of thirdshift's model Grader.
- **No statistics.** Mean score, mean Δ, threshold pass/fail and "Perfect runs" (the share of with-plugin runs where every grader passed — the analogue of `pass_cubed`). No interval, no paired test, no pre-registered Bar. Not documented as absent, so treat it as unverified absence rather than confirmed absence.
- **No time-safe repository.** `context.scaffold_script` runs author-supplied bash as you (only under `--scaffold`, minimal environment, 120-second limit) and the docs say it may create "fixture files or a git repository". A script could check out a pinned commit, but that is an inference from the docs, not a documented recipe **[unverified]**, and nothing checks that later history was scrubbed the way `evals verify` does.
- **No void-Trial model.** Since 2.1.299 a run ending on an API error scores 0 without grading and the command exits 1. thirdshift calls that void and re-runs it; scoring it 0 would bias an Arm.
- **No resume.** No equivalent of pausing at a plan-limit warning and continuing the same Experiment later.

**[interpretation] Verdict on it:** it is the right tool for a *different* job — checking a single Claude plugin or skill before shipping it — and it is worth knowing about if thirdshift ever publishes a plugin. It is not a replacement for any Experiments component, because it fixes the one axis (Harness) that thirdshift most needs to vary, and it has no Verdict.

*One source conflict, resolved:* a second verification pass concluded `claude plugin eval` "does not appear to exist", on the grounds that `anthropics/claude-code`'s `CHANGELOG.md` contains no occurrence of "eval". That is a false negative from grepping the public repo's changelog. The feature is documented at the URLs above and `claude plugin eval --help` ran locally against CLI 2.1.311, with the output quoted in this note's working material. Take the docs and the CLI as authoritative. Its one clearly transferable idea is `--max-cost-usd`: a hard budget ceiling checked before each run launches, which an Experiment does not have.

| **Dependency-based suite selection** | none | no | Both the manifests' five dependency categories and `evals touched` are thirdshift's. |
| **Release gate** | `claude plugin eval` `--threshold` + exit codes | partly | A gate on a mean, not on a paired interval against the last release tag, and no suite selection. |
| **Scoring run on production pull requests** | Langfuse / Braintrust / LangSmith / MLflow production scoring + annotation queues | partly | The platform shape exists; the attribution stripping, human-first reveal and 18-of-20 calibration do not, and ADR-0015 keeps the data local. |
| **Bug origins** | none | no | No eval tool traces a bug to the pull request and Run that introduced it. |
| **Console Experiments page** | `inspect view`; Phoenix compare view; `report.html` | partly | [eval-viewers.md](eval-viewers.md): Phoenix's compare view is the nearest, and no viewer computes the Verdict. |
| **Trajectory export** | OTLP | covers | Already shipped (§6.1). |
| **Hard cost ceiling** | `claude plugin eval --max-cost-usd` | — | thirdshift has a per-Trial timeout, not a budget. The only feature in this table thirdshift lacks and a tool has. |

## 4. Commodity versus differentiating

Sorting the components by whether an off-the-shelf tool could plausibly take them over. **[interpretation]** throughout.

### 4.1 Differentiating: nothing off the shelf does these

- **Time-safe Eval task repositories.** Base-history-only clones, the change applied without its commit objects, `evals verify` refusing later history, a local bare origin for Spec review. The nearest equivalent is SWE-bench's history scrub, which [eval-sandboxes.md](eval-sandboxes.md) already recommended copying and which thirdshift did. No runner offers it as a feature.
- **Subscription Harness CLIs across *six* Harnesses.** This is narrower than the prior notes implied but still decisive. Three tools now document subscription login — `claude plugin eval`, promptfoo's `anthropic:claude-agent-sdk` and `openai:codex-sdk`, Harbor's `claude-code` and `codex` (§5.2, §5.3) — and every one of them covers Claude and Codex only. None covers agy, grok, muse or opencode, and all drive the vendor SDK or CLI their own way rather than thirdshift's session code, which [`settled.md`](../grill-with-docs/done/698-evals/settled.md) (Q2.4) requires. Inspect's `inspect_swe`, the closest thing in the field, routes model calls through Inspect's own API-key providers by design.
- **The Verdict and the Bar.** A paired Dirichlet interval over each Eval task's difference, with a Bar recorded before the first Trial and refused if it changes, pass and fail judged at their own credible levels, and a prediction of how many more Eval tasks would settle an inconclusive result. **Partly eroded:** MLflow's `compare_evaluations` is a genuine paired comparison with a gate (§5.6), and AISI's `hibayes` is hierarchical Bayesian. What remains unique is the *combination* — Bayesian, pre-registered, with a margin and separate pass and fail levels, refused if changed mid-Experiment, and reporting how many more Eval tasks would settle it. Nothing off the shelf has the notion of a pre-registered Bar at all.
- **Blind packets spanning both Arms.** [eval-runners.md §1](eval-runners.md) found no candidate that groups two Arms' Trials and all their repeats into one grading call, and §5.4 now confirms the stronger claim across the whole field: **no tool documents hiding which system produced an output.** Every "blind review" feature found is peer blinding. LangSmith's pairwise queues are the closest shape and use fixed left/right positions with no documented randomisation. This is thirdshift's single strongest differentiator.
- **Void Trials with a fixed cause list.** [eval-sandboxes.md §7.5](eval-sandboxes.md) showed the field disagrees: Phoenix's `infra_ok` is 0 for any recorded exception but keeps the reward, Harbor counts such trials as 0, SWE-bench flags them but keeps them in the denominator. thirdshift's rules are fixed with the Bar and the Trial is re-run and excluded. Adopting any tool's default here would quietly change verdicts.
- **The release gate.** `scripts/release.sh --with-experiment` plus `experiment --release`, dependency-based suite selection and the `release_skip` reasons. `claude plugin eval` has a threshold and exit codes, which is a gate on one suite's mean, not a gate on a paired interval against the last release.
- **The Scoring run.** Weekly production sampling, attribution stripping so the Grader cannot tell which Harness built the pull request, the human-first reveal rule, and the rolling 18-of-20 per-criterion calibration. Hosted platforms have annotation queues; none of them has the reveal rule or per-criterion calibration, and ADR-0015 keeps the data local anyway.
- **The sandbox and proxy.** Not because no sandbox exists, but because the requirements are peculiar: no Docker, a small disk, the real login file bound in place (Codex rotates `auth.json` in place, so a copy strands the factory's token — [eval-sandboxes.md §4](eval-sandboxes.md), and Harbor's Codex agent copies it), an allowlist checked before DNS, and six Harness binaries. §5.5 confirms no eval tool has a bwrap backend, Inspect's `local` provider is "no sandbox at all", and Harbor's tasks need Docker *images* whatever runtime runs them.

### 4.2 Commodity: an off-the-shelf tool could do these about as well

- **Scheduling Trials.** Two workers alternating Arms, a per-Trial timeout, one result file per finished Trial. Inspect's epochs, `max_samples` and `concurrency(name, n)` cover it; so does promptfoo's `--repeat` with `-j 2`.
- **Resume after a stop.** Inspect's `eval-retry` keeps completed samples and re-runs those in flight; `inspect ctl task drain` lets running samples finish. thirdshift wrote its own checkpoint, pause and resume logic, and the Tickets kept amending it (#1360, #1362).
- **pass^k.** Inspect's reducers include `pass_at_k`, `pass_k_k` and `at_least_k`; `pass_cubed` is `pass_k_k` with k=3.
- **Descriptive and agreement statistics.** Inspect's `stderr(cluster=)`, `bootstrap_stderr`, `ci`, `ci_wilson` and `krippendorff_alpha`. Not the Verdict's paired interval, but these come free there — and `krippendorff_alpha` is a better-founded Grader-calibration statistic than the Scoring run's 18-of-20 rule.
- **A trial viewer.** `inspect view` is loopback-only, has no analytics and can be bundled as a static site; `claude plugin eval`'s `report.html` is self-contained. The Console's Experiments pages (1,363 lines) are the part most plausibly replaceable, and [eval-viewers.md](eval-viewers.md) already found that no viewer computes the Verdict, so a viewer would show numbers thirdshift computes either way.
- **A log/report schema.** Inspect publishes a JSON Schema (`inspect log schema`); `claude plugin eval` documents an additive `schemaVersion: 1`. thirdshift's own `experiments --json` and per-Trial result files are undocumented outside `docs/eval-tasks.md` and the guide.
- **Case authoring.** `claude plugin eval init` runs an authoring interview; promptfoo has a config schema and generators. thirdshift's Eval tasks are authored by hand or proposed from a confirmed Bug origin.

### 4.3 The asymmetry

Every differentiating item is load-bearing for the verdict's honesty, and every commodity item is bookkeeping. That is the same split [eval-runners.md §1](eval-runners.md) predicted, and the build confirmed it. What the build *also* showed is that the bookkeeping is a much larger fraction of the code than estimated — resume, checkpointing, pausing, void causes and recheck recalculation are most of `src/evals/`. So the commodity side is where any real saving would have to come from, and it is exactly where swapping in a framework would move the accuracy-critical defaults (retries, caches, timeouts, resume rules) outside thirdshift's control. **[interpretation]**

## 5. What changed in the tools since 2026-10-21

Checked live on 2026-10-27. **More changed than expected, and four prior-note facts needed correcting. The build-vs-buy answer does not change, but three specific claims in the earlier notes are now wrong.**

The four corrections first, because they matter more than the version bumps:

1. **Subscription login is no longer unique to `claude plugin eval`** (§5.2, §5.3). Three tools document it — for Claude and Codex only.
2. **A paired comparison with a gate now exists off the shelf**: MLflow's `compare_evaluations` (§5.6). [eval-runners.md §5.3](eval-runners.md) found no paired statistic in MLflow; it looked at the UI, and this is an API.
3. **ATIF is a real, RFC-specified trajectory format documented for external producers** (§5.3), not the unverified acronym this note first recorded.
4. **Inspect Scout exists and publishes a machine-readable schema explicitly for external writers** (§5.7). It was in none of the prior notes and is the best interop target in the field (§6.2).

### 5.1 Inspect AI

- **Inspect AI: 0.3.282 → 0.3.285** (0.3.285 released 2026-10-25, [CHANGELOG](https://raw.githubusercontent.com/UKGovernmentBEIS/inspect_ai/main/CHANGELOG.md); 0.3.285 is PyPI's latest, [PyPI JSON](https://pypi.org/pypi/inspect-ai/json)). Three releases in six days, confirming the two-or-three-a-week cadence [eval-runners.md §4.6](eval-runners.md) recorded.
  - **One breaking change** in 0.3.283: "dataset loaders now read a top-level `checkpoint` field as the sample's checkpoint configuration", and "Dataset records can no longer set the checkpoint trigger."
  - **A behaviour change** in 0.3.284: "Docker sandboxes now block writable host mounts by default."
  - **Three log-format bug fixes** in 0.3.284 alone: floats in `.json` headers saved as strings after tag edits, valid `.eval` logs failing to open with `struct.error` or "Corrupt ZIP64 structure", and a dtype change in `score_to_float()`. Relevant to §6.2: the log format is still being repaired under its readers.
  - **Agent bridge** gained recorded host tool calls in the transcript (0.3.283). Still a bridge for an agent that Inspect's own model providers serve, not a way to drive a subscription CLI.
  - **No paired comparison and no Bayesian statistics** in these three releases, and none in the package at all: [the metrics page](https://inspect.aisi.org.uk/metrics.html) documents `stderr()`, `std()`, `var()`, `bootstrap_stderr()`, clustered standard errors via `stderr(cluster=)`, `ci()` (Student-t by default, bootstrap optional), **`ci_wilson()`**, `grouped()`, `pass_at_k`/`pass_k_k`, and **`krippendorff_alpha()`** for inter-rater agreement across judges — but no significance test of any kind and no power analysis, which the docs state. The Verdict's gap is unchanged. `krippendorff_alpha` is, however, a better-founded calibration statistic than the Scoring run's 18-of-20 rule, and worth a look.
  - **Blinding: confirmed absent.** A code search for `blind`/`anonymi` across the repository returns no feature.
  - **No official CI gate.** `eval_set()` returns whether all tasks *completed*, not whether they met a threshold.
  - **Two AISI statistics packages that were in none of the prior notes**, both MIT, both reading Inspect logs, both **GitHub-only with no tagged releases or PyPI presence**: [`hibayes`](https://ukgovernmentbeis.github.io/hibayes/) (hierarchical Bayesian modelling for eval statistics; reference implementation for HiBayES, arXiv:2505.05602) and [`optstop`](https://github.com/UKGovernmentBEIS/optstop) (Bayesian optimal stopping for LLM evals, arXiv:2608.14425, with **convergence projection that estimates the additional trials needed when an eval ends before convergence** — the same question `src/verdict/prediction.rs` answers, and relevant to the concurrent scaling note).
- **`inspect_swe` 0.2.72 (2026-10-20, MIT)** is the Inspect-native coding-agent-CLI driver, shipping `claude_code()`, `codex_cli()`, `gemini_cli()`, `kimi_code()`, `opencode()` and `mini_swe_agent()` as Inspect agents, all built on `sandbox_agent_bridge()` ([repo](https://github.com/meridianlabs-ai/inspect_swe)). This is the closest thing in the field to what thirdshift does, and it still does not fit: the bridge's purpose is to intercept and re-route the agent's model calls through Inspect's own providers, which means **Inspect holds the API keys**. There is no documented path for a bridged agent to keep its own subscription login, and `transparent_proxy` (added 0.2.71) governs generation parameters, not auth. Every documented example uses `sandbox="docker"`; whether `sandbox="local"` works is **[unverified]**.
  - **Worth stealing regardless:** its `_BRIDGE_SAFE_ENV` table disables five Claude Code client-side retry and idle watchdogs (`API_FORCE_IDLE_TIMEOUT`, `API_TIMEOUT_MS`, `CLAUDE_ENABLE_STREAM_WATCHDOG`, `CLAUDE_ENABLE_BYTE_WATCHDOG`, `CLAUDE_CODE_MCP_TOOL_IDLE_TIMEOUT`) plus `DISABLE_AUTOUPDATER=1` and `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1`, with a comment per entry naming the failure each prevents. Relevant to Trial honesty: these are exactly the client-side retries that would turn one Trial into several silently.
  - Its **`human_cli()`** human-agent support (Inspect's, inherited) records terminal sessions by default via `script` and plays them back in the viewer (asciicast playback 0.3.284, Terminals tab 0.3.285). thirdshift has no human-baseline notion; if one is ever wanted, this is the prior art.

It also sets `metadata.usageAccounting='unavailable'` and fails cost assertions rather than treating unknown cost as zero, a good honesty default.

- **[`agent-rubric`](https://www.promptfoo.dev/docs/configuration/expected-outputs/model-graded/agent-rubric/)** is the most interesting grader in the field: an agentic `llm-rubric` where the grader itself is a coding agent gathering evidence with its own tools and workspace, restricted to the coding-agent providers. It keeps grading on the same subscription credentials, with no API key. Conceptually what thirdshift's model Grader does.

Its docs are explicit that "workspaces are not a sandbox". It has a CI gate (exit code 100 plus a GitHub Action) and human cell-grading in its local viewer, but no blinding and no significance testing.

### 5.3 Harbor and Terminal-Bench

- **Everything moved out of `laude-institute`**: `laude-institute/terminal-bench` redirects to `harbor-framework/terminal-bench-1` (frozen), and the live repos are [`harbor-framework/harbor`](https://github.com/harbor-framework/harbor) and `harbor-framework/terminal-bench`. The old `terminal-bench` PyPI package stopped at 0.2.18 (2025-09-26); treat the `tb` CLI as abandoned. Terminal-Bench is now a continuous benchmark, **v4.0.0 (2026-08-26)**, consumed as a dataset: `harbor run -d terminal-bench/terminal-bench@latest`.
- **Harbor 0.25.0 (2026-10-25)**, Apache-2.0, Python ≥3.12, monthly-ish cadence.
- **Docker is the default, not mandatory** ([installation](https://docs.harborframework.com/getting-started/installation.md), [sandboxes](https://docs.harborframework.com/sandboxes/pre-integrated-sandboxes.md)): local runtimes are `docker`, `podman`, `apple-container`, `singularity` and `sbx`. But **podman's `preflight()` unconditionally requires a compose frontend**, and — the decisive point — **tasks define their environment as a Dockerfile or `docker_image` regardless of runtime**, so image pulls and builds are unavoidable and the `.sif` conversion cache is additional disk. **No bwrap backend exists**; the `BaseEnvironment` seam where one would live is documented, with a ~65 KB base class.
- **It drives arbitrary CLIs as the normal case.** `BaseInstalledAgent` installs and runs your CLI inside the task container in a ~30-line subclass, and **43 agents ship pre-integrated**, including `claude-code`, `codex`, `grok-build`, `opencode` and `muse-code`.
- **Subscription login is supported for two of thirdshift's six**, verified in source rather than docs: `codex.py` resolves `CODEX_AUTH_JSON_PATH` or `CODEX_FORCE_AUTH_JSON` and uploads `auth.json` into the sandbox chowned and `chmod 600`; `claude_code.py`'s `_should_force_oauth()` drops the API key under `CLAUDE_FORCE_OAUTH` so the CLI uses `CLAUDE_CODE_OAUTH_TOKEN`, with error text naming `claude setup-token` — the exact mechanism [`settled.md`](../grill-with-docs/done/698-evals/settled.md) (Q3.6) chose. **But `grok_build.py` and `opencode.py` have no subscription path**, and this is credential-file *upload into a sandbox*, not an interactive login. Note also that Codex's `auth.json` handling here copies the file — the rotation hazard [eval-sandboxes.md §4](eval-sandboxes.md) warned about.
- **ATIF is real** and this note's first draft was wrong to call it unverified. [The docs page](https://docs.harborframework.com/agents/atif.md) defines the Agent Trajectory Interchange Format, and [RFC 0001](https://github.com/harbor-framework/harbor/blob/main/rfcs/0001-trajectory-format.md) is an Active, 683-line specification with RFC2119 MUST/MAY language, written to unify MiniSweAgent and OpenHands structures "for debugging, visualization, SFT, and RL pipelines" — **explicitly a cross-tool format for external producers.** It ships Pydantic models, a standalone validator (`python -m harbor.utils.trajectory_validator`) and golden fixtures. Caveats: the docs page says v1.7 while the RFC header says v1.8, governance is single-vendor, and Harbor's models reject undeclared fields (extras go in `extra`).
- **Scoring is a numeric reward file** (`/logs/verifier/reward.txt` or `.json`), statistics are **mean only**, there is no human review UI, no blinding, and CI integration is **[unverified]** beyond `harbor lint` and `--dry-run`. Its viewer (`harbor view`) is fully local on 127.0.0.1. There is a telemetry page that was **not read** — check the opt-out before any trial.
- **So [eval-sandboxes.md §6](eval-sandboxes.md)'s conclusion stands,** but for a sharper reason than "needs Docker": it needs *images*, which this host has no disk for, and it covers two of six Harnesses on subscription.

### 5.4 Blinding across the whole field

Worth stating plainly because it is thirdshift's strongest differentiator. **No surveyed tool documents hiding which system produced an output.** Braintrust's "blind human reviews" hides *peer* judgments; LangSmith's reviewers cannot see each other's feedback; Weave's queues let you choose which fields annotators see (the nearest mechanism, not framed as blinding); MLflow records and attributes every reviewer. LangSmith's **pairwise annotation queues** are the closest shape to a two-Arm comparison, but with fixed left/right positions and no documented randomisation. The recommended workaround across the field is exactly what thirdshift already does: write a neutral label at ingest, randomise per task, keep the mapping outside the review store.

### 5.5 Sandboxes

- **No eval tool has a bwrap backend.** Code search across Inspect's sandbox providers and Harbor's `environments` directory finds none; Inspect's `local` provider is documented as "no sandbox at all".
- **[`anthropics/sandbox-runtime`](https://github.com/anthropics/sandbox-runtime)**, Apache-2.0, **v0.0.81 (2026-10-20)**, is the one released tool for "enforcing filesystem and network restrictions on arbitrary processes at the OS level, **without requiring a container**". [eval-sandboxes.md §3.2](eval-sandboxes.md) already borrowed its allowlisting-proxy-over-a-Unix-socket pattern, which is what `src/proxy.rs` implements. Whether its Linux backend is bwrap, seccomp or Landlock was not inspected **[unverified]**. Worth a read before any further sandbox work, not a replacement for working code.
- `inspect-openshell-sandbox` 0.1.0 (2026-09-30, MIT) wraps NVIDIA OpenShell, which uses Landlock and seccomp, but everything describing the Inspect provider is secondary **[unverified]**.

### 5.6 MLflow: the one correction that affects the Verdict

- **3.17.2 (2026-10-21)**, Apache-2.0 for the whole repo including server and UI, and it **self-hosts without Docker**: `pip install mlflow` then `mlflow server`, default backend store SQLite.
- **[`compare_evaluations`](https://github.com/mlflow/mlflow/blob/master/docs/docs/genai/eval-monitor/comparing-evaluation-runs.mdx) pairs rows across two runs on the same dataset and tests the per-row differences**, reporting per scorer: a **BCa bootstrap confidence interval** of the mean difference (95% default, adjustable), a two-sided **p-value**, **McNemar's test** (exact or chi-square) for binary scorers, **Wilcoxon signed-rank** otherwise with a paired **t-test p-value**, and **Cohen's d_z**. **`assert_improved` gates on `p_value < alpha`.** No power analysis.
- **This is the strongest statistics of any tool surveyed, and it directly contradicts [eval-runners.md §5.3](eval-runners.md)**, which found "no interval and no paired statistic". That note read the comparison *page*; this is an API.
- **It still does not replace the Verdict.** It is frequentist where the Bar is Bayesian; it has no notion of a pre-registered Bar, a margin, separate pass and fail credible levels, or a prediction of how many more Eval tasks would settle an inconclusive result. It also brings everything [eval-runners.md §5](eval-runners.md) documented against it: telemetry on by default, ~87 packages, an extra validation call, 40 default workers, retries on text matching "429", a 300-second scorer timeout added in a patch release, and no resume. **[interpretation]** What it is genuinely worth is as a *cross-check*: running the same Trial outcomes through McNemar's test and comparing the direction of the answer against the Dirichlet interval would be a real validation of the Verdict's implementation, with no dependency in the Experiment path.
- It also **ingests externally-produced runs two documented ways**: OTLP/HTTP at `POST <tracking-uri>/v1/traces` with an `x-mlflow-experiment-id` header (3.6.0+, SQL backend required, **no auth header documented — bind to loopback**), and `search_traces()` → `genai.evaluate(data=traces, scorers=...)` with no `predict_fn`, which is exactly thirdshift's external-runs shape. Its **review queues are open source as of 3.14.0**, though reviewer attribution needs auth; the Review App and labeling sessions are Databricks-only.

### 5.7 Inspect Scout: the best interop target in the field

Not in any prior note. **0.6.1 (2026-10-21), MIT**, Python ≥3.11 ([repo](https://github.com/meridianlabs-ai/inspect_scout), [docs](https://meridianlabs-ai.github.io/inspect_scout/)). It analyses agent transcripts with LLM or pattern "scanners", and it matters here for three reasons:

1. **It already reads what thirdshift's Harnesses write.** [Documented import sources](https://meridianlabs-ai.github.io/inspect_scout/db_importing.html) include **Claude Code** (local session files) and **Harbor** (ATIF trajectories), plus Inspect logs, Phoenix, LangSmith, Logfire, MLflow and Weave. `scout import claude_code` needs nothing from thirdshift at all.
2. **Its transcript schema is the only open format in the field documented for external *writers*.** One flat table, one row per transcript, only `transcript_id` required; `scout db schema` emits the schema as **JSON Schema, Avro, PyArrow and pandas**, explicitly "for creating transcript databases outside of the Python `TranscriptsDB.insert()` API", with `scout db validate` to check conformance and `scout db index` to make rows visible ([schema docs](https://meridianlabs-ai.github.io/inspect_scout/db_schema.html)). Storage is Parquet plus DuckDB. Its fields map onto thirdshift's model unusually well: `task_set`/`task_id`/`task_repeat` for suite/Eval task/Trial number, `agent`/`agent_args`/`model`/`model_options` for the Arm, `score`/`score_explanation`/`success`/`error`/`limit` for the Score, and any extra field becoming queryable metadata. Caveat: no versioned format *document* — the guarantee rests on those schema exports.
3. **Its human-validation workflow has real metrics and dev/test splits**, reporting balanced accuracy, precision, recall and F1 of a scanner against human labels, with the docs warning to keep the split so "scanner prompts aren't overfit to your validation set". That is a sharper version of the Scoring run's calibration idea. But there is **no inter-rater measure, no multi-labeler recording, and blinding is not mentioned** — the label editor sits beside the scanner output.
- Security note if it is ever adopted: 0.6.0 added a nonce marking real message headers in transcripts rendered into scanner prompts, and 0.6.1 fixed a forgery past that nonce. Prompt-injection-by-transcript is an actively patched threat class there, and thirdshift's Graders read Trial reports.

### 5.8 Dead ends, now confirmed dead

- **METR's `task-standard` and `vivaria` were both archived 2026-10-07**, with the READMEs saying METR no longer maintains the Task Standard and uses Inspect instead. Do not build on either.
- **OpenAI's hosted Evals platform is days from shutdown.** Read-only since 2026-10-31 in the published schedule, dashboard and API off on 2026-11-30, with promptfoo named as the migration target ([deprecations](https://developers.openai.com/api/docs/deprecations)). This confirms [eval-tools-landscape.md §2.1](eval-tools-landscape.md) and removes it from consideration permanently. The separate `openai/evals` repository is MIT but dormant: last substantive change 2025-11-03, PyPI `evals` last released 2024-05-01, no shell-command provider (a `CompletionFn` is an importable Python class returning strings), and no trajectory model. Not viable.
- **The remaining hosted platforms fail on hosting, not features**, and the constraint ruling them out has not moved ([`settled.md`](../grill-with-docs/done/698-evals/settled.md), ADR-0015). Re-verified shapes: **Braintrust** self-hosting is Enterprise-only and split-plane — you host the data plane, Braintrust hosts the control plane *including the web UI, auth and metadata such as project and experiment names* — and its significance-testing reputation is **not substantiated by its own docs**, which mention no CIs, p-values or bootstrap. **LangSmith**'s server is proprietary, Kubernetes-and-Helm only, needs ≥16 vCPU and 64 GB plus a license key, and **requires egress to `beacon.langchain.com`** for license verification unless air-gapped. **W&B Weave**'s backend needs a replicated ClickHouse cluster on Kubernetes ≥1.29, ~7 pods and 180 GiB minimum, and will not start without a license. All three ingest OTLP/HTTP, so §6.1's export reaches them if that ever becomes desirable.
- **No trajectory interchange standard exists outside ATIF.** OpenTelemetry's GenAI semantic conventions moved to [their own repository](https://github.com/open-telemetry/semantic-conventions-genai) (Apache-2.0, created 2026-05-05), are still marked **Status: Development** with **no tagged releases**, and define spans and events — including Plan, Execute tool, Agent skills and Load skill — but **no trajectory document concept**. OpenInference treats agents as a span kind (`openinference.span.kind = AGENT`) with no trajectory format. AgentOps has had no release since 2025-08-29. AGNTCY has no trajectory spec and its `acp-spec` is archived. So the OTLP export (§6.1) is the portable *telemetry*, and ATIF (§5.3) is the only portable *trajectory document*. Note the three-way "ACP" collision: Harbor's agent registry, Inspect/Zed's Agent Client Protocol, and AGNTCY's archived Agent Connect Protocol are three different things.
- **The SWE-bench family and friends are task sources, not runners.** SWE-bench evaluates *patches*, needs Docker and recommends **≥120 GB free storage** — on its own enough to rule out the full local image set here, though handing it a diff thirdshift produced remains viable. SWE-smith is a training-data generator, Docker-required. `SWE-rebench/SWE-rebench` does not exist (the org has V2 repos, licences **[unverified]**). Aider is dormant (last release 2025-08-09) and its benchmark harness drives aider's own coders only; Harbor ships an `aider_polyglot` adapter if that task set is ever wanted. OpenHands' eval harness moved to [`OpenHands/benchmarks`](https://github.com/OpenHands/benchmarks) and runs OpenHands agents, Docker by default; driving external agents is **[unverified]**. AgentBeats is a year stale with no licence file, and its active ecosystem is hosted-leaderboard and A2A-oriented. "Harness Arena", which third-party write-ups describe as anonymising outputs from several coding agents before judging — the only thing in the field resembling blinded head-to-head — has **no repository and no licence that could be found [unverified]**.
- **Anthropic ships no coding-agent eval harness** beyond `claude plugin eval`; `anthropics/evals` was last touched 2024-07-02. OpenAI's `frontier-evals` (MIT, pushed 2026-10-12) holds PaperBench, SWE-Lancer and EVMbench; arbitrary-agent-CLI support is **[unverified]**.
- **`claude plugin eval` is the other real change** and has its own section (§2). The 2.1.299 change (2026-10-14) that makes a run ending on an API error score 0 without grading, instead of grading it, is a good illustration of why thirdshift's void rules are fixed with the Bar: the same change in an adopted tool would have silently biased an Arm.

## 6. Interop short of replacement

These are additive: none changes who runs the Trials, so none touches the accuracy-critical core.

### 6.1 OTLP, which already works

`thirdshift logs <command> --export <dir>` writes the Experiment's whole Command Trace as OTLP JSON Lines — `spans.jsonl` and `logs.jsonl`, one export request per line — including every Trial's and model Grader's Session trace spans and the code Graders' spans, all under one trace ID. `otlp.endpoint` streams ended spans live. Security and Scoring run sessions export none, per ADR-0015.

**What this already buys.** Any OTLP consumer can read an Experiment's trajectories today. [eval-viewers.md](eval-viewers.md) established that MLflow and Workshop take OTLP JSON over HTTP, Phoenix takes OTLP over HTTP as protobuf only, and Grafana with Tempo and Loki is the only one that keeps the log records. So the "export to an outside viewer later" option [eval-runners.md §9](eval-runners.md) left open is already exercised. Nothing further is needed for trajectory interop.

**The gap.** The OTLP export carries the trajectories, not the *Scores or the Verdict*. A Score's pass/fail, reason, wrong-finding flag, borderline mark, mechanical checks and recheck history live in the Experiment's private directory and in `experiments <id> --json`. OTLP has no natural place for them beyond span attributes.

### 6.2 Three candidate export formats, ranked

Writing a derived export per Experiment is additive and reversible. Three formats are now plausible, and they rank differently than this note's first draft assumed.

**Best: Inspect Scout's transcript schema.** It is the only format in the field whose docs say, in so many words, that the schema exports exist "for creating transcript databases outside of the Python `TranscriptsDB.insert()` API" (§5.7). It is one flat table, one row per transcript, with only `transcript_id` required, and `scout db validate` checks a producer's output. Its fields line up with thirdshift's model — `task_set`/`task_id`/`task_repeat` for suite, Eval task and Trial number; `agent`/`agent_args`/`model`/`model_options` for the Arm; `score`/`score_explanation`/`success`/`error`/`limit` for the Score — and extras become queryable metadata, so the Bar and the recheck history have somewhere to live. It is also the only candidate that would carry **Scores**, not just trajectories. Against it: Parquet and DuckDB from Rust is real work, the format has no versioned spec document, and Scout's own threat model includes prompt injection through transcripts.

**Second: ATIF.** The only RFC-specified trajectory *document* format, with MUST/MAY language, a validator CLI and golden fixtures, explicitly designed for external producers (§5.3). A per-Trial `trajectory.json` would be readable by Harbor's viewer and, through Scout's Harbor importer, by Scout too. Against it: single-vendor governance, a docs-versus-RFC version discrepancy (v1.7 against v1.8), models that reject undeclared fields, and — the main thing — it carries the trajectory but not the Verdict or the Bar, which §6.1 already says OTLP covers well enough.

**Worst: Inspect `.eval` logs.** This was the first draft's suggestion and it is the weakest of the three. [eval-runners.md §4.4](eval-runners.md) recorded that the format changed under its own readers once; §5.1 adds that 0.3.284 alone shipped three log-format bug fixes, including valid `.eval` files failing to open with "Corrupt ZIP64 structure". Logs may hold NaN and Inf. Third-party *readers* are a documented use case; third-party *writers* are not — the only documented write path is Python's `write_eval_log()`. And the viewer it would unlock cannot show the Verdict, the Bar, the blinding or the rechecks.

**[interpretation] Recommendation: do none of them yet, and do §6.3 first.** All three are worth less than a documented native format, because all three would be *derived* from files thirdshift writes anyway, and none of the three is a format thirdshift's own tooling needs. If an outside consumer ever becomes concrete — a second Console, a hosted analysis, a collaborator — Scout's schema is the one to target, because it is the only one documented for writers and the only one that carries Scores.

### 6.3 A documented schema for thirdshift's own Score and Verdict files

The cheapest interop win, and it points inward rather than outward: `docs/eval-tasks.md` documents format 1 of the *input* manifests and the Arm record, and `docs/trial.md` documents version 1 of the Trial request and result. There is no equivalent document for an Experiment's *output* — the per-Trial result, the Score with its checks and recheck history, and the Verdict with its suite intervals and Bar — beyond what the guide says in prose and what `experiments <id> --json` happens to emit.

Writing that down, versioned the way the Trial protocol is, would let the concurrent scaling work, a future Console, and any outside analysis read Experiment results without reading `src/evals/`. It costs a document and a version field, not a dependency. **[interpretation] This is the one interop item worth doing.**

### 6.4 External tooling for authoring and viewing only

- **Authoring.** `claude plugin eval init`'s interview and promptfoo's generators author cases for their own formats, not thirdshift's TOML. The Eval task pipeline that matters — a confirmed Bug origin proposing an Eval task with a draft catch criterion, approved in the Console or CLI — has no off-the-shelf equivalent. No gain.
- **Viewing.** Covered by §6.1; OTLP already reaches every viewer that could show a trajectory, and none shows the Verdict.
- **Statistics libraries.** The concurrent [eval-suite-scaling.md](eval-suite-scaling.md) covers power; three pointers for its author, not pursued here. Inspect ships `ci_wilson()` and `krippendorff_alpha()` but states it has no significance test and no power analysis. **MLflow's `compare_evaluations`** does paired McNemar, Wilcoxon, BCa bootstrap CIs and `assert_improved` (§5.6) — useful as an independent cross-check of the Dirichlet implementation, not as a dependency. AISI's **`optstop`** does Bayesian optimal stopping with a convergence projection that estimates the additional trials needed, which is the same question `src/verdict/prediction.rs` answers, and **`hibayes`** does hierarchical Bayesian eval modelling — the shape [eval-runners.md §7.1](eval-runners.md) said Bowyer et al. leave undone for several trials per item. Both are GitHub-only with no releases.

## 7. Recommendation

**Keep Experiments as built. Replace nothing. Adopt one idea and write one document.** **[interpretation]**

The reasons, in order of weight:

1. **The expensive parts are the ones nothing sells.** 13,248 non-test lines shipped, and the components no tool covers — time-safe repositories, the six-Harness Trial protocol, the sandbox and proxy, the scopes, blind packets, void rules, the Verdict and Bar, rechecks, suite selection, the release gate, the Scoring run — account for the great majority of them. Replacing the commodity remainder (scheduling, resume, pass^k, a viewer) would remove perhaps 2,000–3,000 lines and add a second language, a package tree, and glue of about the same size. [eval-runners.md §8.2](eval-runners.md) predicted that trade and the build did not change it.

2. **A replacement now costs more than it would have before the build.** In October the choice was between writing code and writing glue. Now it is between keeping working code and *rewriting* it, with the behaviour the thirty Tickets settled — the void causes, the pause-and-resume checkpointing, the decisive-Score rule, the `repository_changed` guard, the graded-copy snapshot — having to be reproduced on top of a framework's own defaults. Sunk cost is not an argument to keep bad code; it is an argument against re-litigating code that works, and 8,565 lines of integration tests plus a fake per Harness are the evidence that it works.

3. **Every candidate's defaults are in the accuracy path.** §5 found three log-format fixes and a sandbox behaviour change in Inspect in six days, a `claude plugin eval` change that turned API errors from graded runs into zeroes, and a Harbor 0.25.0 change that stopped mounting local sandbox logs live. `inspect_swe`'s `_BRIDGE_SAFE_ENV` table exists precisely because Claude Code ships five client-side retry and idle watchdogs that have to be switched off for an eval to be honest. thirdshift's equivalent decisions are fixed with the Bar and refused if they change mid-Experiment. Putting them under a dependency that ships two or three times a week moves them outside that guarantee.

4. **Subscription support exists now, and still covers the wrong axis.** Three tools document it, all for Claude and Codex only, and all driving the vendor SDK rather than thirdshift's session code. The Arm matrix is six Harnesses.

5. **Blinding is unique.** §5.4 checked the whole field: nothing hides which system produced an output. The blind packet is the mechanism the Verdict's honesty rests on, and it would have to be built on top of any tool adopted.

**What to adopt alongside:**

- **A hard cost ceiling, borrowed from `claude plugin eval --max-cost-usd`.** Checked before each Trial launches, so overrun is bounded to the Trials in flight. thirdshift has a per-Trial timeout and a plan-limit pause but no budget. This is a small addition to the Bar (recorded with it, like the timeout) and the only feature in §3's table that a tool has and thirdshift lacks. Worth an issue.
- **A one-off cross-check of the Verdict against MLflow's `compare_evaluations`.** Take a finished Experiment's Trial outcomes, run McNemar's test and the BCa bootstrap CI over them outside the Experiment path, and check the direction agrees with the Dirichlet interval. This is the strongest validation available for 150 lines of statistics with no published reference implementation, and it costs a throwaway script, not a dependency. Pair it with the synthetic coverage checks [eval-runners.md §7.1](eval-runners.md) already ran.
- **A read of three files, for ideas rather than code:** `inspect_swe`'s `_BRIDGE_SAFE_ENV` (the Harness watchdogs an honest Trial should disable), [`anthropics/sandbox-runtime`](https://github.com/anthropics/sandbox-runtime) v0.0.81 (container-free OS-level restriction, whose proxy pattern `src/proxy.rs` already follows), and Inspect's `krippendorff_alpha` (a better-founded calibration statistic than 18-of-20).
- **Nothing else.** No framework, no second language, no viewer.

**What to write:**

- **§6.3's output format document**, versioned the way `docs/trial.md` versions the Trial protocol: the per-Trial result, the Score with its checks and recheck history, and the Verdict with its suite intervals and Bar. This is the interop that pays, because it serves the concurrent scaling work and any future analysis without a dependency, and because OTLP (§6.1) already covers trajectories and carries no Scores.

**What to decline, explicitly:**

- **Writing Inspect-shaped `.eval` logs** (§6.2). Third-party readers are a documented use case; writers are not, and the format shipped three bug fixes in one release.
- **Harbor, SWE-bench's harness and Inspect's Docker sandbox.** Harbor's runtime list now includes podman and singularity, but its tasks define Docker *images* regardless, and SWE-bench recommends ≥120 GB of storage. Disk, not the Docker daemon, is the binding constraint.
- **Any hosted platform**, under [`settled.md`](../grill-with-docs/done/698-evals/settled.md) and ADR-0015 — and now also on re-verified hosting shapes: Braintrust keeps the web UI and metadata on its own control plane, LangSmith needs ≥16 vCPU/64 GB and egress to `beacon.langchain.com`, Weave needs a replicated ClickHouse cluster.
- **METR's task-standard and vivaria**, both archived 2026-10-07.

## 8. What would change the answer

Each of these is a concrete trigger, not a worry. **[interpretation]**

- **A bigger host with more disk.** Not Docker specifically — Harbor already runs on podman and singularity, and MLflow and Scout need no container at all. The binding constraint is images and caches. With disk, Harbor becomes usable, per-repository images solve the "a commit stops building on the host" problem [`settled.md`](../grill-with-docs/done/698-evals/settled.md) (Q6.7) anticipates, and the implement suite gets easier. Even then the Verdict, the Bar, the blinding and four of six Harnesses stay thirdshift's, so this would make a *sandbox* swap plausible, not a runner swap.
- **Harbor's `resolve_auth_file` pattern reaching grok and opencode.** Harbor already does subscription login for `claude-code` (via `CLAUDE_FORCE_OAUTH` and `claude setup-token`, the mechanism thirdshift uses) and `codex`, through a generic helper. `grok_build.py` and `opencode.py` have no such path **today**. If that helper is wired through the remaining agents, Harbor would cover four of thirdshift's six on subscription, and with disk available the comparison would be worth redoing. This is the single most watchable change in the field.
- **`claude plugin eval` growing an `--agent` option or an effort axis.** It is the only tool where the agent under test is the harness itself, so it has the least glue. One axis is the whole gap.
- **A documented blind-packet or two-Arm grading call in Inspect.** Its scorer signature is the single reason Inspect cannot grade thirdshift's packets. If a scorer could take a group of samples spanning two logs, Inspect would cover the Graders as well as the scheduling, and the Python-versus-Rust question would be live again. Watch the `review`/`Reviewer` surface, which is currently in-run tool-result review rather than post-hoc grading.
- **A concrete outside consumer of Experiment results.** A second Console, a collaborator or a hosted analysis would make §6.2's export real, and Inspect Scout's transcript schema is the target — the only format in the field documented for external writers, and the only one that carries Scores as well as trajectories.
- **`hibayes` or `optstop` getting releases.** Both are AISI, MIT and directly on the Verdict's territory — hierarchical Bayesian eval statistics, and a convergence projection for the trials-needed question. Today they are GitHub-only with no tags, which is not a dependency to take on for a release gate. A tagged, PyPI-published `hibayes` would be the first serious argument for Python in the Verdict.
- **The maintenance becoming the bottleneck.** Six days and 139 commits built it; the signal to watch is how many commits per month it takes to *keep* it running once Harnesses update themselves underneath it. If the eval modules start consuming more Run capacity than the factory produces, the commodity 20% is where to cut, and `inspect view` in place of the Console's Experiments pages is the first candidate.
- **A second person.** The whole case for Rust-in-one-language rests on one maintainer and one test suite. A contributor who knows Inspect would change the cost of a second language.
- **A Verdict that needs a hierarchical model.** [eval-runners.md §7.1](eval-runners.md) notes Bowyer et al. leave several trials per item to a hierarchical model they do not give. If the Bar ever needs one, the 150–200 lines of Rust becomes a real statistics dependency, and Python's ecosystem starts to matter.

### 8.1 Update (2026-10-27): the host constraint is lifted

The Day shift can provide a bigger host with room for container images, so this note no longer treats disk, or Docker, as a constraint. §8's first trigger is met.

**What doesn't change: keep the runner.** Disk was never why a runner swap was declined. These still are:
- Harbor and the other tools drive only Claude and Codex on subscription logins, out of six Harnesses (§5.3).
- None hides which Arm produced an output from its Graders (§5).
- None has the Verdict, the Bar or the Void Trial rules (§3).

**What changes:**
1. **The implement suite becomes much easier.**
   - An image per repository solves the "a commit stops building on the host" problem that [`settled.md`](../grill-with-docs/done/698-evals/settled.md) Q6.7 anticipated.
   - SWE-bench's harness (≥120 GB) and SWE-smith's per-repository images for bug injection ([eval-suite-scaling.md §2](eval-suite-scaling.md)) become usable as they are.
   - Harbor's task format becomes a candidate for implement Eval tasks, even with thirdshift's runner still driving the Trials.

   These are questions for the implement suite's grill (#1484), not research to do now.
2. **Trials could run in containers instead of bwrap.** This is plausible now, though not clearly better. The bwrap sandbox works today, and what containers mainly add is per-repository toolchains, which only the implement suite needs. Decide it there.
3. **Harbor is worth re-checking when the implement suite is grilled**, especially whether its `resolve_auth_file` helper reaches `grok-build` and `opencode`.

§7 declined Harbor, SWE-bench's harness and Inspect's Docker sandbox mainly because of disk. For the implement suite's tasks and environments, that decline is reopened (item 1). As a replacement runner it still holds, on the grounds above.
