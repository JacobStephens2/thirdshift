# Eval tools for thirdshift: the wider landscape

Research date: 2026-10-16 (America/New_York).

**Question.** What belongs beside Langfuse on the shortlist for [#698](https://github.com/JacobStephens2/thirdshift/issues/698), after AI Engineer New York and a broader search? This companion leaves [eval-tools.md](eval-tools.md) unchanged. Its three jobs remain **(a)** replays before changing Factory skills, Session prompts or Harness/Model/Effort defaults; **(b)** scoring production Runs; **(c)** viewing traces. The user put (a) first and wants production analysis to measure accuracy and quality, with efficiency separately.

**Method.** Official product documentation, public specifications and first-party repositories were checked read-only. Code citations use fixed commits; live documentation and prices can change. The earlier note supplies the six-Harness inventory and existing replay design; this search adds candidates and challenges its recommendation. The constraints remain subscription execution, a preference for open source and self-hosting, buy over build as a preference rather than a requirement, and a 4-core/8-GB host without Docker. The user explicitly added that handrolling is acceptable; a maintained custom runner is therefore a first-class option. Architectural plausibility is not a measured resource result. No tool was installed, no service started, no account created and no eval or Session log uploaded.

Private conference evidence was retrieved and examined separately. This public note includes public agenda links and independently corroborated product claims, without private recordings, people, quotations or Session content. Security sessions and their derived grades/datasets stay off third-party eval services, following [ADR-0015](../adr/0015-security-findings-stay-private-until-fixed.md). Hosting permission is still unanswered; asking about formats did not answer it.

**Tags.** **[unverified]**: no adequate primary confirmation; **[3rd-party]**: secondary evidence, unused for the recommendations; **[interpretation]**: fit judgment rather than documented capability; **[needs live check]**: requires a real run. **Deep** below means focused source/document review, not a deployment or benchmark. **Screen** means bounded triage; absence from its row does not establish that a feature is absent.

## TL;DR

- **Langfuse is not the first tool to choose for the first job.** With handrolling explicitly acceptable, start with a maintained **#429 runner plus versioned task/trial/results JSON and a small comparison report**. **promptfoo around the same workspace/CLI boundary** is the leading alternative when assertions, repetitions and UI maintenance justify it; Inspect is the Python alternative. For a narrower Claude skill/plugin change, the native **`claude plugin eval`** is a serious new option. These are distinct from an observability backend. (§3.1–§3.3)
- **For production scoring plus datasets and traces on this host, MLflow remains the strongest OSI-licensed full-platform candidate.** Phoenix is the close alternative when its coding-agent/ATIF integration matters more than its ELv2 licence and protobuf ingestion. Their deployment shapes are plausible here; coexistence with the Factory is unmeasured. (§3.4)
- **For just a local trace viewer, add Raindrop Workshop to the first trial.** It is MIT, SQLite-based and available as a native binary; it accepts OTLP HTTP JSON and protobuf. This materially broadens the earlier two-tool shortlist. Its local viewer and its optional Cloud product are different choices. (§3.5)
- **If hosted storage is allowed, Braintrust is the strongest eval-first commercial challenger [interpretation].** LangSmith is another credible option; Arize AX, Galileo, HoneyHive and Raindrop target different production workflows. None establishes free reuse of model subscriptions for its managed judges. (§3.6)
- **Session logs contain trace evidence, but are not already a portable trace.** OTel/OTLP, GenAI conventions, OpenInference, ATIF and Agent Trace serve different purposes. Standardize export and IDs first; do not discard original logs or assume every viewer renders the same attributes. (§3.7)

## 1. What the conference adds

The [official New York 2026 agenda](https://ai.engineer/nyc/2026/schedule) places the event on October 12–14. Relevant sessions include a Harbor workshop, agent verification, Langfuse, observability/regression testing and coding-agent review. An agenda establishes that these sessions were scheduled; it does not independently establish everything said in the room. The private notes were used to identify questions to check, rather than published as public evidence.

The independently verifiable common thread is a loop: capture behavior, select representative cases, run a candidate against a baseline, grade outcomes and inspect trajectories. [Langfuse's evaluation overview](https://langfuse.com/docs/evaluation/overview), [MLflow's dataset guide](https://mlflow.org/docs/latest/genai/datasets) and [Phoenix's Harbor integration source](https://github.com/Arize-ai/phoenix/tree/c9a3087027fedff23c32b083534d0a16bcce1a25/packages/phoenix-client/src/phoenix/client/harbor) substantiate different parts of that loop. The talks do not make it exclusive to one vendor.

**Implication [interpretation].** Preserve successful cases alongside failures; compare correctness, false findings, task completion and efficiency separately; calibrate model graders against human labels. Outcome checks should establish what changed in the repository or external system. Exact tool-path checks belong in tests specifically about tool selection or skill activation. These are evaluation-design choices, not reasons to adopt a particular trace store. [Anthropic's eval methodology](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents) supports outcome-based grading, repeated trials and grader calibration.

## 2. Landscape, grouped by what each tool does

**Reading the tables.** Jobs are (a)/(b)/(c) above. “CLI wrapper” means thirdshift supplies a callable that starts an already authenticated Harness; it is an integration possibility, not a verified vendor integration. “Ingest” means supplied events/spans, not direct parsing of all six Session-log formats. “Plausible” is a deployment-shape judgment **[needs live check]**. Licence names refer to the linked distribution, not every hosted feature or dependency.

**Three different credentials.** A platform key authenticates logging/results; a provider API key pays for inference; a CLI login may draw from an existing subscription. Accepting traces or arbitrary functions does not make managed judges subscription-compatible. Conversely, a paid platform can store scores produced by local subscription-backed CLIs. Some platforms include inference credits instead of requiring a separate provider key; that still buys new inference. The earlier blanket wording “managed judge needs an API key” should be read with this distinction.

## 3. The reads that affect the shortlist

### 3.1 Handrolling and promptfoo: compare the incremental work

The user's willingness to handroll changes the weighting. A small owned runner can be the better fit without becoming an observability platform **[interpretation]**. The public [#429 script](https://github.com/JacobStephens2/thirdshift/blob/6d272cf29f3ebedaf349726861f7bed7efbb3fba/docs/research/second-opinion-replays/replay.py) already defines task/arm units and six CLI commands, prepares restricted Git inputs, records versions/events/metadata, runs serially, resumes work and handles plan-limit stops. It also hardcodes paths, dates, tasks and model arms. Its repository setup limits historical objects; full-access CLIs on the same host still have other host/memory/network access. Calling that globally “leak-free” would overstate it.

| Incremental concern | Bounded owned runner | promptfoo around the same wrapper | Inspect custom solver |
|---|---|---|---|
| Keep from existing work | CLI commands, workspace preparation, artifact capture, limit handling | Same | Same |
| Add/maintain | Versioned case/arm/trial manifest, grader results/evidence, repeat accounting, comparison thresholds and small report | Provider/metadata adapter, assertion mapping, configuration/version compatibility | Solver/transcript mapping, scorers and task metadata |
| Buy | No new framework; JSON files can remain the first store | Assertions, repetitions, result storage/UI and CI plumbing | Task/scorer framework, repeated-attempt metrics and eval-log analysis |
| Still own in every case | Historical input validation, clean per-trial context, correct CLI auth, private artifact separation, domain grades | Same | Same |
| Reason to switch | Report/assertion/scheduling maintenance becomes a recurring cost | Framework semantics obscure the real Harness or add more work than they save | Custom solver's model/auth integration outweighs its analysis value |

All integration/maintenance judgments in this table are **[interpretation]**; no effort estimate was measured. Day one needs no SQLite driver or new service: store immutable input fingerprints and versioned results in JSON, classify failures/limits/cancellations separately from task failures, and render a simple arm/case comparison. SQLite, dashboards and general experiment APIs can wait until their actual query/review needs appear. A static comparison report is not a production span viewer.

**promptfoo remains a credible alternative**, rather than being dismissed because a wrapper is necessary.

The useful comparison is not “script versus framework from scratch.” thirdshift already has the workspace preparation and Harness invocations described in [second-opinion-replays.md](second-opinion-replays.md). promptfoo's [custom-script provider](https://www.promptfoo.dev/docs/providers/custom-script/) can invoke a command; Python/JS providers can return structured metadata. Its [configuration reference](https://www.promptfoo.dev/docs/configuration/reference/) supplies repetitions, concurrency, assertions and lifecycle hooks. This can purchase the generic orchestration/reporting work while preserving the Factory-specific workspace and graders **[interpretation]**.

The [Claude adapter](https://www.promptfoo.dev/docs/providers/claude-agent-sdk/) explicitly documents `apiKeyRequired: false` for delegating authentication to an active local Claude Code session. The [Codex adapter](https://www.promptfoo.dev/docs/providers/openai-codex-sdk/) documents reuse of the existing ChatGPT login when API credentials are unset. Its SDK integration evaluates final output, usage and tool trajectories; heuristic skill detection is weaker than a native skill event. The [OpenCode provider](https://www.promptfoo.dev/docs/providers/opencode-sdk/) adds another direct adapter, but actual login propagation is still a live check.

Auth capability is not a blanket provider-policy guarantee. Anthropic's [credential-use guidance](https://code.claude.com/docs/en/legal-and-compliance) distinguishes ordinary individual CLI/SDK usage from developers offering services using subscription credentials. For the first comparison, preserve thirdshift's actual CLI invocation and login behavior in a wrapper rather than silently replacing its runtime with a new SDK configuration **[interpretation]**.

**Incremental work [interpretation]:** expose prepared cases and candidate arms, launch the existing command once per trial, return stable case/Run IDs plus outputs, and translate existing correctness criteria into assertions. Keep candidate Git history, memory, network and workspace leakage controls in that boundary. Copying a working directory alone is not a validated historical replay. For fresh stochastic comparisons, its [caching guide](https://www.promptfoo.dev/docs/configuration/caching/) calls for `--no-cache` with `--repeat`; repeat indices separate cache entries but later reruns may still reuse them. Start with concurrency one or two, and check retries/repetition identity and grader selection **[needs live check]**. The [local storage documentation](https://www.promptfoo.dev/docs/usage/self-hosting/) describes SQLite; source is [MIT at 7901170](https://github.com/promptfoo/promptfoo/blob/79011700b4cb544ddd9267565571a1d42d3a3051/LICENSE).

The comparison is a maintained small runner versus a framework around that runner, with explicit capabilities bought or maintained. Neither implies adopting a production trace database.

### 3.2 Native Claude skill/plugin evals: a narrower unit can be cheaper

[`claude plugin eval`](https://code.claude.com/docs/en/plugin-evals) compares repeated candidate/baseline trials with HTML/JSON reports. Agents and graders use normal Claude auth. Temporary workspaces/config omit ordinary project/user context; file setup requires explicit `--scaffold`. Linux Bash needs OS sandbox prerequisites, while plugin hooks and real MCP processes remain outside that sandbox. Use `--no-publish`: eligible subscription shell runs can otherwise publish a private report artifact. Native eval cases and skill-creator authoring data use different formats.

**Fit [interpretation].** A narrow skill/plugin test complements a multi-Harness historical replay. Supplying the intended Factory context and outcome graders remains work **[needs live check]**. Neither unit should silently stand in for the other.

### 3.3 Inspect and Harbor: distinguish their execution models

Inspect is an evaluation framework with custom solvers/scorers and a [local log viewer](https://inspect.aisi.org.uk/log-viewer.html); [scoring metrics](https://inspect.aisi.org.uk/scoring.html) support repeated-attempt analysis. The existing [MIT implementation](https://github.com/UKGovernmentBEIS/inspect_ai/tree/a699376315c95b6410f5aec01af37c8dec452aea) remains a serious Python alternative to promptfoo. A custom solver that calls the existing CLI is plausible, but subscription behavior and model-free execution need a bounded trial **[needs live check]**.

Do not confuse that solver with **Inspect SWE's bundled adapters**. Its [official overview](https://meridianlabs-ai.github.io/inspect_swe/) says agents run in sample sandboxes and their model API calls are proxied back to Inspect. Claude's [pinned environment code](https://github.com/meridianlabs-ai/inspect_swe/blob/963523e73f8657535fdaf7a2bcb1fdb5ba3d566d/src/inspect_swe/_claude_code/env.py) confirms the bridge configuration. These adapters do not establish reuse of the host's CLI subscription. Framework solvers normally run in the host process; requesting [sandbox operations](https://inspect.aisi.org.uk/sandboxing.html) is a separate act.

Harbor's [supported environments](https://docs.harborframework.com/sandboxes/pre-integrated-sandboxes) now include Podman and Singularity as well as Docker and remote sandboxes. “Requires Docker” is therefore too narrow. “Requires a supported runtime or remote execution environment” is the defensible constraint. No ready bare-host replay path was verified. Agent credentials are [resolved separately](https://docs.harborframework.com/agents/agent-auth-resolution), and supporting a Harness does not guarantee its subscription path. Its [Apache-2.0 source](https://github.com/harbor-framework/harbor/tree/3e9f14a7c1033896cc600d27de69d6948bcb3410), task verifiers and trajectory artifacts make it a strong future choice if the environment constraint changes. Remote sandboxes introduce another data destination; Q1.2 still applies.

### 3.4 MLflow and Phoenix: full local platforms still earn their place

**MLflow.** The [production-trace evaluation guide](https://mlflow.org/docs/latest/genai/eval-monitor/running-evaluation/traces/) documents fetching existing traces and scoring them, with local Python-server deployment. [Evaluation datasets](https://mlflow.org/docs/latest/genai/datasets) require a SQL backend; SQLite qualifies, FileStore does not. [The evaluation API](https://mlflow.org/docs/latest/api_reference/python_api/mlflow.genai.html) accepts existing traces or a prediction callable and custom scorers; built-in model judges use provider inference. Some advanced features are Databricks-specific: do not transfer every managed monitoring feature to OSS.

MLflow's [OTLP ingestion docs](https://mlflow.org/docs/latest/genai/tracing/opentelemetry/ingest) require an experiment-ID header and HTTP ingestion. The [pinned handler](https://github.com/mlflow/mlflow/blob/6d3ff8585e55714b22b653cd389b1b4070e5ef8e/mlflow/server/otel_api.py#L107-L181) accepts JSON and protobuf. That makes a Rust HTTP JSON exporter possible without a Python SDK. **Fit [interpretation]:** first full local platform to assess when OSI licensing, score storage and datasets matter together; process size under real ingestion is unmeasured.

**Phoenix.** [Native CLI deployment](https://arize.com/docs/phoenix/self-hosting/deployment-options) and [SQLite storage](https://arize.com/docs/phoenix/self-hosting/deploying-phoenix) allow a local instance without a separate database. The [Harbor client integration](https://github.com/Arize-ai/phoenix/tree/c9a3087027fedff23c32b083534d0a16bcce1a25/packages/phoenix-client/src/phoenix/client/harbor) translates tasks/trials and trajectories into analysis concepts. This is a concrete advantage for a Harbor/ATIF workflow, not proof that it already parses thirdshift's logs.

Phoenix's [trace endpoint](https://github.com/Arize-ai/phoenix/blob/c9a3087027fedff23c32b083534d0a16bcce1a25/src/phoenix/server/api/routers/v1/traces.py#L461-L499) accepts HTTP protobuf, rejecting other content types; its [GenAI conversion layer](https://github.com/Arize-ai/phoenix/blob/c9a3087027fedff23c32b083534d0a16bcce1a25/src/phoenix/trace/gen_ai/conversion.py) maps attributes into OpenInference. Licence: [ELv2](https://github.com/Arize-ai/phoenix/blob/c9a3087027fedff23c32b083534d0a16bcce1a25/LICENSE). **Fit [interpretation]:** assess beside MLflow if the coding-agent analysis workflow saves enough work to justify these tradeoffs. Neither tool reconstructs missing historical fields or supplies thirdshift's domain-specific outcome graders.

### 3.5 Workshop and TruLens: the local set is wider than two

Workshop's [README at a6b82d7](https://github.com/raindrop-ai/workshop/blob/a6b82d71596cf7e8974e5efae63f9e15260d76ef/README.md) describes a local SQLite trace viewer distributed as a binary. Its [ingestion handler](https://github.com/raindrop-ai/workshop/blob/a6b82d71596cf7e8974e5efae63f9e15260d76ef/src/server.ts#L653-L843) accepts OTLP HTTP JSON and protobuf. Cloud setup is optional. This is a credible viewer to adopt with a smaller deployment shape than Langfuse **[interpretation]**.

There are separate AI execution paths. [Claude chat](https://github.com/raindrop-ai/workshop/blob/a6b82d71596cf7e8974e5efae63f9e15260d76ef/src/claude-cli-chat.ts#L42-L49) and [Codex chat](https://github.com/raindrop-ai/workshop/blob/a6b82d71596cf7e8974e5efae63f9e15260d76ef/src/codex-cli-chat.ts#L23-L31) spawn the CLIs; reuse of their login is plausible, untested. Built-in model-call replay, summary and analysis routes in [server.ts](https://github.com/raindrop-ai/workshop/blob/a6b82d71596cf7e8974e5efae63f9e15260d76ef/src/server.ts) use provider API keys. Application replay can instead call a registered local HTTP server, as its [replay setup skill](https://github.com/raindrop-ai/workshop/blob/a6b82d71596cf7e8974e5efae63f9e15260d76ef/skills/setup-agent-replay/SKILL.md) documents. That does not establish historical repository reconstruction. Durable issue/good/note annotations and MCP queries are verified in its [MCP tools](https://github.com/raindrop-ai/workshop/blob/a6b82d71596cf7e8974e5efae63f9e15260d76ef/src/mcp/tools.ts); comparable dataset versioning and experiment comparison were not established by the checked [schema](https://github.com/raindrop-ai/workshop/blob/a6b82d71596cf7e8974e5efae63f9e15260d76ef/src/db/schema.ts) **[unverified]**. Treat it as a viewer challenger, rather than assuming feature parity with MLflow/Phoenix.

TruLens' [current client-hook guide](https://github.com/truera/trulens/blob/86893205ee4ae749444df8d59d5a3d73d5bec4a3/docs/component_guides/instrumentation/client_hooks.md) documents Claude Code/OpenCode/Cursor hooks, default local SQLite and optional OTLP export. Source-bearing content is opt-in. Its explicit limitation matters: these hooks create managed Run objects only on Snowflake; local database/OTLP paths export spans and skip that lifecycle. That makes it a useful [MIT](https://github.com/truera/trulens/blob/86893205ee4ae749444df8d59d5a3d73d5bec4a3/LICENSE) capture/feedback component, without proving that its local hook path is a complete drop-in platform for all three jobs.

### 3.6 If hosted storage is allowed: Braintrust first, LangSmith beside it

Braintrust's [function-based evaluation workflow](https://www.braintrust.dev/blog/any-framework-any-provider) supports arbitrary tasks/scorers and repeated trials; [OTel ingestion](https://www.braintrust.dev/docs/integrations/sdk-integrations/opentelemetry) separates tracing from execution. A local task could call the existing CLI **[interpretation, needs live check]**. This is a stronger buy-over-build candidate than adopting a store and writing all experiment plumbing oneself **[interpretation]**.

Its [pricing](https://www.braintrust.dev/pricing) currently has Starter at $0 with 1 GB processed, 10,000 scores and 14-day retention; Pro starts at $249/month with larger allowances and $100/month in model credits. Starter includes $10/month in model credits. These credits are separate from an existing CLI subscription. Custom-code scores also affect metering. Enterprise [self-hosting](https://www.braintrust.dev/docs/admin/self-hosting) is a data plane with a hosted control plane, and the documented infrastructure is far beyond this host. It does not satisfy a fully local interpretation of Q1.2.

LangSmith's [quickstart](https://docs.langchain.com/langsmith/evaluation-quickstart) also accepts arbitrary target/evaluator functions, and its [OTel integration](https://docs.langchain.com/langsmith/trace-with-opentelemetry) maps several attribute conventions. [Pricing](https://www.langchain.com/pricing) currently offers a one-seat Developer tier with 5,000 base traces and Plus at $39/seat/month with 10,000 base traces, plus usage; retention depends on trace class. Enterprise [self-hosting](https://docs.langchain.com/langsmith/self-hosted) needs a Kubernetes stack, rather than the current host. Hosted/tuned evaluator products may bill through platform usage rather than a BYO model key; neither route uses the existing CLI allowance automatically.

**Why the others stay screened [interpretation].** [Arize AX](https://arize.com/pricing) and [Signal](https://arize.com/compare/) emphasize production diagnosis and recurring issues; they should not be confused with Phoenix OSS. [Galileo's local metrics](https://docs.galileo.ai/how-to-guides/metrics/create-local-metric/create-local-metric) are flexible, but its [specialized Luna judges](https://docs.galileo.ai/concepts/luna/luna) are an enterprise inference product. [HoneyHive](https://www.honeyhive.ai/pricing) combines reviews and evaluations; its [hosted provider keys](https://docs.honeyhive.ai/v2/workspace/provider-keys) and [EKS self-hosting](https://docs.honeyhive.ai/v2/setup/self-hosted) do not improve present local fit. [Raindrop Cloud](https://www.raindrop.ai/) targets production signals/failure discovery; its event unit is not one span, so its price cannot be compared to Langfuse observations directly. No primary evidence in this search established a HoneyHive/Raindrop rename relationship; treat them as separate products.

### 3.7 Answer to the trace-format question

A Session log is a sequence of Harness events. A trace is a correlated execution tree: spans have IDs, parent relationships, times and attributes. Much of the evidence overlaps. Converting logs into traces requires deciding which events form a span and how Runs, Sessions, model calls, tools and sub-agents relate. Original events can retain details no shared convention captures **[interpretation]**.

| Name | Role | What it does not establish |
|---|---|---|
| [OpenTelemetry](https://opentelemetry.io/docs/concepts/signals/traces/) | Trace data model, context and instrumentation ecosystem | An eval's task manifest, grader or score meaning |
| [OTLP](https://opentelemetry.io/docs/specs/otlp/) | Export protocol, with protobuf/JSON HTTP and gRPC forms | Every receiver supports every form |
| [GenAI semantic conventions](https://github.com/open-telemetry/semantic-conventions-genai/blob/f3c6d0c9bb66ebd474668a3a0be25c61226f02c2/docs/gen-ai/README.md) | Names/meaning for model/agent attributes; currently Development | Frozen universal schema or identical backend UI |
| [OpenInference](https://github.com/Arize-ai/openinference/blob/38b858d9baa8477985dce5031a8f47c216cc52f6/spec/README.md) | AI-specific span kinds/attributes layered over OTel/OTLP | A different network transport or guaranteed lossless GenAI mapping |
| [ATIF](https://docs.harborframework.com/agents/atif) | Agent trajectory JSON: steps, tools, sub-agents, metrics | An OTLP stream or a guarantee a Harness can resume the trajectory |
| [Agent Trace](https://agent-trace.dev/) | A draft code-attribution format connecting lines to AI conversations | A general execution trajectory; the spec excludes quality assessment |

The GenAI conventions now live in a [dedicated upstream repository](https://opentelemetry.io/docs/specs/semconv/gen-ai/); their Development status argues for recording the convention version. Phoenix's conversion code illustrates why interoperable transport still produces different presentation. OTLP HTTP JSON is accepted by MLflow and Workshop, while Phoenix's current endpoint requires protobuf (§3.4–§3.5).

**Recommendation [interpretation].** Use stable Run/Session/trial IDs and a versioned OTel/GenAI export, with backend-specific mapping at the edge. Preserve raw Session logs until a round-trip review establishes what would be lost; retain domain outcomes/grades alongside traces. Adopt ATIF if it buys a concrete Harbor/Phoenix integration, rather than renaming every log ATIF. A format decision can proceed independently of hosted-storage permission. No storage migration is implemented by this research.

## 4. Fit against Langfuse, separately for each job

The following ranking is **[interpretation]**, conditional on present constraints, not a measured benchmark.

| Job | First candidate | Credible alternative | Where Langfuse wins |
|---|---|---|---|
| (a) Cross-Harness pre-change replays | Maintained #429 runner + versioned JSON + small report | promptfoo around same wrapper; Inspect solver; Harbor with supported runtime | Integrated experiment/annotation surface once a backend is wanted; it still needs the execution boundary |
| (a), specifically a Claude plugin/skill | Native plugin eval, with intended context explicitly supplied | promptfoo skill/CLI cases | Shared datasets/review workflow across providers; not native isolated skill execution |
| (b) Production Run scores locally | Domain code graders + externally executed model graders; MLflow if persistent comparison/UI is needed | Phoenix annotations/experiments; Evidently for metric reports | Comprehensive integrated scoring/annotation workflow on another host |
| (c) Simple local viewer | Workshop trial | MLflow for broader platform; Phoenix for agent/ATIF workflow | Integrated viewer+evaluation suite when larger hosting is acceptable |
| (a/b/c), hosted permission granted | Compare Braintrust with Langfuse; LangSmith as another finalist | AX/Galileo/HoneyHive/Raindrop for specific workflow needs | MIT eval core and a self-host exit path, plus its particular dataset/annotation UX |

Two independent fit lenses were considered: the current host/subscription constraints with handrolling allowed, and an advocate for Langfuse given a second machine or permitted hosting. These are reasoned assessments, not deployment benchmarks.

**The strongest case for Langfuse [interpretation].** A second machine removes the resource objection. If its dataset, annotation and production-to-experiment workflow saves enough work, one backend may be worth operating instead of stitching several tools together. If Cloud is permitted for a specific data class, it also avoids host operations. Nothing here demonstrates that another platform's UX is better on thirdshift's own cases; that requires a controlled comparison. What does not change is the need to prepare historical workspaces, execute the real Harnesses and supply trustworthy domain graders.

## 5. What changes in the earlier §6.2

This section supersedes recommendations only; [eval-tools.md](eval-tools.md) remains intact for existing references.

1. **Retain an owned runner as a serious first choice, with a concrete boundary.** The user is open to handrolling. Grow #429 into a maintained task/arm/trial runner with graders, versioned JSON and a small comparison report; avoid rebuilding a general platform. Compare promptfoo around the same wrapper when generic orchestration/UI becomes recurring work, and Inspect when its task/scoring model earns the adapter cost. Native Claude plugin eval is the narrow skill supplement. The wider search changes the alternatives and switching criteria, rather than forcing a packaged-tool win.
2. **Keep (b)'s domain graders, but do not confuse end-state/friction scores with quality.** Feed correctness/error categories and human-reviewed outcomes into the dataset, and maintain separate completion/accuracy/false-finding/efficiency measures. A tool supplies score storage and review, not the definition of a correct Run.
3. **Expand (c)'s local shortlist.** Workshop joins MLflow/Phoenix; TruLens, Evidently and native Docent/Lunary paths invalidate the categorical “only two without Docker” claim. They do not all offer the same workflow or resource profile.
4. **Qualify standards and auth.** GenAI-compatible ingestion does not guarantee identical rendering or transport support. Distinguish platform credentials, provider inference and actual CLI-login reuse. Included judge credits do not consume an existing model subscription.
5. **Replace “Harbor needs Docker” with its actual supported-runtime requirement.** Podman/Singularity and remote sandboxes exist; none was installed or demonstrated as suitable here.

## 6. Direct input to the #698 grilling

**Does anything fit better than Langfuse?** Under the present constraints: **yes for (a), and plausibly for (c)**. A maintained runner around existing CLI execution, with handrolling explicitly acceptable, better matches the first requested decision; a native local viewer avoids Langfuse's service stack. For **(b)**, local MLflow is the leading full-platform candidate, while the graders stay thirdshift-specific. If data may be hosted, Braintrust and LangSmith deserve an actual workflow comparison with Langfuse; this research does not establish an unconditional winner.

**Q1.2 remains open.**

| User's hosting choice | Consequence |
|---|---|
| Only machines the user runs | Local runners and local MLflow/Phoenix/Workshop stay in scope; Langfuse needs another suitable machine. Hosted control planes and remote sandboxes require separate examination. |
| Hosted public-repository traces allowed | Hosted candidates enter scope only for approved non-Security data. A public repository does not itself make its Session logs public or grant upload permission. |
| Hosted private-repository traces also allowed | More non-Security Runs become eligible; pricing, retention and access control still need review. |
| Every branch | Security sessions, their evaluator inputs, explanations, datasets and derived grades stay off third-party eval services. |

**The next concrete comparison [interpretation].** Use the same small set of existing cases and arms. Measure integration effort, faithfulness to production CLI invocation, independent repeated trials, grade review, and useful comparison output. For a viewer, import one deliberately public/synthetic trajectory into local candidates and compare nested tools, token/timing fields, IDs and annotations. This is a proposed follow-up, not work authorized or run by this read-only research. Do not upload the existing replay corpus as a convenient demo dataset.

## 7. Uncertainties and live checks

- **Hosting permission:** still unanswered. No service can be selected on the assumption that public-repository traces may be uploaded.
- **First-party product transition:** OpenAI's official retirement dates and promptfoo migration are verified (§2.1). Continued existence of older API guides is not a basis for starting a new hosted-Evals integration; revalidate migration behavior and graders.
- **Subscription allowances:** adapter docs establish supported credential mechanisms, not which current allowance a trial consumes, whether the account has the model, or throughput limits **[needs live check]**. Preserve CLI-native auth; do not extract credentials into a provider adapter.
- **Runner integration:** promptfoo wrappers, Inspect's custom solver and native plugin scaffolding have not been exercised against thirdshift cases. Caching/repetition independence, leakage controls and blind grader behavior need validation.
- **Host resources:** no idle/RSS/ingestion/coexistence measurements exist for any candidate in this search. Native/no-Docker is a deployment fact, not a capacity benchmark. Shared memory/CPU with Factory builds matters.
- **Viewer completeness:** verify model/tool hierarchy, token/cache accounting, timestamps, score attachment, truncation and missing fields. No candidate was shown to parse all six thirdshift Session-log formats directly. Standard export does not recover fields absent from the source.
- **Feature splits:** verify the exact OSS/Cloud/enterprise edition before adoption, particularly TruLens lifecycle, MLflow advanced managed monitoring, Lunary editions and hosted custom evaluators. Screened candidates were not audited feature by feature.
- **Session-tool defaults:** Entire can put transcripts in Git checkpoint refs that travel on push; default public-repository checkpoint publication is unsuitable for private Session content. Git AI/ccusage adapter behavior and private-session filters still need validation against installed Harness versions. They are inputs, not quality-eval systems.
- **Prices:** prices are a dated screen, not a quote or normalized cost model. Spans, traces, observations, scores, events, processed bytes and inference are different billing units. No new monthly cost estimate was calculated.
- **Conference evidence:** the public schedule corroborates agenda and dates. Private notes informed questions; no public recording was verified for every substantive workshop remark. Vendor performance claims were not treated as independent measurements.
