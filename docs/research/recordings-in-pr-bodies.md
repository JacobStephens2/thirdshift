## TL;DR

- **What transfers from Ben Holmes / Warp Oz (Nov 2026) vs what does not:** Interactive clicking before PR review, a two-layer "how to boot/verify this repo" skill + onboarding seed bootstrap, and concise video walkthroughs trimmed of LLM think-time transfer directly. Docker-configured cloud VMs, `warp-xvfb-sidecar`, remote desktop takeover, and hosted Oz artifact storage do not transfer: `thirdshift` delivers via local **Worktrees** over shared `.git` across seven subscription-authenticated **Harnesses** ([run-isolation.md](run-isolation.md)), and `Q1.1`–`Q1.4` already settled headless web verification on local Fleet Worktrees / `#1486` `bwrap` (`§1`).
- **Browser driving must stay CLI/shell-driven, and interactive exploration should precede a clean walkthrough pass:** All seven `src/harness/*.rs` adapters run unattended shell commands in the Worktree with zero shared MCP configuration (`§2.1`). Meanwhile, `microsoft/playwright` `v1.64.0`'s `FfmpegVideoRecorder` (`videoRecorder.ts`) stamps frames by wall-clock elapsed time (`timestamp - _creationTimeMs`) and repeats frames across idle intervals — so recording during slow LLM turns injects 10–30+ s of frozen "dead air" per turn. Exploring interactively first and then running a clean continuous walkthrough script (as `playwright-cli` itself recommends) eliminates dead air, and Playwright `1.64.0` (already in `console/` and `site/`) natively supports VP9 `.webm` + `showActions` cursor/click markers (`§2.2`–`§2.4`). Transcoding `.webm` to H.264 `yuv420p` with `-movflags +faststart` gives reliable Safari/iOS playback and seeking (`§2.5`).
- **`bwrap --unshare-net` already provides an isolated loopback for dev server + browser, while Chromium flags and daemon cleanup need care:** `bubblewrap` `network.c` brings up `127.0.0.1` (`lo`) inside `--unshare-net`, completely disjoint from host loopback (`8711`, `2019`); `src/sandbox.rs` already sets `NO_PROXY=127.0.0.1,localhost` (`§3.1`). However, Ubuntu 24.04's AppArmor profile grants `userns` only to `/usr/bin/bwrap`, not Chromium (`eval-sandboxes.md §1`), so headless Chromium inside `bwrap` or `--unshare-user` will need `--no-sandbox` (`chromiumSandbox: false`) `[needs live check]` (`§3.2`). Concurrent Runs (`spec.parallel = 3`) require ephemeral ports and per-Worktree state (`§3.3`), and any foreground wrapper **must** kill its dev server and browser daemon on exit (`trap ... EXIT` / `close`), or `tests/background_work.rs` kills them and forces a wasted `Resume` (`§3.4`).
- **Major finding for `Q1.5` — GitHub shipped `gh --attach` in `v2.99.0` (2026-09-01), while raw GitHub / Gist URLs cannot play video inline:** The local Mac runs `gh 2.96.0` (pre-`--attach`), which is why `2023-recordings-in-pr-bodies.md` assumed `user-attachments` had no CLI path. Starting in `gh 2.99.0` (and `v2.103.2` for GitHub App tokens), `gh pr create/edit/comment --attach` uploads `.mp4`/`.webm` (up to 10 MB free / 100 MB paid) to `uploads.github.com/user-attachments/assets`, rendering an inline PR video player behind GitHub's own private-repo access control — with the trade-offs of requiring `gh >= 2.99.0` (`>= 2.103.2` for App tokens), write access, no GHES support, and **irreversible uploads with no delete endpoint** (`cli/cli` `attach.go`) (`§4.1`, `§4.6`).
- **How the four `Q1.5` options compare with concrete codebase & HTTP facts:**
  - **(a) `thirdshift console` + `#2036` `console report`:** Gives an in-browser `<video>` player behind `allowed_emails` sign-in, but `src/console.rs` currently caps bodies at `16 KiB` (`4 MiB` for `metrics::receive`), has **no HTTP `Range` / `206 Partial Content` streaming** (needed for `<video>` scrubbing and Safari), sets a 5 s `AFTER_COMMAND` push timeout, requires every PR teammate to onboard via Resend email code + password, needs video pruning, and does not serve external open-source PR reviewers cleanly (`§4.2`).
  - **(b) Dedicated unmerged git ref (`refs/thirdshift/evidence/...`) vs orphan branch (`refs/heads/...`):** Custom `refs/thirdshift/...` refs stay out of default `git clone`/`git fetch` (`+refs/heads/*:refs/remotes/origin/*`) and inherit GitHub permissions, **but live HTTP checks prove `raw.githubusercontent.com` serves `.mp4` as `application/octet-stream` and `.webm` as `audio/webm` + `Content-Disposition: attachment` with `X-Content-Type-Options: nosniff`**, and GitHub's blob UI renders no video player — so every link forces a download rather than playing in-browser, while bloating the repo's packfile (`§4.3`).
  - **(c) Configurable upload command/endpoint in `User config`:** Cleanest escape hatch for teams with S3/R2 + Cloudflare Access / Tailscale / internal SSO, at the cost of per-host config parity (`§4.4`).
  - **(d) Secret Gist (`#1092`):** Same `nosniff` / `attachment` forced-download headers as `raw.githubusercontent.com` for `.mp4`/`.webm`, plus zero viewer auth (`§4.5`).
- **Process, gating, Repairs, and `#2022`:** Putting UI verification inside a composable **Factory skill** (`Q1.6(a)`) matches `processes/ticket-run.toml` / `spec-run.toml` and ADR-0024 while allowing `Custom process` / **Experiment** isolation (`§5.1`). If `Self-merge` gating (`Q1.7(b)`) is wanted later, `Delivery`'s existing `merge_hold()` (`src/delivery.rs:1569`) is the clean Rust seam (`§5.2`). Crucially, `conflict_repair`, `ci_fix_repair`, and `review_repair` (`src/prompt.rs:825–937`) **do not** currently tell the agent to refresh PR visual evidence if a Repair edits UI code (`§5.3`), and normal `Review runs` forbid PR-body edits (`src/prompt.rs:565, 575`), confirming `Q1.8(a)` (`§5.4`).

## 1. Prior art and problem framing

### 1.1 Ben Holmes / Warp Oz (Nov 2026) and peer coding factories

Ben Holmes' November 2026 presentation and Warp write-ups on *"solving / addressing the code review bottleneck"* (`warp.dev`, referenced in `#2023` and grounded via Warp's blog and docs) frame agentic PR review around three levers: adversarial pre-human code review, **end-to-end verification with computer use**, and merge-risk scoring (`warp.dev` blog & `docs.warp.dev`). Warp's **Oz** cloud platform implements computer use by attaching an Xvfb sidecar container (`warpdotdev/warp-xvfb-sidecar:latest`) only when computer use is enabled, letting the agent drive graphical browsers/apps, take screenshots, and produce **annotated video artifacts** that render smooth synthetic cursor movements, clicks, and key presses while **trimming idle time**, attached to PRs and retrievable via `oz artifact get <ARTIFACT_UID>` (`docs.warp.dev`).

Peer cloud coding agents show the same product shape inside hosted VMs:
- **Cursor Cloud Agents** (`cursor.com` docs/announcements) run each agent in an isolated remote VM where it boots the app on `localhost`, clicks through UI flows, inspects console/network errors, and attaches video recordings and screenshots directly to the PR, with remote desktop takeover if human intervention is needed.
- **Devin** (`docs.devin.ai`) spins up local services in its cloud VM, executes a test plan from the PR diff, records a video of the browser interaction, and exposes an **Interactive Browser** tab for saving authenticated staging profiles or clearing MFA/CAPTCHAs.
- **Browser CLI tooling (`vercel-labs/agent-browser` v0.43.0, `microsoft/playwright-cli` v0.1.25):** Rather than pixel-coordinate OS computer use over X11, both Vercel and Microsoft built shell-driven browser CLIs that return compact accessibility-tree refs (`@e1`, `e2`), avoid MCP schema bloat, and integrate video capture directly (`agent-browser record start/stop --cursor`, `playwright-cli video-start --cursor` / `run-code`).

### 2.3 How Playwright `1.64.0` `recordVideo` and `page.screencast` work headlessly

Reading `playwright.dev/docs/videos`, `playwright.dev/docs/release-notes`, `playwright.dev/docs/api/class-browser`, `playwright.dev/docs/api/class-screencast`, and `microsoft/playwright` at tag **`v1.64.0`** (`packages/playwright-core/src/server/videoRecorder.ts` and `screencast.ts`) establishes:

1. **No X11 / Xvfb required:** `chromium.launch({ headless: true })` (already used across `console/tests/*.cjs` and `site/tests/*.cjs`) streams Chromium DevTools `Screencast` JPEG frames directly into Playwright's `FfmpegVideoRecorder`, which spawns Playwright's bundled `ffmpeg` reading a minimal Matroska pipe (`-f matroska -i pipe:0`) and encoding **VP9** `.webm` (`-c:v libvpx-vp9 -deadline realtime -cpu-used 8`, upgraded from VP8 in Playwright `1.64`; `videoRecorder.ts:187–210`, `release-notes` 1.64).
2. **Finalization on `context.close()`:** `startAutomaticVideoRecording` attaches `VideoRecorder` when a page starts and writes frames continuously, **but the `.webm` file is only flushed and valid after `await context.close()`** (`playwright.dev/docs/videos`, `videoRecorder.ts:69–81, 261–280`). For `page.screencast.start({ path })` (added in `v1.59`), `await page.screencast.stop()` closes the stream without tearing down the context (`screencast.ts`, `release-notes` 1.59). Reading the file before `close()`/`stop()` yields a truncated or unplayable `.webm`.
3. **Playwright Trace `.zip` (`context.tracing`):** `await context.tracing.start({ screenshots: true, snapshots: true })` / `stop({ path: 'trace.zip' })` records action timelines, before/after DOM snapshots, network request/response headers & bodies, and console errors (`class-tracing.md`). Trace zips are compact and high-signal for debugging, though reviewers must load them in Playwright Trace Viewer rather than playing them directly in a browser.

### 2.4 Wall-clock "dead air" and cursor/click overlays

- **Why live-during-exploration recording creates "dead air":** In `microsoft/playwright@v1.64.0` `packages/playwright-core/src/server/videoRecorder.ts:169–170, 251, 272–273`:
  ```ts
  // "-r 25" forces a constant output frame rate; ffmpeg duplicates frames as needed based on
  //   the input timestamps, so we don't have to repeat frames ourselves.
  this._emitFrame(frame, timestamp - this._creationTimeMs);
  ```
  Playwright encodes **real wall-clock elapsed milliseconds** (`timestamp - _creationTimeMs`) into every Matroska cluster header (`agent-browser`'s `recording.mdx` likewise states: *"The latest Chrome frame is held between repaints so the file duration matches wall clock"*). If an agent starts recording and then spends 15–30 seconds per LLM turn reading accessibility snapshots and reasoning between shell commands, a 6-step verification becomes a 2-minute video composed 90% of frozen frames.
  **Two-phase pattern:** `microsoft/playwright-cli`'s own `video-recording.md` prescribes separating exploration from recording: (1) drive the app interactively (inspecting DOM/snapshots, console errors, network requests, edge cases, and gathering stable locators), then (2) execute a single continuous walkthrough script (`node walkthrough.mjs` or `playwright-cli run-code --filename=...`) with deliberate short human-readable pacing (`pressSequentially` / 300–800 ms pauses). This yields crisp 10–30 second walkthroughs with zero LLM think-time dead air, and keeps each walkthrough reproducible.
- **Cursor and click indicators:** In older Playwright (`< 1.59`), `recordVideo` captured raw headless pixels with no cursor, requiring an injected `page.addInitScript` DOM overlay (`pointer-events: none` element tracking `mousemove`/`mousedown`). In **Playwright `1.64.0`** specifically (already in `console/` and `site/`), both `browser.newContext({ recordVideo: { dir, size, showActions: { cursor: 'pointer', duration: 800, style: { point, highlight, title } } } })` and `page.screencast.showActions(...)` natively render an animated cursor that travels along a curved/eased path, survives navigations, and draws click-point rings, target highlights, and action titles (`class-browser`, `class-screencast`, `release-notes` 1.64, `videoRecorder.ts:98–99`). If a target repo pins Playwright `< 1.59` (or uses raw CDP), a small `addInitScript` inert cursor/ripple overlay remains a ~30-line fallback.

### 2.5 `.webm` vs `.mp4` transcoding with `ffmpeg`

Playwright writes `.webm` (VP9 in `1.64.0`), and GitHub `--attach` accepts `.webm` (`cli/cli` `userasset.go:34`). However:
- GitHub Docs (*Attaching files*) explicitly advise: *"Video codec compatibility is browser specific, and it's possible that a video you upload to one browser is not viewable on another browser. At the moment we recommend using H.264 for greatest compatibility."*
- Safari / iOS WebKit historically lack consistent native VP9-in-WebM support for inline `<video>` playback (especially seeking), whereas **H.264 (`libx264`) in `.mp4` with `-pix_fmt yuv420p` and `-movflags +faststart`** is universally playable across macOS/iOS Safari, Chrome, and Firefox (`MDN`, `.agents/skills/explainer-video/REFERENCE.md:54`).
- Crucially, `-movflags +faststart` relocates the MP4 `moov` atom (index metadata) from the end of the file to the start, allowing HTML5 `<video>` players (especially Safari) to start playback and scrub immediately via initial `Range` requests instead of downloading the whole file (`MDN`). Adding keyframe spacing (e.g., `-g 15 -keyint_min 15 -sc_threshold 0` as noted in `.agents/skills/explainer-video/REFERENCE.md:54`) also avoids coarse 8-second scrub jumps. Note that `agent-browser`'s built-in `.mp4` command (`cli/src/native/recording.rs:768–795`) passes `-pix_fmt yuv420p` but **omits** `-movflags +faststart` `[observed in source]`. Note also that Playwright bundles its own `ffmpeg` binary inside the Playwright browser cache (`videoRecorder.ts:47`), whereas system `ffmpeg` on `PATH` may or may not be installed on every Fleet host `[needs live check]`.

## 3. Local Worktree, concurrency, bootstrap, and `#1486` `bwrap` Run sandbox interactions

### 3.1 Loopback inside `--unshare-net` (dev server + Chromium without touching host `8711`)

In `src/sandbox.rs:749–766`, `base_argv()` launches `bwrap` with `--unshare-pid`, `--unshare-ipc`, `--unshare-uts`, `--unshare-net`, `--die-with-parent`, `--new-session`, `--dev /dev`, `--proc /proc`, and `--tmpfs /tmp`.

Inspecting `containers/bubblewrap`'s `network.c:125–225` (`loopback_setup()`) confirms that whenever `--unshare-net` is active, `bwrap` itself configures and brings up the `lo` interface (`127.0.0.1/8`, `IFF_UP`) via `AF_NETLINK` inside the new network namespace. That namespace has its own loopback and abstract Unix socket space, completely isolated from the host's `127.0.0.1:8711` (**Console**) and `127.0.0.1:2019` (Caddy admin API) ([eval-sandboxes.md §1](eval-sandboxes.md)).

- `src/sandbox.rs:575–581, 644–656` already relies on this: its `socat` relay listens on `127.0.0.1:3128` inside `--unshare-net` and sets `NO_PROXY=127.0.0.1,localhost` / `no_proxy=127.0.0.1,localhost`.
- Therefore, a dev server and headless Chromium launched inside the same sandbox session talk directly on `127.0.0.1:<ephemeral-port>` **without** hitting `src/proxy.rs:253–273`'s `address_refusal` ("the name resolves to loopback") and **without** reaching host loopback listeners.
- **Gotcha to guard against:** Because `HTTPS_PROXY`/`HTTP_PROXY` point to the relay inside `bwrap`, any Playwright/Chromium launch or `curl` check against `127.0.0.1` relies on honoring `NO_PROXY=127.0.0.1,localhost` (or passing `--proxy-bypass-list=<-loopback>` if Chromium's proxy handling ignores `NO_PROXY` in a given config `[needs live check]`).

### 3.2 Headless Chromium inside `bwrap`: user namespaces, AppArmor, and `/dev/shm`

- **User namespaces & `--no-sandbox`:** On Ubuntu 24.04 (`kernel.apparmor_restrict_unprivileged_userns = 1`), `thirdshift`'s host AppArmor policy grants `userns,` only to `/usr/bin/bwrap` (`/etc/apparmor.d/bwrap`; [eval-sandboxes.md §1](eval-sandboxes.md)). Chromium's own chrome binary is not covered by `/etc/apparmor.d/bwrap`, and if a future `#1486` Run sandbox also adopts `--unshare-user` + `--cap-drop ALL` (as `src/sandbox/triage.rs:46–58` does), nested unprivileged user namespaces for Chromium's renderer sandbox fail unless Chromium is given `--no-sandbox` (Playwright `chromiumSandbox: false` or `args: ['--no-sandbox']`). `[needs live check]` on Ubuntu 24.04 inside `bwrap`. (Playwright's Docker docs explicitly note disabling Chromium's inner sandbox is standard when driving trusted first-party tests inside an outer container/sandbox boundary, while warning against browsing untrusted public sites.)
- **`/dev/shm` and `--unshare-ipc`:** Reading `containers/bubblewrap` `bubblewrap.c:1433–1467` (`SETUP_MOUNT_DEV`) shows that `--dev /dev` mounts a fresh `tmpfs` with `size=0` (Linux kernel default limit = 50% of physical RAM, **not** Docker's 64 MB cap) and creates `/dev/shm` (`0755`) inside it, while `--unshare-ipc` isolates POSIX/SysV IPC from the host.
  - Note **two nuances** on the 4-core / 8 GB Fleet host (`eval-sandboxes.md §1`: 7,941 MiB RAM, 1.8 GiB swap): (1) Chromium `/dev/shm` usage comes directly out of host RAM/swap (`tmpfs`), and passing `--disable-dev-shm-usage` merely moves those files to `/tmp` — which in `src/sandbox.rs:761–762` is *also* a `--tmpfs /tmp`! So `--disable-dev-shm-usage` does not save RAM inside `bwrap` unless `/tmp` is disk-backed, though `/dev/shm` permissions (`0755` vs `1777` sticky, fine for single-UID `bwrap`) should be smoke-tested `[needs live check]`. (2) `src/resources.rs` checks available RAM, load, and disk (`DEFAULT_MIN_AVAILABLE_DISK_MB = 5120`) before each session (`src/session.rs`), but Chromium + dev server spikes during a session are unmeasured unless `systemd-run --user --scope` caps are wired ([run-isolation.md §8.1 Q10](run-isolation.md)).

### 3.3 Concurrent Runs (`spec.parallel = 3`, `command_limit = 1`)

`src/config.rs:186–188` defaults `spec.parallel = 3` and `pass.command_limit = 1`. Up to three child Ticket worktrees (`<repo>-issue-<n>`, `src/worktree.rs:220`) run concurrently on the same machine, and different repositories or explicit CLI commands can run concurrently as well. Any UI-verification bootstrap that hardcodes:
- a dev server port (e.g., `:3000`, `:5173`, or `8711` colliding with a live host Console when unsandboxed),
- a shared SQLite/tmp DB path or fixed Docker Compose project name/port mapping (`keeplore` in `eval-sandboxes.md §1`), or
- a shared `/tmp/walkthrough.webm` filename (outside `bwrap`, where host `/tmp` is shared; inside `bwrap`, `--tmpfs /tmp` isolates `/tmp`),

will race and corrupt concurrent Runs. `console/tests/` (`console/README.md:14–15`) and `site/tests/README.md:12` already model the right rule: bind `127.0.0.1:0` (or pick a free ephemeral port), isolate `HOME`/DB/state inside a `mktemp -d` directory, and name all temporary artifacts with `mktemp`.

### 3.4 Leftover background servers & browser daemons trigger `Resume`

`tests/background_work.rs:1–5` and `GLOSSARY.md:100–101` (**Resume**) establish a critical lifecycle constraint: if an agent session ends its turn while *any* child process it started (such as a backgrounded dev server, `playwright-cli` daemon, or `agent-browser` daemon) is still alive, `thirdshift` kills the leftover process along with the session and triggers **one `Resume`** prompting the agent (`src/prompt.rs:941–953`) to re-run it in the foreground; if the Resume also leaves background work running, `thirdshift` logs the killed work and carries on, blaming it if the Run subsequently fails.

- **Critical interaction with daemonized CLIs:** Both `playwright-cli` (`README.md`) and `agent-browser` (`README.md`) spawn a background browser daemon on first command with a **1-hour idle timeout** (`--idle-timeout`). If an agent runs `playwright-cli open` / `agent-browser open` and forgets `playwright-cli close-all` / `agent-browser close` before ending its turn, `thirdshift` will detect the live daemon, kill it, and burn a full `Resume` round-trip!
- **Safe execution pattern:** Either (a) wrap the dev server and browser verification in a single foreground script with `trap 'cleanup...' EXIT` (exactly as `agent-browser`'s own `recording.mdx` CI recipe shows: `trap 'agent-browser record stop 2>/dev/null || true; agent-browser close 2>/dev/null || true; kill "$SERVER_PID" ...' EXIT`), or (b) have the **Factory skill** require explicit teardown (`close` + server `kill` + `wait`) and verification that no background job remains before ending the turn.

### 3.5 Fresh `git worktree` onboarding (`Q1.4`: two-layer contract vs `User config`)

`src/worktree/acquisition.rs:69–85` runs `git worktree add` directly from the fetched base commit. A fresh Worktree contains **only git-tracked files**: untracked `.env` / `.env.local` files, `node_modules/`, seed SQLite DBs, and Rust `target/` builds present in the **Launch directory** are absent.

Comparing the two-layer repo contract (`Q1.4` agreed) against `User config`:
- **Repository layer (versioned in git):** Target repositories can commit both (1) a repo skill under `.agents/skills/<name>/SKILL.md` or `.claude/skills/<name>/SKILL.md` (both automatically discovered by `src/skills.rs:123` and linked for every Harness) holding app routes, dev-server commands, faux-user selectors, and "learned gotchas", and (2) an idempotent bootstrap/seed script that installs/links deps if needed, seeds deterministic faux data into per-Worktree isolated storage, starts the app on an ephemeral port, runs the walkthrough, and tears down cleanly on `EXIT`.
- **Host secrets / non-committed test credentials:** Non-committed staging/test credentials (if a repo cannot seed purely faux local auth) must live outside git on the Fleet host (e.g., `~/.thirdshift/...` or environment config). Note the `#1486` interaction: `src/sandbox.rs:589–596, 689–693` uses `bwrap --clearenv` and mounts only explicitly listed paths. Once `#1486` enables a `bwrap` **Run sandbox**, any host-side test credential file or env var needed by a repo's bootstrap script will be invisible unless `Run sandbox` config explicitly permits/binds it `[interpretation]`.

### 4.1 GitHub PR Markdown & `user-attachments`: the `gh v2.99.0` `--attach` shift

Verified directly from GitHub Docs (`attaching-files`, `attaching-files-with-github-cli`, `basic-writing-and-formatting-syntax`), `cli/cli` source (`v2.99.0`–`v2.105.0`), and live `curl -sI` responses on `github.com` and `raw.githubusercontent.com`:

### 4.2 Option (a): `thirdshift console` (`https://<console>/...`) + `#2036` `console report` outbound push

Checked in `src/console.rs`, `src/console/auth.rs`, `src/console/accounts.rs`, `src/console/auth/password.rs`, `src/console/tokens.rs`, `src/console/report.rs`, `src/console/metrics.rs`, `src/console/assets.rs`, `src/console/install.rs`, `src/config/console.rs`, and `Cargo.toml`:

- **Body limits & timeouts:** `src/console.rs:1310` sets a global `DefaultBodyLimit::max(16 * 1024)` (16 KiB) across the Axum `0.8.9` router; `metrics::receive` raises it to `4 * 1024 * 1024` (4 MiB, `src/console/metrics.rs:445`) and `plan_usage::receive` to `256 * 1024` (`src/console/plan_usage.rs:227`). Accepting video uploads (e.g., 10–50 MiB) requires a dedicated upload route with a raised body limit (or streaming to disk via `BodyDataStream` rather than buffering full `Bytes` in RAM on an 8 GB host). Furthermore, `src/console/report.rs:21` caps `AFTER_COMMAND` outbound pushes at **`5 seconds`** (and `BY_HAND` at `10 seconds`), which is too tight for a multi-MB video upload from `lima-thirdshift` over slow Wi-Fi.
- **No HTTP `Range` / `206 Partial Content` streaming exists yet:** `Cargo.toml:17` uses `axum 0.8.9` with `default-features = false` and **no `tower-http`** (`ServeFile`/`ServeDir`). `src/console.rs:1740–1781` (`asset()`) reads entire files into `Vec<u8>` (`Body::from(bytes)`) with no `Range` header handling, no `Accept-Ranges: bytes`, and no `206 Partial Content` / `Content-Range` response. Per MDN and Safari WebKit playback rules (`§2.5`), browsers — especially Safari/iOS — require `Accept-Ranges: bytes` + `206 Partial Content` to seek/scrub HTML5 `<video>` (and Safari frequently stalls or re-fetches without `206` support). Also note `src/console/auth.rs:535–539` sends `default-src 'self'` CSP and `X-Content-Type-Options: nosniff`, so served files must return exact `video/mp4` / `video/webm` `Content-Type` (or `image/png` for thumbnail previews).
- **Reverse proxy (`src/console/install.rs`):** Caddy (`flush_interval -1`) and Apache (`ProxyPass`) sit in front of `127.0.0.1:8711` (`src/console.rs:1100`); Caddy imposes no default small body limit that blocks 10–50 MB uploads `[unverified for Apache LimitRequestBody]`.
- **`allowed_emails` teammate auth friction & public-repo mismatch:** `src/console.rs:1088`, `src/config/console.rs:50`, `src/console/accounts.rs:17`, and `src/console/auth/password.rs:73, 87–90` enforce email-allowlist sign-in: every viewer clicking a PR link must be added to `console.allowed_emails` in `User config`, receive a 15-minute Resend verification code (`ResendKey`), set a Console password, and keep a 30-day `__Host-thirdshift-session` cookie (`SameSite=Strict`, `auth.rs:128` — note `SameSite=Strict` means clicking a link from `github.com` in a fresh tab triggers an extra redirect or cookie edge case if not careful `[needs live check]`!). For **public repositories** (`JacobStephens2/thirdshift`), external open-source reviewers are not on `allowed_emails` and cannot watch Console-gated videos at all unless Console adds per-recording public/repo-visibility exceptions or public PRs continue using Gist/`gh --attach`.
- **Disk retention & pruning:** Neither `.command.json` nor `logs/fleet-metrics/` is pruned automatically today (`2036-console-metrics.md:43`). Storing 5–20 MB recordings per UI PR on the 154 GB Console VM (`eval-sandboxes.md §1`: 32 GB free) requires explicit TTL or count-based pruning (e.g., delete recordings older than N days or after PR merge/close) plus a `Scope::Report` holder-scoped storage directory so `lima-thirdshift` (`report` token) cannot overwrite other hosts' recordings.

### 4.3 Option (b): Dedicated unmerged git ref (`refs/thirdshift/evidence/...`) vs orphan branch (`refs/heads/...`)

Checked against `git-clone.adoc`, `git-fetch`, `git-gc`, `docs.github.com` (*Repository limits*, *Working with non-code files*), and live `curl -sI` tests on `github.com` and `raw.githubusercontent.com`:

- **Default clone/fetch behavior:** `git clone` initializes `remote.origin.fetch` to `+refs/heads/*:refs/remotes/origin/*` (`git-clone.adoc:38–39`). Pushing PR evidence to an **orphan branch under `refs/heads/...`** causes every developer `git fetch` and CI checkout to download all media blobs by default and clutters branch lists. Pushing to a **custom ref outside `refs/heads/`** (e.g., `refs/thirdshift/evidence/<pr-or-branch>`) keeps normal `git clone` and `git fetch` clean and leaves `scripts/affected-tests` untouched.
- **GitHub GC & UI visibility:** Because a custom ref is a real Git reference in the remote repository, commits reachable from it are protected from `git gc --prune` (`git-gc`) until the ref is deleted. However, GitHub's branch/tag UI dropdowns only list `refs/heads/*` and `refs/tags/*` (`github.com` custom-ref browsing requires explicit SHA URLs like `/blob/<sha>/...` or `raw.githubusercontent.com/<owner>/<repo>/<sha>/...`; whether GitHub's internal server-side GC treats custom `refs/thirdshift/*` identically to `refs/heads/*` over multi-year retention is `[needs live check]`).
- **Disqualifying playback behavior observed live (`curl -sI`):**
  - On `github.com/<owner>/<repo>/blob/<sha>/...mp4`: GitHub's *Working with non-code files* list includes PNG, JPG, GIF, PSD, SVG, STL, CSV/TSV, PDF, GeoJSON, Jupyter, and Mermaid — **no `.mp4` or `.webm`**. The blob page renders a download / "View raw" link, not an inline video player.
  - On `raw.githubusercontent.com/...` (observed live against `microsoft/playwright@v1.64.0` `tests/assets/movie.mp4` and `movie.webm`):
    - `.mp4` returns `content-type: application/octet-stream`, `x-content-type-options: nosniff`, `content-security-policy: default-src 'none'; style-src 'unsafe-inline'; sandbox`.
    - `.webm` returns `content-type: audio/webm` (not `video/webm`), **`content-disposition: attachment; filename=...`**, and `x-content-type-options: nosniff`.
  - **Consequence:** Clicking either a `blob` or `raw` URL for `.mp4`/`.webm` **forces a file download to the reviewer's disk** rather than playing inline in the browser! Only `.gif` (with `image/gif`, capped practically at low-fps/short clips and up to 10 MB in GitHub attachment limits) or `.png` renders inline.
- **Repository bloat:** GitHub enforces a 100 MB single-object hard cap (1 MB recommended) and 2 GB push limit (*Repository limits*). Accumulating video blobs in the target repository's object store slows server-side repacks and requires force-deleting refs + GitHub support/maintenance to reclaim space, even when excluded from default clone refspecs.

### 4.4 Option (c): Configurable upload command / endpoint in `User config`

Delegating upload to a user-configured shell command or HTTP endpoint in `~/.thirdshift/config.toml` (e.g., an S3/R2 bucket behind Cloudflare Access / employer SSO, an internal Tailscale media host, or a Console endpoint), with `gh --attach` or secret Gist fallback when unset:

### 4.5 Option (d): Secret git-pushed Gist (`#1092` baseline)

`skills/thirdshift-pr/SKILL.md:193–257` pushes `.png`/`.gif` files to a secret Gist (`gh gist create` + `git push`) and embeds `https://gist.githubusercontent.com/<owner>/<id>/raw/<sha>/<file>`:

### 5.1 `Process` placement (`Q1.6`) and `Spec run` interaction

- `processes/ticket-run.toml:7–25` runs `implement` → `security-review` → `delivery` → `self-merge` (`src/processes/ticket.rs`, `src/delivery.rs:795–820`).

- **Why `Q1.6(a)` (composable Factory skill, no new `Step` in `ticket-run.toml` / `spec-run.toml`) fits best:**
  1. Most Runs touch backend/CLI code, so an unconditional cold `verify-ui` session `Step` adds session startup overhead and token cost even when skipped.
  2. The implementing (`src/prompt.rs:431–434, 494–504`) or `spec_review` (`src/prompt.rs:689–699`) session already has the branch built, dependencies warm, and the exact UI flows in context.
  3. Making it a standalone **Factory skill** (e.g., `thirdshift-verify-ui`, called by `thirdshift-implement`, `thirdshift-diagnosing-bugs`, `thirdshift-pr`, and `spec_review`) preserves composability: a **Custom process** or **Experiment** **Arm** can still run it as its own isolated `[[steps]] skill = "thirdshift-verify-ui"` **Step** later (`src/processes.rs:175`) to measure whether a cold verification session earns its extra cost.
- **Spec run subtlety:** Child **Ticket runs** inside a **Spec run** target the **Spec branch** (`gate_self_merge_on(spec_pr)`, `src/pull_request.rs:216`). Their Ticket PRs merge into the Spec branch, and then `spec_review` (`src/prompt.rs:699`) rewrites the whole **Spec PR** body (*"Update PR {pr_url} using the `thirdshift-pr` skill, rewriting its body to cover the whole Spec"*). Thus `spec_review` is where the end-to-end Spec walkthrough recording belongs for the human reviewer's final Spec PR.

### 5.2 `Self-merge` gating (`Q1.7`)

`Delivery` already has a clean deterministic merge-hold mechanism (`MergeHold { reason }`):
- `src/delivery.rs:1569–1636` checks `merge_hold()` immediately before calling `gh pr merge` (`src/delivery/repair_loop.rs:146–148`), holding **Self-merge** for `protected_paths` (`protected_hold`) while leaving the PR ready for review (never converting it back to draft or triggering `Failed ticket run`, `src/delivery.rs:958`; `GLOSSARY.md:250`). `SecurityOutcome::hold` (`src/processes/review.rs:577–581`, `src/delivery.rs:958`) uses the same hold pattern.
- **Constraint on mechanical gating (`Q1.7(b)`):** Rust cannot reliably classify arbitrary target-repo diffs as "UI-changing" across languages without heuristics or explicit per-repo opt-in (e.g., repo-configured UI file globs or an opt-in verification config). Without opt-in globs, starting with `Q1.7(a)` (require recording when supported; allow Ready-for-review with an explicit `## Evidence` limitation, matching `#1092`) avoids false `agent-failed` holds on unconfigured repos; if later opting in `Self-merge` UI repos (`Q1.7(b)`), `merge_hold()` checking for a recording URL (or absence of a limitation bypass) when diff paths match the repo's UI globs fits `Delivery`'s existing architecture cleanly.

### 5.3 Stale-recording refresh across `Continuations`, `Security reviews`, and `Repairs`

Reading `src/prompt.rs` and `src/delivery.rs` reveals an important asymmetry:
- **`Continuation` (`src/prompt.rs:467–475, 492–505`)**: Explicitly instructs *"Update PR {url} using the `thirdshift-pr` skill, rewriting its body to cover the whole branch"* — so Continuations naturally refresh screenshots and walkthrough recordings.
- **`Security review` (`src/prompt.rs:981–989`)**: Tells the session to update `Unaddressed findings` while preserving *"the rest of the body"*; if it commits a UI security fix, it does not re-record the walkthrough.
- **`Repairs` (`conflict_repair` `:825–847`, `ci_fix_repair` `:852–902`, `review_repair` `:907–937`)**: None of the three Repair prompts invoke `thirdshift-pr` or mention refreshing visual evidence (`review_repair` `:926` says *"If there is no new review information, leave the PR body unchanged"*, `ci_fix_repair` `:891` mentions only adding `"CI notes"`), and `Delivery::repair` (`src/delivery.rs:1519–1537`) only runs `refresh_built_with()` afterwards.
- **Implication:** If a `Security review` or `CI-fix` / `Conflict` / `Review` **Repair** modifies UI files after the opening session created the PR and recording, the PR body's recording becomes stale unless either (1) `Repair` / `security_review` prompts instruct refreshing visual evidence when their diff touches UI files, or (2) a post-edit check/hold flags stale recordings.

### 5.4 Reusing the path for `#2022` (`Review run` backfill, `Q1.8`)

Confirmed in `processes/review-run.toml`, `src/processes/review.rs:128–146, 545–608`, `src/processes/review/delivery.rs:20–113`, and `src/prompt.rs:564–646`:
- `--recommend-only` (`prompt.rs:565`) forbids changing files, committing, pushing, or editing the PR; `Address` mode (`prompt.rs:575`) forbids pushing or editing the PR (*"thirdshift pushes fixes without force and posts your final report as a comment"*).
- `src/processes/review/delivery.rs:102–107` only posts a review comment (`github.comment_review`), with no PR-body update path, and enforces strict captured-head checks (`unchanged` / `unchanged_head` in `review.rs:553, 563` and `delivery.rs:62, 88–111`) so concurrent author pushes are never overwritten.
- Settling hosting and recording in `#2023` first (`Q1.8(a)`) avoids implementing secret-Gist `.png` backfill in `#2022` only to replace it once `#2023` lands, while `#2022` still owns deciding how `Review run` posts backfilled evidence (updating the PR body safely under captured-head guards vs attaching to the review comment) and keeping `--recommend-only` read-only.

## 6. Concrete takeaways for the `#2023` grill (`Q1.3`–`Q1.9` and Round 2)

1. **`Q1.5` (open) needs `gh >= 2.99.0 --attach` put explicitly on the table before settling Console or Gist:** The earlier grill summary stated `user-attachments` had no CLI API (true for the local `gh 2.96.0`, false since `gh 2.99.0` on 2026-09-01 and `v2.103.2` on 2026-10-23). Meanwhile, Option (b) (`refs/thirdshift/...` + `raw.githubusercontent.com`) and Option (d) (secret Gist) **cannot play `.mp4`/`.webm` in a browser** due to live-observed `nosniff` + `application/octet-stream` / `audio/webm` + `Content-Disposition: attachment` headers, and Option (a) (`thirdshift console`) requires adding HTTP `Range` / `206` streaming, raising body limits, lengthening the 5 s `AFTER_COMMAND` push timeout, video pruning, and resolving public-repo auth.
   - **Actionable grill comparison:** Compare **(e) `gh >= 2.99.0 --attach`** (native inline PR video player, zero infra, GitHub repo permissions on private repos, **caveat:** irreversible uploads and `gh` upgrade across Fleet + `uploads.github.com` in `#1486` allowlist) vs **(a) `thirdshift console`** (revocable/prunable self-hosted storage, **caveat:** `Range`/`206`, teammate email onboarding, public-repo exception) vs **(c) configurable upload hook** (team S3/R2/SSO, revocable/expirable, zero Rust media code).
2. **`Q1.6` (open):** Keep `(a)` — composable **Factory skill** inside `implement`, `diagnosing-bugs`, `pr`, and `spec_review`, with `Custom process` `skill` step readiness (`DraftKind::Skill`) preserved under ADR-0024.
3. **`Q1.7` (open):** Keep `(a)` initially (require when supported, explicit `## Evidence` limitation otherwise), and record `Delivery::merge_hold()` (`src/delivery.rs:1569`) as the exact seam if `(b)` opt-in `Self-merge` gating is desired for UI repos.
4. **`Q1.8` (open):** Keep `(a)` — settle `#2023`'s capture and hosting contract before implementing `#2022` `Review run` backfill.
5. **`Q1.9` (open):** Keep `(a)` (**Visual evidence**, **walkthrough recording**, **UI verification**; `_Avoid_`: *computer use*, *test skill*, *video artifact*, *app harness*). Add **Visual evidence** to `GLOSSARY.md` only if `thirdshift` owns hosting (`Q1.5(a)`/`(c)`) or gating (`Q1.7(b)`).
6. **Round 2 concrete design points from this research:**
   - **Browser tool & dead-air control:** Standardize on **Playwright `1.64.0`** (already in `console/` and `site/`, zero MCP dependency across 7 Harnesses; optional `@playwright/cli` or `agent-browser` noted as ergonomic explorers), mandating a **two-phase workflow** (explore interactively first, then record a continuous walkthrough pass with `showActions` cursor/click markers or inert DOM cursor overlay) plus `ffmpeg` transcode to H.264 `yuv420p` `-movflags +faststart` `.mp4` for Safari/cross-browser playback.
   - **Process hygiene (`tests/background_work.rs`):** Require `trap` cleanup / explicit daemon `close` and foreground server teardown before turn end so neither leftover dev servers nor browser daemons trigger a spurious `Resume`.
   - **`bwrap` live checks (`[needs live check]`):** Verify Chromium `--no-sandbox` + `--proxy-bypass-list=<-loopback>` + `/dev/shm` inside `bwrap --unshare-net` on the Ubuntu 24.04 Fleet host, and decide how `#1486`'s `--clearenv` Run sandbox binds host-only non-committed test credentials for repo bootstrap scripts.
   - **Stale-recording refresh:** Decide in Round 2 whether UI-touching `Repair` / `security_review` prompts also refresh the walkthrough recording when they edit UI files after PR creation.
