# 1695 — Unattended triage of existing `needs-triage` issues

Issue: <https://github.com/JacobStephens2/thirdshift/issues/1695>

## Context

`#1323` introduced `thirdshift triage` for raw text Reports (from `--file <path>` or standard input), which investigates the Report read-only against the codebase, checks open issues for duplicates, and files new issues or comments on matching open issues.

`#1695` extends `thirdshift triage` to existing GitHub issues so that:
- `thirdshift triage <Issue URL or number> [base <branch>]` triages a specific existing issue in place on demand.
- `thirdshift triage [base <branch>]` (with no `<Issue>` and no Report on `--file` or non-empty stdin) runs as an unattended Pass suitable for `cron`, picking one eligible open `needs-triage` issue on the repository and triaging it in place.

---

## Round 1

❓ **Q1.1** - **Three entry modes for `thirdshift triage` (and cron's `/dev/null` stdin)**:
Should `thirdshift triage` select among its three modes as follows?
1. **Single-issue mode** (`thirdshift triage <Issue URL or number> [base <branch>]`): triages that existing GitHub issue in place against the Base branch.
2. **Report mode** (`thirdshift triage --file <path> [base <branch>]` or `... | thirdshift triage [base <branch>]` when non-terminal stdin has non-whitespace bytes): existing `#1323` behavior—investigates the Report, deduplicates against open issues, and creates a new issue or comments on a match.
3. **Pass mode** (`thirdshift triage [base <branch>]` with no `<Issue>` and no `--file`, when stdin is a terminal or 0-byte EOF as in `cron`): runs a single-issue Triage Pass that picks one eligible open `needs-triage` issue on the repository and triages it in place (exiting `0` cleanly when none is eligible).

➡️ Recommend **yes**.

💬 **A1.1**: Agreed.

❓ **Q1.2** - **Which issues an unattended Triage Pass may pick (and on-demand re-triage)**:
Should a Triage Pass consider an issue eligible only when:
1. It is an open issue in the repository with `needs-triage`, no other triage state label (`ready-for-agent`, `ready-for-human`, `needs-info`, `wontfix`), and no `in-progress` Claim;
2. Its author is a **Trusted account** (`OWNER`, `MEMBER`, or `COLLABORATOR`) and its title/body have not been edited by a non-Trusted account, with any non-Trusted comments filtered out of the session's view;
3. It is not a parent Spec that already has sub-issues; and
4. Eligible issues are ordered by `[pickup] order`?
And for on-demand `thirdshift triage <Issue URL or number>`, should it allow re-triaging an open issue regardless of its current triage state label while still enforcing the Trusted-account check on the issue content fed to the session?

➡️ Recommend **yes**.

💬 **A1.2**: Agreed.

❓ **Q1.3** - **What in-place issue triage writes to GitHub for each recommended state (and how `allow_ready_for_agent = false` avoids an infinite Pass loop)**:
Should in-place issue triage update `#N` by:
- Applying the recommended category label only if `#N` does not already carry a repository category label;
- Posting one comment (prefixed with `> *This was generated by AI during triage.*`) containing the `## Agent Brief` (`ready-for-agent`), the investigation summary + `## Questionnaire` (`ready-for-human` or `needs-info`), or the closure explanation (`wontfix`);
- Replacing `needs-triage` (or the prior triage state label in on-demand mode) with the target state label (`ready-for-agent`, `ready-for-human`, `needs-info`, or `wontfix`), and closing `#N` when `wontfix`; and
- When `triage.allow_ready_for_agent` is `false` (the default) and the session recommends `ready-for-agent` on an existing issue, posting the `## Agent Brief` comment (with a note that `ready-for-agent` was recommended) and transitioning `#N` to **`ready-for-human`** so a human can review and flip the label without the next Pass looping on `#N`?

## Round 2

❓ **Q2.1** - **Failed and Stopped issue Triage runs (`ready-for-human` + `agent-failed` vs infinite retry loop)**:
Should a failed or Stopped issue Triage run end its Claim as follows:
1. **Failed run:** transitions `#N` to `ready-for-human` and adds `agent-failed` (removing `in-progress` and `needs-triage`), so a single broken issue does not block or loop the cron job from triaging the remaining `needs-triage` issues, while `agent-failed` still counts toward `pickup.failure_limit` (after the Sweep clears any `agent-failed` issues the Day shift has acted on) to halt the Pass if a systemic failure hits `failure_limit` issues in a row.
2. **`thirdshift stop --requeue`:** restores `needs-triage` (removing `in-progress`, without `agent-failed`) so the next Pass can take `#N` again.
3. **`thirdshift stop` (without `--requeue`):** transitions `#N` to `ready-for-human` (removing `in-progress`, without `agent-failed`) so the operator who stopped it takes over without re-triggering the Pass.

➡️ Recommend **yes**.

💬 **A2.1**: Agreed — failed issue Triage runs change the label to `ready-for-human` and `agent-failed`.

❓ **Q2.2** - **Duplicate open issues and multi-issue / Spec splits when triaging an existing issue**:
When triaging an existing issue `#N` in place:
1. **Never create additional new issues automatically:** `#N` is updated in place (one entry in `recommendation.issues` representing `#N` itself). If `#N` is too large for a single Ticket or mixes multiple concerns that should be split into a Spec/Tickets, the session recommends `ready-for-human` on `#N` with a `## Questionnaire` proposing how to split or scope it.
2. **Duplicates of another open issue `#M`:** if `#N` duplicates an already-open issue `#M` in the repository, the session recommends `wontfix` on `#N` (explaining that it duplicates `#M` and closing `#N`), and may include `#M` in `recommendation.comments` to cross-reference `#N` or add any new details from `#N` onto `#M`.

➡️ Recommend **yes**.

💬 **A2.2**: Agreed.

❓ **Q2.3** - **Pass concurrency, Command limit, and draining a large `needs-triage` backlog via cron**:
When `thirdshift triage [base <branch>]` runs as a **Pass** (no `<Issue>` and no Report), should it behave like `fix` and `pickup` Passes:
- Checking `pass.command_limit` with `Sharing::UpToTheLimit`, running the Sweep, checking `pickup.failure_limit`, picking the next eligible `needs-triage` issue in `[pickup] order`, reserving and triaging it in place, and sending a Run notification only when an issue was taken (skipping cleanly with `activity.quiet_skips` when at the Command limit, at the Failure limit, or when no eligible `needs-triage` issue remains), so a recurring `cron` job works steadily through even a hundred `needs-triage` issues while stopping automatically if systemic failures reach `pickup.failure_limit`?

➡️ Recommend **yes**.

💬 **A2.3**: Agreed.

## Settled Summary

- **Three modes of `thirdshift triage` (Q1.1):**
  1. `thirdshift triage <Issue URL or number> [base <branch>]`: on-demand in-place triage of that open GitHub issue against the Base branch.
  2. `thirdshift triage --file <path> [base <branch>]` or `... | thirdshift triage [base <branch>]` (when non-terminal stdin has non-whitespace bytes): existing Report triage (`#1323`).
  3. `thirdshift triage [base <branch>]` (no `<Issue>`, no `--file`, and stdin is a terminal or 0-byte EOF as under `cron`): unattended Triage Pass.
- **Eligibility & ordering in Pass mode (Q1.2, Q2.3):**
  - Checks `pass.command_limit` (`Sharing::UpToTheLimit`), runs the Sweep, and checks `pickup.failure_limit`.
  - Considers open issues in the repository labelled `needs-triage` with no other triage state label (`ready-for-agent`, `ready-for-human`, `needs-info`, `wontfix`), no `in-progress` Claim, no `agent-failed`, not a parent Spec with sub-issues, and passing the Trusted-account check (`OWNER`, `MEMBER`, or `COLLABORATOR` author and no title/body edit by a non-Trusted account), ordered by `[pickup] order`.
  - On-demand `thirdshift triage <Issue URL or number>` can re-triage an open issue regardless of its current triage state label, while still enforcing the Trusted-account check and filtering out non-Trusted comments.
- **Reservation, Claim, Failure, and Stop lifecycle (Q1.4, Q2.1):**
  - Reserves the issue on `origin` across competing hosts and applies `in-progress` (removing `needs-triage` or the prior triage state label) while the Triage run is active.
  - On successful completion, replaces `in-progress` with the final triage state label (`ready-for-agent`, `ready-for-human`, `needs-info`, or `wontfix`, closing the issue when `wontfix`).
  - On a failed issue Triage run, replaces `in-progress` with `ready-for-human` and `agent-failed` so subsequent cron Passes continue triaging the rest of the `needs-triage` queue while `agent-failed` counts toward `pickup.failure_limit` to stop the cron Pass if systemic failures accumulate.
  - On `thirdshift stop --requeue`, replaces `in-progress` with `needs-triage` (no `agent-failed`). On `thirdshift stop` without `--requeue`, replaces `in-progress` with `ready-for-human` (no `agent-failed`).
- **In-place publication & `allow_ready_for_agent` (Q1.3, Q2.2):**
  - Updates `#N` in place (never creating new issues automatically; multi-issue/Spec splits are routed to `ready-for-human` with a `## Questionnaire`).
  - Applies the recommended repository category label only if `#N` does not already have one.
  - Posts a single AI-attributed comment (`## Agent Brief`, investigation + `## Questionnaire`, or `wontfix` explanation).
  - If `triage.allow_ready_for_agent` is `false` (and `--allow-ready-for-agent` was not passed) when `ready-for-agent` is recommended on an existing issue, posts the `## Agent Brief` comment (noting `ready-for-agent` was recommended) and labels `#N` `ready-for-human` so the Pass does not loop on `#N`.
  - If `#N` duplicates another open issue `#M`, recommends `wontfix` on `#N` (closing `#N`) and may post a cross-reference comment on `#M`.
- **Issue screenshots & images (Q1.5, Q2.4):**
  - Before starting the session, downloads HTTPS GitHub-hosted images (`github.com`, `*.githubusercontent.com`) referenced in the trusted issue body and trusted comments (up to 10 images, max 20 MiB each) into `.thirdshift-issue-images/` in the triage worktree and lists their local paths in `.thirdshift-issue.md` (warning and continuing if an image download fails).
