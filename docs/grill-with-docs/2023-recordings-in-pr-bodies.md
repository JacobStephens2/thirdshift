## Round 1 (answered)

**Q1.1 - What "computer use" means here: headless web browser vs virtual OS desktop.** Every UI repository the Fleet works on today (`thirdshift` Console and `site`, private employer web apps, and personal web apps) is a web application, and Playwright 1.64 is already used in `console/` and `site/` with built-in headless video capture (`recordVideo`). Full OS-desktop computer use (`Xvfb` + window manager + desktop app/browser + pixel-coordinate mouse/keyboard + `ffmpeg -f x11grab`) handles native desktop GUIs too, at the cost of X11 dependencies on every Fleet host, higher memory/CPU per Run, slower/flakier coordinate clicks than DOM/accessibility locators, and differing computer-use support across thirdshift's seven **Harnesses**. The options:
- (a) **Web browser UI verification first.** Target headless Chromium / browser-driven interaction and recording across all seven Harnesses; leave `Xvfb` virtual-desktop capture out of scope unless a native desktop GUI repository joins the Fleet.
- (b) **Full virtual desktop (`Xvfb` + `x11grab`) from the start**, so browser chrome and non-web GUIs share one screen-recording path.

*Recommended:* (a). Every target UI in play is web-rendered, headless Chromium runs cleanly on existing Linux Fleet hosts and inside `bwrap` without an X server, and Round 2 can pick the exact browser-driving mechanism so all seven Harnesses work uniformly.

*Answer:* agreed

**Q1.2 - What #2023 adds beyond #1092: interactive exploration + walkthrough recording vs scripted capture.** #1092 already updated `thirdshift-implement`, `thirdshift-diagnosing-bugs` and `thirdshift-pr` to require Before/After `.png` screenshots (or `.gif` recordings for interactive/animated flows) at `1440×900` desktop and `390×844` mobile, and #2265 (`87d9c019`) added visible bold `**Before — <flow>, <viewport>**` / `**After — <flow>, <viewport>**` labels above captures in `thirdshift-pr`. Ben Holmes' first note pushes past static captures: the agent should *click around the running app* like a human engineer ("did you run it on your machine?") and attach a video walkthrough of using the UI change. The options:

- (c) **Scripted capture is enough.** A single one-shot Playwright script that records the happy path satisfies verification without multi-step exploratory driving first.

*Recommended:* (a). Static side-by-side Before/After `.png`s remain faster to scan for pure CSS/layout diffs (Mayer's transient-information finding in `clear-architecture-diagrams.md`), while an exploratory check + recorded walkthrough solves the real review bottleneck on interactive UI changes.

**Q1.5 - Hosting recordings and what "viewable by team only, with built-in auth" means.** GitHub PR Markdown strips `<video>` tags and renders inline video players *only* for `https://github.com/user-attachments/assets/<uuid>`, which has no CLI or API upload path (browser session cookies only); every other `.mp4`/`.webm` URL renders in a PR body as a clickable permalink (optionally paired with an inline preview image). Meanwhile, #1092's **secret Gist** recipe has *no* viewer auth—anyone with the raw URL can read it, and files sit under the `gh` user's personal Gists—and thirdshift works on both **public solo repos** (`JacobStephens2/thirdshift`) and **private employer repos** (across shared employer Fleet hosts plus NATted `lima-thirdshift` on your MacBook) where teammates review PRs. The options:
- (a) **Serve recordings from `thirdshift console` (`https://<console>/...`) behind existing `Console account` sign-in (`allowed_emails`, ADR-0016/0026), with outbound push from NATted machines (`lima-thirdshift`) to a 24/7 Console hub (the `#2036` `thirdshift console report` pattern in `src/console/report.rs`, which already pushes both `Run metrics` and `Plan usage` outbound under the `report` scope after each Command).** Gives a real `<video>` player page with pause/scrubbing, zero third-party storage vendor, and built-in email-code sign-in; teammates who review PRs get `allowed_emails` access on a shared Console (and Round 2 settles whether public-repo PRs allow unauthenticated playback or keep Gists).
- (b) **Push recordings to a dedicated unmerged git ref / orphan store in the target GitHub repository itself** (e.g. outside `main` so the **Base branch** stays clean and `scripts/affected-tests` is untouched), linking the commit-pinned GitHub URL in the PR body. Viewer auth is **GitHub's own repository permissions** automatically—every repo collaborator who can read the PR already has access, works identically from `lima-thirdshift` and every Fleet host with zero extra accounts—at the cost of media blobs living in the remote repo's git store and GitHub's blob/raw handling instead of a custom player page.
- (c) **Configurable upload command / endpoint in `User config`** (targeting e.g. S3/R2 behind Cloudflare Access / employer SSO, an internal preview host, or a Console endpoint), falling back to secret Gists on public repos when unset.
- (d) **Keep #1092's secret Gist hosting (unlisted capability URL, no viewer login)** and drop the team-auth requirement.

*Recommended:* (a) if team reviewers can sign in to a shared Console (one self-hosted binary, real `<video>` player, no blobs in git); pick (b) if zero-friction access for every GitHub repo collaborator matters more than a custom player, or (c) if the team already has an internal SSO-protected bucket/host you want to target.

*Answer:* b

Full primary-source investigation saved in [recordings-in-pr-bodies.md](../research/recordings-in-pr-bodies.md). Key verified facts:

- **GitHub `gh --attach` vs raw GitHub / Gist headers (`§4.1`, `§4.3`, `§4.5`).** While this Mac runs `gh 2.96.0` (pre-`--attach`), `cli/cli` `v2.99.0` (2026-09-01) shipped repeatable `gh pr create/edit/comment --attach` and `v2.103.2` (2026-10-23, PR `#14804`) added `ghs_` GitHub App installation tokens, uploading `.mp4`/`.webm` (`<= 10 MB` free / `100 MB` paid) to `uploads.github.com/user-attachments/assets` for native inline PR `<video>` playback behind GitHub repository permissions — with irreversible uploads (no delete API, `attach.go:93`) and no GHES support.
