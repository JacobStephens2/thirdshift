# Settled by earlier answers (shout if any is wrong)

Part of the [#698 grilling](README.md).

- No write-up of a Security finding goes to a new third party. That's why a Security run's Run notification, which passes through Resend, carries only severity, title and link ([ADR-0015](../../../docs/adr/0015-security-findings-stay-private-until-fixed.md)). So Security sessions' logs and grades stay off any hosted eval service, whatever Q1.2 decides.
- **Order and Specs.** Four Specs, for Session traces, Experiments, the Scoring run and Run metrics, each with its own Tickets and all linked from #698 (Q4.13, Q7.4). All four are published together, as #921 allows. Session traces and Experiments are built in parallel (Q3.18), and Session traces come before the Console's log view and Waterfall are reworked (Q3.19). The Scoring run's Grader Ticket waits only for the Experiments Spec's sandbox Ticket, and its other Tickets can start at once. Only Run metrics' Session-trace Tickets wait for the Session-trace Spec. The Specs are written with `to-spec` and `to-tickets` once this grilling ends, and published as `docs/agents/triage-labels.md` says.
- Accuracy and quality come first. Efficiency (minutes, tokens, cost-equivalent) is measured and shown beside them, never folded into one score (Q1.1).
- A Run's outcome, its Repairs and its CI rounds don't count as evidence of quality on their own (Q1.1, and the triage notes on the issue).
- **Tools.** Packaged tools come before handrolling, but accuracy outranks that preference: Trials start sessions through thirdshift's own code (Q2.4). `thirdshift experiment` runs Experiments itself, in Rust, with no eval framework beneath it. Every framework leaves the parts that decide accuracy to thirdshift, and the retries, caches and timeouts they add are where silent inaccuracy comes from (Q5.6). The Console is the viewer (Q5.5). Langfuse is out for now (Q2.2); it and Grafana would need a bigger host, which you'd allow.
- **Nothing leaves the host but the sessions.** Eval data, Session traces included, stays on machines you run, and the eval framework, whichever it is, sends nothing anywhere (Q2.2, Q3.12). Only the Harness sessions talk to their providers: Trials and Graders do so just as Runs do. Hosted viewers are out unless a local one falls short (Q2.2).
- Eval sessions run through the Harnesses on your subscriptions, as Runs do, not on API keys: subscription auth came first in the Warp and OpenHands research. A tool feature that needs an API key, such as a hosted LLM judge, is out unless you choose to pay for API use.
- **Names (Q3.1, and in chat on 2026-10-21):** Eval, Eval suite, Eval task, Arm (the Baseline arm and the Candidate arm), Trial, Grader, Score, Experiment, Scoring run, Run metrics and Bug origin. Task became Eval task so it can't be read as a Ticket. Replay became Experiment and Grade became Score, to match the words eval tools use, and Eval now covers offline Experiments and the online Scoring run. #943 puts the 2026-10-21 changes into `GLOSSARY.md`. Round 7 adds Void Trial, Verdict and Bar, says a Trial belongs to its Experiment, which is a Command, though it writes no Command record of its own, and adds the Experiment to Command (Q7.3). They join #943 too, with ADR 0019's amendment for two files per session (Q5.9) and ADR 0016's for the Console's new actions (Q6.9).
- **Suites.** The first Eval suites are code review, which replays #429's 9 bugs in a review-only session (Q3.9), and Spec review, #429's 30 Spec branches (Q2.3). The plan-check suite waits for a plan check to exist (Q3.10). The implement session comes next, graded against the merged fix and its tests, then the Architecture review once its plans have graded Eval tasks. A Model change runs every suite that exists, and Security stays separate under ADR-0015 (Q3.20).
- **Trials.** Three per Arm on each code-review Eval task, and one on each Spec-review Eval task (Q3.2). An Experiment runs only the suites its change touches, and a change to a Harness, Model or Effort default runs every suite that uses it (Q3.3). Every Experiment runs the Baseline arm fresh beside the Candidate arm, which doubles its Trials (Q2.6).
- **The bar** is a standing default, fixed before each Experiment and never changed after it starts. The Candidate must be no worse than the Baseline on accuracy and on wrong findings. Efficiency is shown, but kept out of the bar unless the change is meant to save time or cost (Q3.4). "Worse" is measured by pairing the Arms on each Eval task, with a 95% Bayesian interval on the Candidate's pass share minus the Baseline's. The interval is a Dirichlet over the values each Eval task's difference can take, with a prior of one pseudo Eval task spread evenly over them, from 20,000 seeded draws (Q5.7). The Candidate fails if the whole interval is below zero, even inside the margin (Q6.11). It passes if the whole interval is above the margin and some of it is at or above zero, and is otherwise inconclusive, with how many more Eval tasks would settle it. Wrong findings are judged the same way, as a flag per Trial, and the code-review suite also reports pass^3 (Q4.4). The seed, draw count, prior, margin, credible level and thirdshift version are recorded with the bar, and "how many more Eval tasks" is the smallest number with at least a 0.8 chance of a clear verdict (Q5.7). The standing margin is 10 points (Q5.3), and the rules for void Trials are fixed with the bar too (Q6.5).
- **Experiments gate releases, not merges** (Q6.1). Runs Self-merge as now. A release whose changes since the last one touch an Eval suite waits for an Experiment on the commit being released, with the last release as the Baseline arm. A pass releases, and a fail or an inconclusive verdict waits for you. One Experiment covers every change in a release, so after a fail you revert, or run an Experiment on each change. The Experiment runs on the `thirdshift` host, not in CI. `scripts/release.sh` works out which suites the changes touch, starts the Experiment itself and waits for its verdict, printing progress. A pass carries on. A fail or an inconclusive verdict shows the interval and asks whether to release anyway, and an interrupted script picks up the same Experiment when run again (Q7.1).
- **Changes that reach production without a release** (Q7.2). Each Run records its Harness's version, in its Session traces and in its pull request's Built-with line, so the Scoring run can split Scores by version for both hosts. Before you change a Harness, Model or Effort default in the User config, you run an Experiment on one build with different flags, though nothing enforces it. Harnesses keep updating themselves, and an Experiment runs all its Trials on the Harness versions it started with.
- **Self-merge settings for each kind of command** (Q6.2). Keys under `[merge]` for `architect`, `pickup` and `security`, for what those Passes start, and `spec`, for every Spec PR, each defaulting to `merge.always`. A Run or Spec PR Self-merges only when every key that applies allows it, and a command's own words still win. It is #966, outside #698's Specs.
- **Grading.** Code Graders run first, where a check is mechanical. Then blind, fresh-session model Graders grade one packet per Eval task against its written success criteria, on a Model from neither Arm when another is available. You recheck borderline Scores and the ones that decide the bar (Q3.5).
- **Keeping Trials honest.** Each Trial gets a throwaway repository that is checked for later commits, with Harness memory off, inside bwrap that shows it only that repository and its Harness's login files (Q3.6). Each Trial also gets a fresh home holding only its login and the user-level instructions, rules, settings and hooks a Run's session reads, those four read-only (Q6.4). Codex's `auth.json` is bound read-write in place, so a refresh reaches the file production uses. Claude uses a one-year token from `claude setup-token`, kept in thirdshift's credentials file and passed as `CLAUDE_CODE_OAUTH_TOKEN`. The other Harnesses bind their one file once a live check shows each works that way.
- **Trials and the host's network.** bwrap keeps the host's network unless told not to, and a Trial's Harness needs the network to reach its provider. So a Trial might reach anything listening on 127.0.0.1, such as a viewer holding Scores. The sandbox research confirms it: loopback holds the Console, Caddy's admin API and a dozen other listeners. So each Trial gets a network of its own, with only its own loopback, and its own PID namespace (Q6.3). It reaches its provider through an allowlisting proxy that thirdshift runs outside the sandbox, over a Unix socket bound into it. The proxy allows only that Harness's provider hosts, and refuses names that resolve to loopback or to the host's own addresses. A Harness that ignores `HTTPS_PROXY` fails, and its Trial is void. Web search stays off by flag.
- **Graders run in the same sandbox as Trials, seeing only their packet.** On the host, a Grader's session could find what it is meant to be blind to: the Trials' Session traces and Arm labels, a Run's Command record, or the pull request itself through `gh`, Built-with line and all (Q3.5, Q4.6).
- **Running.** On demand, or when a release needs one (Q6.1), at most two Trials at once beside the factory, stopping at a plan-limit warning and resuming later (Q3.7). Experiments run on the `thirdshift` host, where #429's private Eval tasks are; `stephens` runs none.
- **Void Trials** (Q6.5). A Trial is void when the sandbox didn't start, the Harness couldn't reach its provider, the login failed or expired, the provider returned a server error before any work, Q3.7's plan-limit stop ended it, or the host or a memory cap that Runs don't have killed it. A timeout, a context-window overflow, a refusal, or anything the agent did inside its sandbox counts as a fail. A void Trial is re-run fresh, up to twice, and shown with its cause, counted per Arm. An Arm that keeps hitting its cap is reported as a finding. An Eval task with a Trial still void after its re-runs drops out of the interval for both Arms, and if more than a tenth of the Eval tasks drop out, the verdict is inconclusive.
- **Memory** (Q6.6). `loginctl enable-linger jacob` is run once on the `thirdshift` host, so each Trial runs in a `systemd-run --user --scope` of its own, with `MemoryHigh`, `MemoryMax` and `MemorySwapMax`. A Trial that outgrows its cap dies alone and is void. Each Trial also raises its own `oom_score_adj`. The cap is set once a Trial's footprint is measured.
- **The implement suite** (Q6.7) runs on the host's toolchains, in bwrap. Each Eval task is prepared once at its base commit, with network, and checked that the merged fix's tests fail there and pass at the fix, then kept read-only for each Trial to copy. Its clone is time-safe, as SWE-bench's are, and preparation fails if `git log --all` shows a later commit. Code Graders run the fix's tests with no network. Per-repository images come only when a commit stops building on the host, a repository needs services, or Experiments move to a bigger machine.
- **Starting a Trial.** A hidden flag runs one session through the code a Run uses and prints one JSON line, and `thirdshift experiment` starts and stops it (Q5.6). An Arm is a thirdshift build plus a Harness, Model and Effort (Q3.8). Trials never write a Command record, and their logs sit outside the factory's logs folder, so the Console's Inbox, Usual ranges and Silent ignore them. Their Experiment is a Command, though (Q6.8).
- **An Experiment is a Command** (Q6.8). `thirdshift experiment` writes a Command record and a Command log, with its Trials and Graders beneath it, never as Runs. The Console shows it live and can Stop it, and the Inbox shows its verdict, a failed Experiment included. Its Trace holds its Trials and Graders, as a Pass's holds its Runs.
- **Arms** are built the same way from two commits. For a release, the Candidate is built from the commit being released and the Baseline from the last release (Q6.1). For a change tried on its own, the Candidate is built from its branch and the Baseline from where that branch left `main`. A change to a Harness, Model or Effort default that needs no code uses one build with different flags (Q4.3).
- **Spec-review Trials** get a local bare repository as their origin, and only their review reports are graded (Q3.11).
- **promptfoo is out** (Q5.6). Fixing its telemetry switch upstream is still a possible first contribution, beside reviewing OpenTelemetry Rust's file exporter (#3763, Q5.8).
- **The Console shows Experiments in full, and every trace** (Q3.13, Q5.5). The span tree grows out of the Waterfall during the Session-trace rework, and span details go in the Peek panel. A /prototype session designs those two pages first, borrowing from Phoenix's compare view and MLflow's trace view. There's no second viewer for now. If you want search across Runs beyond #813's charts, MLflow is trialled behind a sign-in of its own, linked by trace ID, after a memory check. You can score Runs, confirm or correct a Bug origin, and approve a proposed Eval task in the Console, each also a CLI command, and the Console hides the model's Scores until you've entered yours. Starting an Experiment stays in the CLI. ADR 0016 is amended once, for these and #919's dismissals (Q6.9).
- **Eval data stays private under `~/.thirdshift/evals/`** (Q2.5, Q6.10): `suites/` for each Eval suite's Eval tasks, `experiments/` for each Experiment's Trials, Scores and verdict, and `scoring/` for the Scoring runs' Scores and Bug origins. #429's files move there from `~/.thirdshift/replays/` once the Eval task format exists. The repository holds the runner and the Eval task format, and research notes give counts only.
- **Session traces replace Session logs** (Q2.1, Q3.19). Each session writes two files where its Session log is today, both named after the session, since the OTLP file format allows one type of data per file (Q5.9). One holds a log record for each Harness event, written as it arrives, which the Console's live view reads and Silent watches. The other holds spans, written as each ends. ADR 0019 is amended on `main` to say so. All of a command's sessions share its trace ID (Q3.16). Spans also go to an OTLP endpoint when one is set. An interruption closes the open spans with an error status, and after a hard kill their records are already on disk (Q3.15).
- **What a Session trace holds** (Q3.14): the GenAI conventions' fields, `thirdshift.*` attributes for what those lack, and each raw Harness event. It is trimmed only after a round-trip check shows that nothing you use is lost, and it records the conventions version it follows. Model evidence and review reports stay beside each session's file, named from its path as now.
- **Terms** (Q3.17): a Trace is one command's whole tree, and a Session trace is one session's part, in place of Session log. That answers #700. Command logs and Activity logs stay logs. ADR 0019 records the switch (#920). The glossary takes Trace and Session trace when the switch is built, so factory Runs working on today's logs aren't told to call them Session traces. Span and log record stay OpenTelemetry's own terms, outside the glossary (agreed in chat on 2026-10-21).
- **The Console's rework** (Q3.19): its log view renders Session traces, first by unwrapping each record's raw event for its Claude and Codex code, then for all six Harnesses. The Waterfall takes tool times from the records and drops its Command-log matcher, and `show` reads the latest record. Silent's file-growth rule doesn't change.
- **A Trace's upper levels** (Q4.10). The command, its Runs and their stages come from the Command record. Each Session trace carries IDs computed from it, the Console puts the whole Trace together, and an export command writes it as OTLP for other tools.
- **Old Session logs** (Q4.11) are converted once into Session traces, with the code that writes them live. Each host converts its own, Security sessions' included, and keeps the originals until the conversion is checked. A record without a time gets one estimated from the Command log, marked as estimated. The conversion doubles as Q3.14's round-trip check.
- **The OTLP writer** (Q5.8) is a module of thirdshift with no thirdshift types. It follows the format's encoding rules, and is tested by round trips through the official types, a test-only dependency, and by the Collector's file receiver. It moves into a crate of its own, such as `otlp-jsonl`, if anyone else wants it, under a name without "opentelemetry" or "otel". You help upstream by reviewing and testing #3763.
- **Codex's diffs** (Q5.10, #854). thirdshift reads each edit's diff from Codex's own session file and adds it to the matching record in the Session trace, marked as Codex's record of the edit. Edits are matched by order and file path. Shell edits stay without a diff, and if the file can't be read, the record stays as it is. Old Codex logs get their diffs in the conversion (Q4.11), and the Session-trace Spec closes #854.
- **Security sessions and their Session traces stay on the machine.** The Console shows them behind its sign-in, on that same machine, as #776 specifies. That is consistent with Q2.2.
- **Run metrics** (Q4.5) keep each signal apart, never one number:
  - from the Run: its outcome, Repairs, CI rounds, Unaddressed findings, the review's findings by kind, and each stage's time against its Usual range;
  - from its Session traces: tokens by Model, cost where the Harness reports one, tool errors, permission denials, killed work, repeated tool calls, and destructive commands a code Grader can spot.

  There is no price table. Run metrics attach to the Run's Command record. Their trends belong with #813's charts, under its rules: a CLI command with `--json` first, drawn from the Command records and logs, and nothing loaded from another site. Q5.2 named them.
- **Production Scores** (Q4.6, Q4.7). A model Grader grades a random sample of about 10 finished Runs a week, spread across the Harnesses and Models in use, on a Model other than the Run's. It sees the issue, the merged diff and the pull request, but not the Harness, Model or Effort. A Claude-built pull request names its Harness and Model in three places: the Built-with line, Claude Code's "Generated with Claude Code" line, and the commits' Co-Authored-By trailers. Codex- and Muse-built ones carry only the Built-with line. A missing line would give the Harness away as surely as a present one, so the packet leaves out all three for every pull request. #937 asks whether Claude sessions should stop adding the other two. That means the diff goes in without commit messages. It grades five things separately: Correct, Scoped, Tested, Honest and Standards. You grade some of the same Runs, and its Scores show as uncalibrated until they agree with yours. It stops at a plan-limit warning. Production Scores watch for drift, and Experiments decide changes.
- **The Scoring run** (Q5.1) is a new kind of Command, started weekly by cron on the `thirdshift` host and covering both hosts.
  - It samples the week's merged factory pull requests in every repository either host works on, spread across Harnesses and Models, and scores them from GitHub. Honest judges only the pull request's claims.
  - It proposes a Bug origin for each `bug` issue closed that week, whoever fixed it. Its first run works back through the 59 closed so far.
  - Its Scores and Bug origins are kept by pull request on the `thirdshift` host, beside Experiments. Session-trace signals stay on the host that ran each Run, so the `thirdshift` host's charts show Scores and Bug origins for both hosts, but tokens and the other Session-trace signals only for its own Runs.
  - The Console shows it and can stop it, as it does any Command.
- **Calibration** (Q5.4). You score each of Q4.7's five things pass or fail, with a reason: 20 past Runs first, without seeing the model's Scores, then 2 from each week's sample. A criterion's model Scores count as calibrated while they match yours on at least 18 of the last 20 Runs you both scored, and show as uncalibrated otherwise. A criterion that never calibrates stays marked without holding up the others. You score from the CLI or the Console (Q6.9).
- **Bug links** (Q4.8, Q4.9). A short session reads a bug's fix and the history, and names the commit that introduced the bug, if the history shows one. thirdshift maps that commit to its pull request, and to the Run that made it, if one did. Nothing counts until you confirm or correct the link from the CLI. A confirmed link counts against that Run, and proposes an Eval task for the code-review suite: the diff as it was reviewed, with a draft catch criterion. The Eval task joins the suite once you approve it. Confirming from the Console as well would amend ADR 0016.
- **Security runs stay out of production Scores and bug links.** A Grader or link session on another provider's Model would show a Security fix to a company that hasn't seen it (ADR 0015).
- **`main` was last merged into this branch on 2026-10-20,** after v0.13.0 and #920. Research before that date read the older code, so its code facts need rechecking before anything is built.
